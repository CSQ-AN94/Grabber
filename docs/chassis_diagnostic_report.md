# 底盘（AGV）无法运动 · 诊断简报

日期：2026-07-01
机器人：`rm@192.168.3.68`（随车电脑），底盘 AGV `169.254.128.2:5410`（Woosh SDK）

## 1. 问题现象

底盘 SDK 通信正常、状态正常、指令全部返回成功，但机械上**完全没有物理运动**——不转、不平移。

## 2. 基本状态确认（正常项）

- 网络：`169.254.128.2:5410` 可 ping 通、TCP 端口可连，SDK CLI 和自写测试程序均可正常连接。
- 电池：91%，未充电，最高温度 22°C。
- 硬件自检：`motor`（双电机）、`lidar`（双）、`camera`（双）、`sonar`（16 路）、`lift`、`roller` 全部 `kNormal`。
- 无长期未恢复的致命异常码（`AbnormalCodes` 为空或仅有历史提示级信息）。
- 初始化流程可以正常走通：`kUninit → kIdle`，控制模式可在 `kManual`/`kAuto`/`kMaintain` 间正常切换，均返回成功。

## 3. 已做过的运动测试（全部无物理响应）

| 序号 | 控制模式 | 控制接口 | 参数 | SDK 返回 | 实际位姿变化 |
|---|---|---|---|---|---|
| 1 | kManual | `twistReq`（连续速度） | 角速度 0.02~0.03 rad/s，约 10° | 全部 `Request succeed` | 无 |
| 2 | kAuto（已初始化 kIdle） | `twistReq` | 同上 | 成功 | 无 |
| 3 | kAuto（已初始化 kIdle） | `StepControl`（离散步进动作，`mode=kRotate`） | 角速度 0.03→0.2 rad/s，10° | 成功 | 无 |
| 4 | kMaintain（维护模式） | `StepControl` | 同上 | 成功 | 无 |
| 5 | kManual（重新初始化后） | `twistReq` | 角速度 0.12 rad/s，30° | 成功 | 转动前后 theta 漂移约 0.01~0.02 rad（远小于指令量，判断为传感器噪声/编码器漂移，非真实转动） |
| 6 | kManual | `twistReq`（直线速度） | 线速度 0.02 m/s，前进+倒退 5cm | 成功 | 位置 x/y **前后完全一致，零变化** |

第 6 项（直线平移）是最干净的反证：如果真的移动过，来回抵消后也会有类似量级的残留漂移；但这次 x、y 坐标前后**分毫不差**，说明驱动轮没有任何物理输出。

## 4. 中途发现的额外情况

- 底盘机身有一个物理「自动 / 手动 / 维护」旋钮，与 SDK 里 `ctrl: kManual/kAuto` 字段是**两套独立的东西**：
  - 旋钮拨到「自动」时，随车电脑（`192.168.3.68`）**断电、无法开机**；拨回「手动」才会自动开机。
  - 这个物理旋钮目前应保持在「手动」，否则连远程调试的电脑都上不了线。
- 历史状态码中出现过一次 `120601000000`（`kFault`，消息为空），出现在一次模式切换尝试附近，随后自行清除。这个数字码是 Woosh 私有编码，SDK 头文件/文档里查不到含义，需要厂家的错误码手册才能解读。
- 曾经发现夹爪遥控进程 `zhixing_ctrl.py` 的 TCP socket（169.254.128.18:8080）出现 `Recv-Q` 持续增长（3 秒内从约 11 万涨到 21 万字节），符合过往记录的"夹爪卡死"特征；同时 `head_servo_ctrl.py` 进程已退出。这两项与底盘无直接关系，是随车电脑重启过程中顺带发现的，如果后续要用夹爪/头部舵机，需要重跑一次官方 `upstart_all.sh` 恢复遥操。

## 5. 结论

已经系统性覆盖了软件层能想到的所有维度（3 种控制模式 × 2 种控制接口 × 转动/平移 × 大小角速度），结果一致：**SDK 层握手、鉴权、指令下发全部正常，但没有任何证据表明驱动轮获得了物理动力输出**。这不是调用方式或参数问题，问题出在 SDK 之下的某一层。

## 6. 可能原因（按可能性排序，均未经现场物理确认，需要人工排查）

1. **驱动轮未真正着地 / 处于维护支架上**：如果底盘被垫高或放在检修架上，电机转但轮子不接触地面，SDK 侧完全看不出来。
2. **驱动轮手推离合器 / 拖动锁处于脱开状态**：很多 AGV 有物理离合机构方便人工推行，脱开时电机再怎么发指令也不会传到轮子。
3. **急停回路被触发**：底盘急停按钮、安全触边或急停继电器状态不体现在 `HardwareState` 的电子自检字段里（自检只报"电机模块本身工作正常"，不代表急停回路允许输出）。
4. **驱动电机独立的电源/保险丝/断路器未接通**：即电控板正常上电，但驱动电机这一路单独没有供电。
5. **那个物理「自动/手动/维护」旋钮还有我们没摸清楚的联动逻辑**：目前只确认它控制随车电脑供电，不排除它同时也控制驱动允许信号，需要厂家文档确认三档各自真正解锁了什么。
6. **`120601000000` 对应的底层故障未真正清除**：虽然 `AbnormalCodes` 显示为空，但不排除该故障在更底层（电机驱动器固件）仍处于闭锁状态，需要物理断电重启或专用解锁指令才能复位。

## 7. 建议的下一步

- 现场检查第 1、2、3、4 条（驱动轮着地情况、离合器/拖动锁、急停按钮、驱动电机保险丝/断路器）。
- 联系 Woosh（底盘厂家）技术支持，提供本文档第 3 节的测试记录和第 4 节的 `120601000000` 故障码，请他们确认：
  - 三档物理旋钮各自解锁了什么权限；
  - `120601000000` 的具体含义和标准恢复流程；
  - 是否存在需要产线工具/专用解锁指令才能启用的驱动锁定状态。
- 在驱动层问题解决前，不建议继续在软件侧加大测试幅度或尝试其他指令组合——已经测穷了常规组合，继续测大概率无效且会消耗现场时间。

## 8. 现场补充确认（2026-07-01）

- 急停确认未触发。
- 据此，第 6 节里的原因 1（轮子未着地）、原因 3（急停触发）可以排除；重点转向原因 2（拖动锁/离合器）、原因 4（驱动电机独立供电）、原因 5（物理旋钮联动逻辑）、原因 6（`120601000000` 底层未清故障）。

## 10. 补充测试（2026-07-04）：release-control 假说已证伪

怀疑过："`kAuto`+`kIdle` 之后没有重新调用 `release-control`（之前只在 `kManual` 时调用过，必然因为不是 auto 模式而失败）"是导致驱动不解锁的原因。补测结果：

- 在 `kAuto`+`kIdle` 状态下重新调用 `release-control` → 返回 `ok=false msg=Request failed`（区别于之前"It is not auto mode"的前置校验失败，这次是过了前置校验、被业务逻辑真正拒绝）。
- 同状态下 `cancel-task` → 返回成功。
- 随后照常做 30° 转动测试 → 位置/角度几乎零变化（`theta` 漂移仅 0.00001 rad，x/y 完全不变），比之前几次测试的噪声还小。

结论：这个假说已证伪，不是漏调用的问题。但 `release-control` 被明确拒绝（而非"模式不对"）这条信息本身有价值，已加入第 9 节客服简报。

## 11. 找到官方状态码手册（2026-07-06）

用户在客服对话里发来了 Woosh 官方资料链接（seafile.wsrobotics.com），其中"软件二次开发接口"文件夹下有一份《悟时机器人状态码V1.0.1.xlsx》，是我们之前一直缺失的官方错误码含义表。下载后查到几条关键信息：

- **`120601000000` 不是故障**：查表得知它是"充电控制"模块的**正常**状态码（`充电控制正常 / Charge control normal`），不是我们之前以为的未知故障码。之前日志里它旁边显示 `state: kFault`，那个 `state` 字段记录的是**当时机器人整体状态**，不是这条状态码本身的严重级别——这条本身是良性的，之前第 9 节客服简报里问它是什么故障，这个问题已经可以自己回答，不用再问客服了。
- **确认了物理解锁机制的存在**：状态码表里多处提到"切到手动模式，按下解锁按钮推到安全位置"（Switch to Manual mode, press Unlock and push the AIV to safety zone），说明底盘上应该有一个物理"解锁"按钮，用于人工推行。急停按钮的释放方式是"顺时针旋转"（不是简单按一下弹起）。这两个物理部件之前没有确认过，建议现场找一下。
- **手册明确把"手动模式"描述为人工推行场景**：安全PLC相关条目写道"手动模式下，推动机器人速度超出限制速度0.3m/s"（Under Manual mode, pushing the robot at speed exceeds the limit 0.3m/s），暗示手动模式的设计意图可能是"允许人工推着走"，而不是"允许网络指令驱动着走"——这跟我们观察到的"三种模式下 twistReq 全部无响应"是吻合的，真正支持网络编程驱动的路径可能需要走调度系统（DMS），而不是我们这种直连 SDK 发速度指令的方式。
- 状态码表里"运动控制/步进控制"模块（`120301xxxxxx`）确实有"被占用"（`120301000022`，非自动模式或手动充电时触发）、"抢占中断"（`120301000202`）这类码，但我们每次测试后查询 `AbnormalCodes` 都是空的——说明底盘压根没有把我们的运动指令识别成"被占用/被打断"，是彻底没有登记，而不是登记了但拒绝。

**给客服的问题需要更新**：不用再问 `120601000000` 是什么（已自己查到），改为直接问——"网络 SDK 的 `twistReq`/`StepControl` 是否只在调度系统(DMS)托管模式下才会真正驱动电机？直连 SDK 发送速度指令在哪种模式下才能真正生效？"

## 12. 找到官方 SDK 接口文档，问题基本定位（2026-07-06）

用户本地下载了完整的"产品二次开发资料"文件夹（`~/Embodied AI/产品二次开发资料/`），里面有官方 PDF 文档 `软件二次开发接口/SDK&API/v1.2.6/woosh_robot_sdk_interface_v1.2.6.pdf`。查到三条决定性信息：

1. **`switchControlModeReq`（我们用来把控制模式切到 `kAuto` 的那个调用）官方文档写明："仅调试可用, 正常作业是请使用车体物理旋钮。"** 也就是说这个 SDK 调用只是软件层面的调试用覆盖，正式运行必须靠车身那个物理「自动/手动/维护」旋钮。我们这几天几乎全程物理旋钮停在「手动」档（唯一一次切到「自动」时随车电脑直接断电，没能测转动），软件层面的 `ctrl:kAuto` 很可能只是改了上报状态，没有真正打开驱动使能。
2. **`twistReq` 文档：「该接口在控制模式为自动模式且机器人状态为未初始化和空闲时请求有效。」** 我们软件层满足了这个条件（`ctrl:kAuto`+`state:kIdle`）但依然零响应——与第1条结合，说明真正的硬件使能可能仍然被物理旋钮（停留在手动档）锁着，软件条件满足不代表硬件条件满足。
3. **`actionOrderReq`（release-control/cancel-task 用的接口）文档：「该接口仅在控制模式为自动模式且机器人状态为任务中时请求有效。」** 我们调用时机器人状态是「空闲」而非「任务中」，所以第10节里 `release-control` 返回 `Request failed` 是必然的、正常的前置条件不满足，不是什么隐藏锁——这个疑点已彻底排除，不用再问客服。

**结论与下一步**：目前唯一还没有真正测过的组合是——**物理旋钮切到「自动」的同时发送运动指令**。之前每次测试物理旋钮都停在「手动」。下次建议：把旋钮切到「自动」（接受随车电脑会断电的代价），然后用客服提供的官方 APP（支持安卓/Windows，通过底盘热点连接，不依赖随车电脑）在该状态下测试底盘是否能动。如果 APP 也不能让它动，才需要真正怀疑硬件本身；如果 APP 能让它动，说明问题出在"随车电脑软件调用 ≠ 真正的自动模式硬件授权"这个环节，需要请教客服如何在软件层面（不碰物理旋钮）真正让 `twistReq` 获得硬件授权。

## 13. ROS2 通道验证（2026-07-06）：结果一致，排除"代码写错"的可能

装了官方 ROS2 Humble 版 `woosh_robot_agent`，走了一遍"切自动模式→初始化→转动"的完整流程（工具和用法见 [chassis_ros_control.md](chassis_ros_control.md)）。结果和原始 C++ SDK 测试完全一致：转动前后 `theta` 只变化约 0.014 rad（噪声级别），零物理响应。

这个 ROS agent 本质只是把同一套 Woosh SDK 协议包了一层壳，`/robot/Twist` 就是 `twistReq`，不是独立通道。这轮测试的价值在于：**排除了"之前的 C++ 测试程序写法有问题"这种可能性**——两套完全独立实现的客户端代码，走同一条协议，得到同样的零响应结果，说明问题确实不在客户端代码层面。
