## 1. 长方体与"点在里面吗"

### 1.1 一维：区间

**区间**就是数轴上一段连续的范围，写作 \([a, b]\)，意思是"从 \(a\) 到 \(b\) 之间的所有数（含端点）"。

判断一个数 \(x\) 在不在区间里，规则很简单：

\[
x\in[a,b] \iff a\le x\le b.
\]

✏️ **手算**：\(x=5\)，区间 \([3, 8]\)。\(3\le5\le8\) ✓ **在里面**。
\(x=9\)：\(9\le8\)？✗ **不在里面**。

### 1.2 二维：矩形

平面上一个矩形，由左下角 \((x_{min}, y_{min})\) 和右上角 \((x_{max}, y_{max})\) 定义。

```
 y
     ┌─────────────┐ (x_max, y_max)
     │             │
     │   矩形内部   │
     │             │
     └─────────────┘
(x_min, y_min)          x
```

判断点 \((p_x, p_y)\) 在不在矩形里：**两个区间条件必须同时成立**（"且"）：

\[
(p_x, p_y)\in\text{矩形} \iff (x_{min}\le p_x\le x_{max})\ \text{且}\ (y_{min}\le p_y\le y_{max}).
\]

✏️ **手算**：矩形 \([0,10]\times[0,5]\)，点 \((3, 8)\)。
横向：\(0\le3\le10\) ✓
纵向：\(0\le8\le5\)？✗（8 大于 5）
**两个条件不能同时满足 → 不在矩形里**（虽然横向没问题，纵向就把它挡在外面了）。

### 1.3 三维：长方体（AABB）

再加一维，就是**轴对齐长方体**（Axis-Aligned Bounding Box，缩写 **AABB**——"轴对齐"意思是长方体的边都平行于坐标轴，不歪斜）。

由最小角 \((x_{min},y_{min},z_{min})\) 和最大角 \((x_{max},y_{max},z_{max})\) 定义。

> **点在长方体里 ⟺ 三个坐标分别都落在各自的区间内。**

\[
\mathbf p\in\text{box} \iff (x_{min}\le p_x\le x_{max})\ \text{且}\ (y_{min}\le p_y\le y_{max})\ \text{且}\ (z_{min}\le p_z\le z_{max}).
\]

**三个条件必须同时成立**。任何一个不满足，点就在外面。

### 1.4 完整手算演练

本项目真实用到的一个长方体（`safety_profiles.json` 的 `table_top` 禁区）：

\[
\min=(-1.0,\ 0.36,\ -0.75),\qquad \max=(1.0,\ 1.5,\ -0.20)
\]

（这是右臂基座坐标系，单位米。含义：这是桌面所在的一大块空间，机械臂 TCP 绝对不能进去。）

✏️ **测试点 A**：\((0.2,\ 0.5,\ -0.4)\)

\[
x:\ -1.0\le0.2\le1.0\ ✓
\]
\[
y:\ 0.36\le0.5\le1.5\ ✓
\]
\[
z:\ -0.75\le-0.4\le-0.20\ ✓
\]

**三个都满足 → 在长方体里**（这个点在桌面禁区内，绝对不允许 TCP 到这里）。

✏️ **测试点 B**：\((0.2,\ 0.5,\ 0.1)\)（只改了 z）

\[
z:\ -0.75\le0.1\le-0.20\ ?
\]

\(0.1 > -0.20\)，**不满足** → **不在长方体里**（这个点在桌面上方，是安全空间——数值上 \(z=0.1\) 比桌面顶 \(-0.20\) 更高，即高于桌面）。

### 1.5 代码对照

`safety.py::FenceBox.contains`：

```python
def contains(self, point, margin_m=0.0):
    point = np.asarray(point, dtype=float)
    lower = np.asarray(self.minimum) + margin_m
    upper = np.asarray(self.maximum) - margin_m
    return bool(np.all(point >= lower) and np.all(point <= upper))
```

`np.all(...)` 就是"数组里的每一个都要满足"——正是 §1.3 那个"**三个条件必须同时成立**"的代码写法。`margin_m` 是余量，先按 0 理解，§12 会展开。

> ✏️ **检查题 1.1**：长方体 \(\min=(0,0,0)\)，\(\max=(2,2,2)\)。点 \((2,1,1)\) 在里面吗？点 \((2.01,1,1)\) 呢？
>
> **答**：\((2,1,1)\)：\(0\le2\le2\) ✓（**端点算在里面**，因为用的是 \(\le\) 不是 \(<\)），其余也满足 → **在里面**。\((2.01,1,1)\)：\(2.01\le2\)？✗ → **不在里面**。

## 2. 集合运算的直觉：交集、并集、子集

避障要用到三个简单的集合概念。

### 2.1 交集：都满足的部分

**交集（intersection）**：两个区域**都**覆盖到的部分。记号 \(A\cap B\)。

```
   A: ████████
   B:      ████████
交集:      ████         ← 两边都有的部分
```

**碰撞检测的本质就是问"机器人占据的空间"和"障碍物占据的空间"有没有交集。** 有交集 = 碰撞；没交集 = 安全。

### 2.2 并集：任一满足即可

**并集（union）**：两个区域**至少一个**覆盖到的部分。记号 \(A\cup B\)。

```
   A: ████████
   B:      ████████
并集: ████████████████    ← 两边覆盖到的全部
```

`table_model.py` 里，桌面禁区水平范围"只允许扩张"就是在做**并集**：

```python
minimum=(min(table.minimum[0], fit.x_range[0] - margin), ...)
maximum=(max(table.maximum[0], fit.x_range[1] + margin), ...)
```

`min(...)` 取更小的下界、`max(...)` 取更大的上界——这就是把"配置的范围"和"新测到的范围"取**并集**，结果只会更大不会更小（详见 §17–18）。

### 2.3 子集：完全被包含

**子集（subset）**：\(A\) 的每个点都在 \(B\) 里，记作 \(A\subseteq B\)。

`safety.py` 加载配置时会检查"允许区必须是总工作空间的子集"：

```python
for zone in profile.allowed_tcp_zones:
    if not (profile.tcp_workspace.contains(zone.minimum, 0.0)
            and profile.tcp_workspace.contains(zone.maximum, 0.0)):
        raise SafetyAbort(f"允许区 {zone.id} 超出总工作空间 {profile.tcp_workspace.id}")
```

**为什么要检查这个？** 因为如果配置写错了，允许区跑到工作空间外面，会出现"TCP 在允许区里、但同时又在工作空间外"的自相矛盾状态——这种配置错误必须在**加载阶段**就拦下来，而不是等到真机运动时才发现。

> ✏️ **检查题 2.1**：\(A=\{\text{在 }[0,5]\}\)，\(B=\{\text{在 }[3,5]\}\)。\(B\) 是 \(A\) 的子集吗？\(A\) 是 \(B\) 的子集吗？
>
> **答**：\(B\subseteq A\)（\([3,5]\) 完全在 \([0,5]\) 里面）。\(A\not\subseteq B\)（比如 \(1\in A\) 但 \(1\notin B\)）。

## 3. 体素化：把点云变成积木

### 3.1 问题

深度相机一帧能给出几十万个三维点（点云）。如果把这几十万个点原样喂给规划器做碰撞检测，会**慢到无法使用**——规划器要对路径上每个候选姿态检查是否和每个点碰撞，点数越多越慢。

### 3.2 解法：切成格子

把三维空间切成一个个边长固定的小立方体格子，叫**体素（voxel，"volume"+"pixel"，体积像素）**。

规则：**只要一个格子里有至少一个点，就把整个格子标记为"占用"**。原来的几十万个点，被压缩成几百个"占用格子"。

```
原始点云（密密麻麻）              体素化后（一格代表一片）
   ····:::····                        ▓▓▓
  ···::::::···          →            ▓▓▓▓▓
   ····:::····                        ▓▓▓
```

### 3.3 怎么算一个点属于哪个格子

设体素边长 \(v\)。一个点 \(\mathbf p=(x,y,z)\) 所在的格子编号是：

\[
(\text{key}_x,\ \text{key}_y,\ \text{key}_z) = \left(\left\lfloor\frac{x}{v}\right\rfloor,\ \left\lfloor\frac{y}{v}\right\rfloor,\ \left\lfloor\frac{z}{v}\right\rfloor\right).
\]

\(\lfloor\cdot\rfloor\) 叫**向下取整（floor）**：舍去小数部分，不管小数是多少都往下取。\(\lfloor 3.7\rfloor=3\)，\(\lfloor 3.1\rfloor=3\)，\(\lfloor -0.3\rfloor=-1\)（注意负数向下取整是往更小的方向）。

✏️ **手算**：体素边长 \(v=0.065\) 米（本项目的 `scene_voxel_m`），点 \((0.30, -0.10, 0.05)\)。

\[
\text{key}_x=\left\lfloor\frac{0.30}{0.065}\right\rfloor=\lfloor4.615\rfloor=4
\]
\[
\text{key}_y=\left\lfloor\frac{-0.10}{0.065}\right\rfloor=\lfloor-1.538\rfloor=-2
\]
\[
\text{key}_z=\left\lfloor\frac{0.05}{0.065}\right\rfloor=\lfloor0.769\rfloor=0
\]

**这个点属于格子 \((4, -2, 0)\)。**

### 3.4 反过来：格子中心在哪

知道格子编号，算这个格子代表的中心位置（方便告诉规划器"这里有障碍"）：

\[
\text{中心} = (\text{key} + 0.5)\times v.
\]

✏️ **手算**：格子 \((4, -2, 0)\)，\(v=0.065\)：

\[
x_{中心}=(4+0.5)\times0.065=4.5\times0.065=0.2925
\]
\[
y_{中心}=(-2+0.5)\times0.065=-1.5\times0.065=-0.0975
\]
\[
z_{中心}=(0+0.5)\times0.065=0.5\times0.065=0.0325
\]

**为什么加 0.5？** 因为格子编号对应的是格子的**左下角**（或者说起点），加 0.5 是取到**格子正中间**，代表这块空间更准确。

### 3.5 去重：同一格子只算一次

许多点会落在同一个格子里（点云很密）。去重之后，几十万个点可能只剩几百个格子。

`scene.py::build_scene_voxels`：

```python
voxel = params.scene_voxel_m
keys = np.floor(points / voxel).astype(np.int32)     # 每个点算出格子编号（§3.3）
unique = np.unique(keys, axis=0)                       # 去重
centers = (unique.astype(float) + 0.5) * voxel         # 每个格子的中心（§3.4）
```

`np.floor` 是向下取整；`np.unique(keys, axis=0)` 是"按行去重"（把每一行 \((\text{key}_x,\text{key}_y,\text{key}_z)\) 当一个整体，去掉重复的行）。

### 3.6 代价：精度换速度

体素不是精确形状——一个 6.5 cm 的格子里，哪怕只在角落有一个点，整个格子都被当成"占用"。这是用**精度**换**速度**：牺牲一点几何精细度，让规划器能在有限时间内处理成千上万个候选姿态。

**上限保护**：

```python
max_voxels = params.scene_max_voxels        # 550
if len(centers) > max_voxels:
    raise SafetyAbort("头部障碍体素超出安全场景预算，拒绝丢弃远处障碍: ...")
```

**注意这里的选择**：格子太多，代码**不是**偷偷丢掉一部分（比如只留最近的 550 个）来凑够预算，而是直接拒绝整个场景。§9 会讲为什么。

> ✏️ **检查题 3.1**：体素边长 0.1 米，点 \((0.25, 0.05, -0.15)\) 属于哪个格子？格子中心在哪？
>
> **答**：\(\text{key}=(\lfloor2.5\rfloor,\lfloor0.5\rfloor,\lfloor-1.5\rfloor)=(2,0,-2)\)。中心 \(=(2.5\times0.1,\ 0.5\times0.1,\ -1.5\times0.1)=(0.25,\ 0.05,\ -0.15)\)。（这个点恰好落在格子正中间，所以中心就是它自己。）

## 4. 点到线段的距离（圆柱通道的数学核心）

这是第 5 部分"右腕点云通道"的数学基础。

### 4.1 问题

给一条线段，起点 \(\mathbf s\)、终点 \(\mathbf t\)；再给一个点 \(\mathbf p\)。**\(\mathbf p\) 离这条线段有多远？**

⚠️ 注意不是"离直线多远"——直线是无限长的，线段是有限的一段。区别很重要。

### 4.2 先解决一个子问题：投影比例

想象太阳从正上方照下来，\(\mathbf p\) 在线段所在直线上的"影子"落在哪个位置。用一个比例 \(a\) 表示：\(a=0\) 是起点，\(a=1\) 是终点，\(a=0.5\) 是正中间。

公式（用到点积——不熟悉的话见[第一册](抓水瓶教程-1-抓取点估计.md)第 4 节）：

\[
a=\frac{(\mathbf p-\mathbf s)\cdot(\mathbf t-\mathbf s)}{\lVert\mathbf t-\mathbf s\rVert^2}.
\]

### 4.3 关键一步：把比例夹在 [0,1] 之间

如果影子落在线段**外面**（\(a<0\) 或 \(a>1\)），那"线段上离 \(\mathbf p\) 最近的点"其实就是线段的**端点**，而不是那个影子本身。

所以要用**夹取（clip）**操作：

\[
a_{\text{clip}}=\operatorname{clip}(a,\ 0,\ 1)=\begin{cases}0 & a<0\\ a & 0\le a\le1\\ 1 & a>1\end{cases}
\]

**直觉图解**：

```
       影子在线段外（左边）           影子在线段内            影子在线段外（右边）
  p                                              p
   \                                            /
    \                                          /
─────s══════════t────      s══════●══════t      s══════════t
     a<0，夹到 0                a=0.6，不用夹        a>1，夹到 1
   最近点 = s                最近点 = 影子处       最近点 = t
```

### 4.4 求最近点和距离

有了夹取后的比例 \(a_{\text{clip}}\)，线段上离 \(\mathbf p\) 最近的点是：

\[
\mathbf c=\mathbf s+a_{\text{clip}}(\mathbf t-\mathbf s).
\]

距离就是 \(\mathbf p\) 到 \(\mathbf c\) 的直线距离：

\[
d=\lVert\mathbf p-\mathbf c\rVert.
\]

### 4.5 完整手算演练

\(\mathbf s=(0,0,0)\)，\(\mathbf t=(0.20,0,0)\)，\(\mathbf p=(0.30,\ 0.03,\ 0)\)（注意这个点在终点**前面**，超出了线段范围）。

**第 1 步**，两个向量：
\[
\mathbf p-\mathbf s=(0.30,\ 0.03,\ 0),\qquad \mathbf t-\mathbf s=(0.20,\ 0,\ 0)
\]

**第 2 步**，分子（点积）：
\[
(0.30)(0.20)+(0.03)(0)+(0)(0)=0.06
\]

**第 3 步**，分母：
\[
\lVert\mathbf t-\mathbf s\rVert^2=0.20^2=0.04
\]

**第 4 步**，比例：
\[
a=\frac{0.06}{0.04}=1.5
\]

**第 5 步**，夹取：\(1.5>1\) → \(a_{\text{clip}}=1\)（**影子跑到线段外面了，最近点就是终点**）

**第 6 步**，最近点：
\[
\mathbf c=(0,0,0)+1\times(0.20,0,0)=(0.20,\ 0,\ 0)
\]

**第 7 步**，距离：
\[
d=\lVert(0.30,0.03,0)-(0.20,0,0)\rVert=\lVert(0.10,\ 0.03,\ 0)\rVert=\sqrt{0.01+0.0009}=\sqrt{0.0109}\approx0.104\ \text{米}
\]

**结果**：这个点离线段最近的地方是终点，距离约 10.4 厘米。

### 4.6 为什么必须夹取

如果**不夹取**，直接用 \(a=1.5\) 算"最近点"：

\[
\mathbf c_{\text{错误}}=(0,0,0)+1.5\times(0.20,0,0)=(0.30,\ 0,\ 0)
\]

距离 \(=\lVert(0,0.03,0)\rVert=0.03\)——**看起来更近，但这是错的**。这个"最近点" \((0.30,0,0)\) 根本不在线段上，是延伸出去的直线上的点。

**在避障里，这个错误会致命**：一个明明在终点**之后**（机器人根本不会经过那里）的物体，会被误判成"就在通行路径正中间"，导致明明安全的路径被拒绝。

> ✏️ **检查题 4.1**：\(\mathbf s=(0,0,0)\)，\(\mathbf t=(0,0.30,0)\)，\(\mathbf p=(0.05,\ -0.10,\ 0)\)（在起点后面）。求 \(a\)、夹取后的 \(a_{\text{clip}}\)、最近点、距离。
>
> **答**：分子 \(=(0.05)(0)+(-0.10)(0.30)=-0.03\)。分母 \(=0.09\)。\(a=-0.03/0.09=-0.333\)，夹到 \(a_{\text{clip}}=0\)（在起点之前）。最近点 \(=\mathbf s=(0,0,0)\)。距离 \(=\lVert(0.05,-0.10,0)\rVert=\sqrt{0.0025+0.01}=\sqrt{0.0125}\approx0.112\) 米。

## 5. 假设检验的直觉：怎么知道一个检查"真的在工作"

### 5.1 一个容易被忽视的问题

你写了一个安全检查，它从来没报过错。这意味着：

- **可能性 A**：一切都很安全，从没出现过该被拦的情况。
- **可能性 B**：检查本身根本没生效，无论发生什么它都说"没事"。

**这两种情况从"表面现象"上完全无法区分——都是"一直没报错"。** 但后果天差地别。

### 5.2 怎么区分：主动制造一个"必然失败"的场景

这是科学实验和工程测试的共同思路：**如果你不知道检查有没有在起作用，就故意制造一个它必须报错的场景，看它报不报。**

比如："我把一个大到不能再大的障碍物塞进机器人身体里，检查器还敢说'没事'吗？"

- 如果它**还说没事** → 检查器坏了（哪怕真障碍来了也不会拦）
- 如果它**报错了** → 至少这条路径是通的

### 5.3 三段式验证（比两段更严谨）

只做"故意造错误"这一步还不够。完整的验证要**三段**：

1. **基线（无障碍）**：先确认"什么都没有时，检查器说安全"——如果连这个都失败，说明测试本身的姿态选得有问题，不能怪检查器。
2. **故意制造障碍**：确认检查器能**发现**问题。
3. **撤掉障碍后复原**：确认撤掉障碍后，检查器**恢复正常**，没有留下"记忆"或状态污染。

```
基线（无障碍）: 应该说"安全"  ✓/✗
     ↓ 加入巨型障碍
探针（有障碍）: 应该说"不安全" ✓/✗
     ↓ 撤掉障碍
复原（无障碍）: 应该说"安全"  ✓/✗
```

只有**三段全部符合预期**，才能确认检查器真的在正常工作。

### 5.4 三段式能诊断出的四种状态

| 基线 | 加障碍后 | 撤障碍后 | 结论 |
| --- | --- | --- | --- |
| 安全 | 不安全 | 安全 | ✅ **一切正常** |
| **不安全** | 不安全 | 不安全 | ❌ 基线姿态本身有问题（不是检查器的错） |
| 安全 | **安全** | 安全 | ❌ 检查器根本没在检测碰撞（最危险的情况！） |
| 安全 | 不安全 | **不安全** | ❌ 清理/复原失败，场景状态被污染了 |

**这张表就是本项目 `classify_moveit_collision_probe` 的完整逻辑**，§19 会逐行拆解它的真实代码。

> ✏️ **检查题 5.1**：为什么"从来没报过错"不能证明一个安全检查在正常工作？
>
> **答**：因为"一直没出问题"和"检查器根本不检测问题"，表现出来的现象完全一样（都是不报错）。必须主动制造一个已知该报错的场景来验证，光靠日常运行的沉默无法区分这两种情况。

# 第 2 部分：为什么避障不是一个函数

## 6. 机器人不是一个点，桌子不是一个函数

### 6.1 两个天真的想法，为什么都不够

**天真想法一：只检查末端（TCP）在哪。**

机械臂有 7 节。末端安全不代表整条胳膊安全——肘部完全可能在半路扫过桌面：

```
        桌子
  ▓▓▓▓▓▓▓▓▓▓▓▓
        ↑
    肘部撞这里了！
   /
  /
 ●────────────● 夹爪安全到达目标
```

**天真想法二：把桌子的形状写成一个公式，一劳永逸检查。**

问题是"桌子在哪"这件事**不是固定的**——底盘每次停靠的位置有细微差异，桌子实际高度和配置文件的记录可能有出入（§17 会详细讲）。写死的公式会过期。

### 6.2 结论

避障必须同时解决**两个独立的难题**：

1. **谁在动**：机器人不是一个点，要么检查整条胳膊的几何，要么用别的手段补上"只查一个点"的漏洞。
2. **障碍在哪**：障碍物的真实位置要从传感器现场测，不能完全依赖静态配置。

**这两个难题任何单一层次的检查都解决不了。这就是为什么避障要分层。**

> ✏️ **检查题 6.1**：只检查 TCP 位置的检查器，能保证整条手臂不撞桌子吗？
>
> **答**：不能。TCP 安全只说明末端这一个点没问题，肘部、前臂等其他部位完全可能在同一时刻撞到障碍物——检查器对此一无所知。

## 7. 三个尺度、三层视力

本项目用**三层**检查，各自负责不同尺度、不同时机的问题：

| 层 | 检查什么 | 看到的范围 | 什么时候起作用 |
| --- | --- | --- | --- |
| **① MoveIt 整臂碰撞** | 整条手臂 + 工具的几何，对场景体素、桌面盒、自身、左臂 | 头部相机能看到的一切 | 规划阶段，全局转移前 |
| **② 电子围栏** | 只有 TCP 这一个点，对工作空间/禁入盒/允许区 | 配置好的长方体规则 | 规划复核 + 每次局部运动前 |
| **③ 右腕点云通道** | 夹爪正前方的一个圆柱形区域 | 腕部相机的实时画面 | 只在最后接近的几厘米 |

**关键的直觉图**：

```
①MoveIt整臂碰撞    看得最"全"（整条胳膊），但只看头部相机看到的静态场景
②电子围栏          看得最"窄"（一个点），但规则最明确、不依赖实时感知
③腕部通道          看得最"近"（只是最后一段路），但最实时、最贴近真正的危险时刻

     全局 ────────────────────────────────→ 局部
   ①MoveIt整臂 ────── ②电子围栏 ──────── ③腕部通道
   (粗，但顾及整条胳膊)  (点，但语义明确)   (窄，但最新鲜)
```

**没有任何一层单独就够。它们的盲点各不相同，叠加起来才形成完整的保护。** 接下来三个部分逐层拆解。

> ✏️ **检查题 7.1**：为什么右腕点云通道检查只在最后接近时用，而不是全程都用？
>
> **答**：右腕相机视野窄、离目标近才能看清夹爪正前方的情况。全局转移阶段目标还很远、路径复杂，腕部相机既看不到全局也不适合承担这个任务；这一层是专门为"最后几厘米"设计的。

## 8. 场景体素怎么来的

### 8.1 完整流程

```
头部深度图 + 内参
      ↓  §3 的反投影（针孔模型，见第一册第 2 节）
基座系点云（几十万点）
      ↓  §3 的体素化
占用格子列表（几百个）
      ↓
交给 MoveIt 当"世界障碍"
```

### 8.2 代码：`scene.py::_base_points`

```python
def _base_points(depth, K, T_base_camera, params, stride=6,
                  min_depth_m=None, max_depth_m=None, bottom_crop=None):
    max_v = min(depth.shape[0], bottom_crop)
    vv, uu = np.mgrid[0:max_v:stride, 0:depth.shape[1]:stride]
    zz = depth[vv, uu]
    valid = (np.isfinite(zz) & (zz >= min_depth_m) & (zz <= max_depth_m))
    z = zz[valid]
    ...
    camera_points = np.column_stack((
        (u - K[0, 2]) * z / K[0, 0],
        (v - K[1, 2]) * z / K[1, 1],
        z, np.ones_like(z),
    ))
    return (T_base_camera @ camera_points.T).T[:, :3], u, v
```

**注意 `stride=6`**：不是每个像素都拿来算点，而是**每隔 6 个像素**取一个（`np.mgrid[0:max_v:stride, ...]`）。这是又一处"精度换速度"——原图有几十万像素，跳着采样能大幅减少计算量，同时仍能覆盖整个场景。

### 8.3 量程限制

```python
min_depth_m: float = 0.25       # 头部场景最近 0.25 米
max_depth_m: float = 2.2        # 头部场景最远 2.2 米
```

比[第一册](抓水瓶教程-1-抓取点估计.md)里瓶子定位用的量程（0.12–0.65 米）宽得多，因为这里要覆盖整个工作场景，不只是瓶子那一小块。

> ✏️ **检查题 8.1**：为什么头部场景的量程（0.25–2.2 米）比瓶子定位的量程（0.12–0.65 米）宽这么多？
>
> **答**：瓶子定位只关心瓶子本身那一小块空间；场景避障要覆盖机械臂可能经过的整个工作范围，包括更远的墙、更近的桌子边缘,所以量程要宽得多。

## 9. 三个容易被忽略的清理步骤

`scene.py::build_scene_voxels` 的文档字符串和代码里，藏着三个非常容易被忽视、但对系统能不能正常工作至关重要的清理步骤。

### 9.1 清理一：删掉水瓶检测框附近的点

```python
# Keep the local arm work volume, not the entire room. Do not delete the
# detector box or a target-centred sphere here...
```

（这句注释解释的其实是**为什么这里不删**——但在别的地方，比如右腕通道检查 `collision.py`，是**会删**的：）

```python
valid &= ~((uu >= x1 - 8) & (uu <= x2 + 8) & (vv >= y1 - 8) & (vv <= y2 + 8))
```

**为什么必须删掉目标瓶附近的点？** 因为如果不删，目标瓶本身会被系统当成"障碍物"，规划器会**拒绝任何靠近它的路径**——机器人永远抓不到瓶子，而且报错看起来像是"路径不可达"，非常容易误诊为可达性问题而不是逻辑 bug。

**为什么全局场景体素这里选择不删？** 见代码注释：全局转移只要到达观察位就够了，不需要真的碰到瓶子；如果这里也挖掉瓶子周围的一个洞，万一瓶子旁边紧挨着一个真实障碍，那个障碍也会被这个洞误删。**"删不删"取决于这一层的检测半径需不需要精确接触目标**——真正的接触判断留给局部接近和腕部通道去做。

### 9.2 清理二：删掉图像下方区域

```python
bottom_crop: int = 405
```

头部相机固定视角拍下去，图像**下方**常常拍到的是**机器人自己的身体和手臂**。

**为什么必须删？** 因为 MoveIt 已经通过机器人的三维模型（URDF/SRDF）处理**自碰撞**了——它自己知道手臂在哪、会不会撞到自己。如果再把"看到的自己"喂进去当**世界障碍**，就会出现"起始姿态本身就在障碍里"的荒谬情况：机器人的手臂被当成了它自己要躲避的东西。

代码注释直白地说明了这一点：

> MoveIt handles robot self-collision from the URDF/SRDF; feeding those pixels back as world obstacles would make the start state falsely collide with itself.

### 9.3 清理三：只保留瓶子附近的工作范围

```python
relative = points - target
valid_workspace = (
    (np.linalg.norm(relative[:, :2], axis=1) < 0.95)
    & (np.abs(relative[:, 2]) < 0.75)
)
```

只保留水平距离目标 < 0.95 米、垂直距离 < 0.75 米的点。远处的墙、房间另一头的东西，不影响这次抓取任务，删掉能大幅减少体素数量。

### 9.4 三个清理的共同逻辑

| 清理 | 删掉什么 | 不删会怎样 |
| --- | --- | --- |
| 目标附近（局部层） | 瓶子本身 | 瓶子被当障碍，永远抓不到 |
| 图像下方 | 机器人自己的身体 | 起始姿态就"撞了"，一开始就报错 |
| 工作范围外 | 远处不相关的场景 | 体素数量暴增，规划变慢甚至超预算 |

**这三条都是"把不该算作障碍的东西挖掉"，但每一条挖的原因都不同——目标是任务相关性、机器人是自己的模型已经处理了、远处是性能预算。混淆这三个理由，很容易在改代码时错误地把某个清理套用到不该用的地方。**

> ✏️ **检查题 9.1**：如果忘了"删掉图像下方区域"这一步，会发生什么现象？
>
> **答**：机器人自己的手臂/身体会被当成世界障碍物喂给 MoveIt。因为起始姿态本身就"包含"这些体素（手臂当然和自己重叠），MoveIt 会在还没开始规划时就报告起始状态碰撞，导致所有规划请求都失败。

## 10. 工具保护体：手臂之外还有夹爪

### 10.1 为什么手臂模型不够

MoveIt 的机器人模型（URDF/SRDF）描述的是**出厂时的手臂结构**。但末端装的夹爪、以及夹爪工作时占据的额外空间，未必被完整建模。

本项目额外定义了一个**工具保护体（tool guard）**——一个围绕工具末端的虚拟防撞盒，规划时把它也算作"机器人占据的空间"的一部分。

### 10.2 参数

```python
tool_guard_xy_m: float = 0.10          # 横截面尺寸
tool_guard_length_m: float = 0.19      # 沿工具轴长度
tool_guard_center_z_m: float = 0.095   # 中心沿轴偏移
```

这三个数定义了一个围绕夹爪的长方体：横截面 10×10 厘米，沿轴长 19 厘米,中心在法兰前方 9.5 厘米处。这个盒子比夹爪本身略大，覆盖夹爪张开时的实际占用空间和一定的安全余量。

### 10.3 深入详解篇里的补充说明

之前的深入详解教材中有一句很关键的话（`core.py:148` 附近的注释思路）：**工具保护体是比固定防撞盒更宽、更不可预测的碰撞形状**——因为夹爪的朝向会随手臂姿态转动，这个盒子在空间里的实际位置和朝向是动态计算的，不是一个写死不动的静态区域。

它随每次规划请求一起传给 MoveIt：

```python
tool_guard={
    "xy": self.params.tool_guard_xy_m,
    "length": self.params.tool_guard_length_m,
    "center_z": self.params.tool_guard_center_z_m,
},
```

### 10.4 为什么要单独建模，而不是直接扩大电子围栏的余量

这是个值得辨析的问题。电子围栏的余量（`clearance_m`）是加在 TCP **这一个点**周围的；而工具保护体是加在**整条工具几何**（包括夹爪张开的宽度和长度）周围,由 MoveIt 在**整臂碰撞检查**里考虑。

两者层次不同：围栏管的是"TCP 点在不在允许的任务空间里"，工具保护体管的是"夹爪这个有体积的东西会不会撞到障碍"。**同一个物理夹爪，需要在两个不同层次分别被建模**——这正呼应了第 7 节"三层各管一段"的思想。

> ✏️ **检查题 10.1**：为什么不能只靠电子围栏的 clearance_m 余量来处理夹爪的体积问题？
>
> **答**：电子围栏只检查 TCP 这一个点，clearance_m 只是把这个点的"安全区"稍微缩小/放大。它无法表达"夹爪是一个有宽度和长度的物体，会以不同姿态占据不同的空间"这件事——那需要在整臂碰撞检查里用一个真正的三维形状（工具保护体）来建模。

# 第 4 部分：第二层——电子围栏

## 11. 三种盒子，三种语义

电子围栏用三类长方体表达空间规则，`safety.py::SafetyProfile.assert_tcp_point` 按顺序检查：

```python
def assert_tcp_point(self, point, *, label, margin_m=None):
    margin = self.clearance_m if margin_m is None else margin_m
    ...
    if not self.tcp_workspace.contains(point, margin):          # ① 总工作空间
        raise FenceViolation(..., kind="workspace", ...)
    for obstacle in self.keepout_boxes:                          # ② 禁入盒
        if obstacle.contains_expanded(point, margin):
            raise FenceViolation(..., kind="keepout", ...)
    if not any(zone.contains(point, 0.0) for zone in self.allowed_tcp_zones):  # ③ 允许区
        raise FenceViolation(..., kind="allowed_zone", ...)
```

三种盒子的语义完全不同：

| 元素 | 本项目实测值（table_demo profile） | 作用 | 余量方向 |
| --- | --- | --- | --- |
| **总工作空间** | \(\min=(-0.65,-0.3,-0.75)\)，\(\max=(0.75,1.0,0.65)\) | 右臂被允许使用的最大范围，防止远离已验证操作区 | **内缩**（§1.3 的 `contains`） |
| **禁入盒** | `table_top`：\(\min=(-1.0,0.36,-0.75)\)，\(\max=(1.0,1.5,-0.20)\) | 明确禁止 TCP 穿入 | **外扩**（`contains_expanded`） |
| **允许区** | 两个，见 §13 | 即使不撞任何东西，也不让 TCP 飞到未验证的空间 | 不缩（§12.3 解释原因） |

**三种检查都要通过，缺一不可。** 只要有一种不满足就是 `FenceViolation`（一种特殊的 `SafetyAbort`，携带结构化信息方便下游做反馈重规划，见 §21）。

### 11.1 为什么需要三种，而不是一种"允许区"就够了

想想只有"禁入盒"会怎样：如果没有总工作空间的限制，机械臂**理论上**可以飞到桌子以外的任何角落——只要没撞到已知的禁入盒。但那些地方可能从未被验证过安全（可能有电线、可能有人、可能超出机械结构极限）。

想想只有"总工作空间"会怎样：机械臂可以在整个工作空间内**任意**移动，包括桌面本身（如果没有禁入盒的话）。

**必须三种叠加**：总工作空间划出一个大范围（"别跑太远"），禁入盒挖掉已知危险的区块（"这里绝对不能进"），允许区进一步收紧到"确实验证过安全"的走廊（"只能走这几条已知安全的路"）。

> ✏️ **检查题 11.1**：一个 TCP 点在总工作空间内，也没进任何禁入盒，但不在任何允许区里。会通过检查吗？
>
> **答**：不会。三个条件必须**全部**满足。哪怕没撞任何已知障碍，只要不在已验证的允许区内,就会被 `FenceViolation` 拒绝（`kind="allowed_zone"`）。

## 12. 余量为什么有的外扩有的内缩

### 12.1 两个方向

```python
def contains(self, point, margin_m=0.0):            # 内缩
    lower = np.asarray(self.minimum) + margin_m       # 下界往里推
    upper = np.asarray(self.maximum) - margin_m       # 上界往里推
    ...

def contains_expanded(self, point, margin_m=0.0):    # 外扩
    lower = np.asarray(self.minimum) - margin_m       # 下界往外推
    upper = np.asarray(self.maximum) + margin_m       # 上界往外推
    ...
```

### 12.2 手算对比

用同一个盒子 \(\min=(0,0,0)\)，\(\max=(1,1,1)\)，余量 0.1，理解两种效果的区别。

**内缩版**（`contains`，判定"点必须严格在盒子内部，留 0.1 的安全边"）：

\[
\text{有效范围} = [0+0.1,\ 1-0.1] = [0.1,\ 0.9]
\]

原本盒子里的点 \((0.05, 0.5, 0.5)\)：\(0.05 < 0.1\) → **不满足**（虽然点在原始盒子里，但太靠边了）

**外扩版**（`contains_expanded`，判定"点只要接近盒子（含盒外 0.1 范围）就算"）：

\[
\text{有效范围} = [0-0.1,\ 1+0.1] = [-0.1,\ 1.1]
\]

原本盒子外的点 \((-0.05, 0.5, 0.5)\)：\(-0.1\le-0.05\le1.1\) → **满足**（虽然点在原始盒子外面，但离得太近了）

### 12.3 为什么方向相反：统一的意图

两种余量看似方向相反，其实**背后是同一个意图：离危险远一点**。

- **工作空间**：里面是安全区，**外面**是危险（越界）。所以内缩边界，让"安全区"变得更保守——原本贴着边界的点不再算数。
- **禁入盒**：里面是危险（撞桌子），**外面挨着**也算危险（离桌子太近，稍有误差就撞了）。所以外扩边界，让"危险区"覆盖得更宽。

```
工作空间（内缩）：              禁入盒（外扩）：
┌─────────────────┐          ┌ ─ ─ ─ ─ ─ ─ ─ ┐  ← 外扩后的判定边界
│ ┌ ─ ─ ─ ─ ─ ─ ┐ │          │ ┏━━━━━━━━━━━┓ │
│ │  有效安全区  │ │          │ ┃   桌子    ┃ │
│ └ ─ ─ ─ ─ ─ ─ ┘ │          │ ┗━━━━━━━━━━━┛ │
└─────────────────┘          └ ─ ─ ─ ─ ─ ─ ─ ┘
  ↑ 边缘一圈也算越界              ↑ 这一圈也算撞了
```

### 12.4 为什么允许区不缩

这是本项目一个**反直觉但有据可依**的设计。允许区检查用的是 `contains(point, 0.0)`——**不带余量**：

```python
if not any(zone.contains(point, 0.0) for zone in self.allowed_tcp_zones):
```

`safety.py` 的注释解释了为什么：

> Allowed zones are authored as already-safe corridors. Do not shrink each box independently: doing so creates artificial gaps where two valid transit volumes overlap.

**图解为什么**：假设两个允许走廊部分重叠，TCP 要从 A 走到 B：

```
不缩（正确）:
   ┌────────A────────┐
              ┌────────B────────┐
   ─────────────────────────────→  全程都在某个允许区里 ✓

各自缩（错误）:
   ┌──A──┐
              ┌──B──┐
   ────────✗✗✗────────→  中间出现人为空隙，明明安全的路被拒！
```

**余量已经由外层工作空间的内缩和禁入盒的外扩保证了。允许区再各自内缩就是重复施加同一份保守，副作用是在重叠处切出不该有的空隙。**

> ✏️ **检查题 12.1**：为什么工作空间内缩、禁入盒外扩，两者最终都是让"合格的点"变得更少（更保守）？
>
> **答**：因为无论哪个方向，效果都是"离原本的边界更远才算数"——工作空间内缩让边缘的点不再合格，禁入盒外扩让原本没进盒子的点也被判定危险。两者都在朝"更保守"的方向调整判定标准。

## 14. 给 MoveIt 的盒子为什么要额外垫大

### 14.1 一个容易漏掉的落差

MoveIt 只做**几何碰撞**检测,它**不知道**围栏还要求 TCP 离禁入盒有 `clearance_m` 的余量。

如果直接把禁入盒的**精确**尺寸告诉 MoveIt，MoveIt 会规划出"贴着盒子表面飞"的路径（几何上确实没碰到），但这条路径随后会被独立电子围栏（要求 2.5 cm 余量）拒绝。

### 14.2 解法：给 MoveIt 的盒子额外垫大

`safety.py::moveit_collision_boxes`：

```python
padding = self.clearance_m + 0.02
result = []
for box in self.keepout_boxes:
    item = box.moveit_box()
    item["size"][0] += 2 * padding
    item["size"][1] += 2 * padding
    item["center"][2] += padding / 2
    item["size"][2] += padding
    ...
```

✏️ **手算**：`clearance_m = 0.025`，所以：

\[
padding = 0.025 + 0.02 = 0.045\ \text{米} = 4.5\ \text{厘米}
\]

**四个水平侧面**（x、y 方向）各往外垫 `padding`，所以尺寸各增加 `2 * padding`（两侧都要垫）：

\[
\Delta\text{size}_x = \Delta\text{size}_y = 2\times0.045=0.09\ \text{米}
\]

**顶面**也往上抬（只往一个方向垫，因为底面不影响桌面上方规划）：

\[
\text{中心}_z\ \text{增加}\ padding/2=0.0225,\qquad \text{size}_z\ \text{增加}\ padding=0.045
\]

（中心上移半个垫量、尺寸增加一个垫量，效果是**顶面往上抬了整整一个 padding**，底面不动。）

### 14.3 为什么给 MoveIt 的余量比围栏本身（2.5 cm）多出 2 cm

这是一次真实调参的产物。深入详解教材记录的历史是：

> 2026-07-17 真机 observe 实测：clearance_m+1cm 的旧余量不够——MoveIt 按其内部路径采样分辨率认为"没碰垫大的盒子"，但独立围栏用更密的插值复核发现实际路径已经比垫大后的盒子边界还深入 1~1.7cm。

**根因**是 OMPL（MoveIt 底层规划算法）的**碰撞检测采样密度**问题——这是[第二册·路径规划](抓水瓶教程-2-路径规划.md)第 20 节详细讲过的"lvsf 参数从 0.01 收紧到 0.0025"那次真实故障的另一面。当时的应对是**双管齐下**：一边收紧 MoveIt 内部的采样密度（根本修复），一边把这里的垫量从 +5cm 回调到 +2cm（因为采样密度修好后，理论上不再需要那么大的垫量）。

### 14.4 诚实的未验证声明

`safety.py` 的注释里有一段极其重要的话：

> 但这个具体数值组合（更密的lvsf + 更小的padding）还没有真机验证过，不能只信这个推算——下次连机器人必须先跑 observe/plan 多轮确认没有回到 narrow-band拒绝循环，再信任这个余量。

**这是本项目最值得学的工程态度**：算出来的数字是"有依据的假设"，不是"已验证的事实"。两者在文档里必须被明确区分。

> ✏️ **检查题 14.1**：为什么给 MoveIt 的余量（4.5 cm）比围栏本身要求的余量（2.5 cm）大？
>
> **答**：因为 MoveIt 的碰撞检测是按固定采样密度离散进行的，两次采样之间存在盲区（详见第二册第 20 节），实际路径可能比几何上"看起来没碰"的位置更靠近障碍。多垫的部分是在补偿这个采样盲区,不是围栏本身要求变严了。

## 15. 完整推导圆柱通道判定

### 15.1 直觉

想象夹爪要沿一条直线冲向瓶子。以这条直线为轴，画一个半径固定的**圆柱**——这就是"通行管道"。任何东西只要落在这个圆柱里（且不是起点/终点附近的正常空间），就判定为**挡路**。

```
       ┌──────────────────┐
  ●════╪══════════════════╪════●
 TCP   └──────────────────┘   目标
        半径 corridor_radius_m 的
              圆柱通道
```

### 15.2 完整推导（对照 §4 的点到线段距离）

设 TCP 当前点 \(\mathbf s\)、锁定目标 \(\mathbf t\)、点云中任意一点 \(\mathbf p\)。

**第一步**，用 §4.2 的公式算投影比例：

\[
a=\operatorname{clip}\left(\frac{(\mathbf p-\mathbf s)^T(\mathbf t-\mathbf s)}{\lVert\mathbf t-\mathbf s\rVert^2},\ 0,\ 1\right)
\]

**注意这里的夹取范围更窄**——代码实际用的是：

```python
along = np.clip(((points - start) @ vector) / length_squared, 0, 1)
```

然后进一步要求投影不能太靠近端点：

```python
blockers = (
    (along > 0.08)
    & (along < 0.86)
    & (distance < params.corridor_radius_m)
)
```

**第二步**，最近点和垂直距离（§4.4）：

\[
\mathbf c=\mathbf s+a(\mathbf t-\mathbf s),\qquad d=\lVert\mathbf p-\mathbf c\rVert
\]

**第三步**，判定"可疑点"：投影在 (0.08, 0.86) 之间，且垂直距离 < `corridor_radius_m`（4.5 厘米）。

**第四步**，数一数可疑点总数，达到 `obstacle_min_points`（18 个）就中止。

### 15.3 为什么排除端点附近（0.08 和 0.86 这两个界）

**起点附近（along < 0.08）**：TCP 自身、夹爪自己的结构，天然就"贴着起点"。如果不排除，夹爪会把自己判成障碍物。

**终点附近（along > 0.86）**：目标瓶子本身、以及围绕瓶子附近正常存在的一些点（哪怕已经删掉了检测框区域,边缘仍可能残留一些点），太靠近终点的判定容易把目标本身的边界误判成"挡路"。

这两个界限**给起点和终点各留了一段"缓冲区"，只在中间段严格判定**。

### 15.4 完整手算演练

`corridor_radius_m = 0.045`，`obstacle_min_points = 18`。

TCP 当前点 \(\mathbf s=(0.40,\ 0.10,\ 0.30)\)，目标 \(\mathbf t=(0.40,\ 0.30,\ 0.30)\)（沿 y 方向直线接近，距离 0.20 米）。

假设点云里有一个点 \(\mathbf p=(0.42,\ 0.20,\ 0.31)\)：

**第 1 步**：
\[
\mathbf p-\mathbf s=(0.02,\ 0.10,\ 0.01),\qquad \mathbf t-\mathbf s=(0,\ 0.20,\ 0)
\]

**第 2 步**，点积（分子）：
\[
(0.02)(0)+(0.10)(0.20)+(0.01)(0)=0.02
\]

**第 3 步**，分母：
\[
\lVert\mathbf t-\mathbf s\rVert^2=0.20^2=0.04
\]

**第 4 步**：
\[
a=\frac{0.02}{0.04}=0.5
\]

\(0.5\) 在 \((0.08,\ 0.86)\) 范围内 ✓（**这一步先检查投影范围，通过才继续算距离——这是实际代码的顺序，省去不必要的计算**）

**第 5 步**，最近点：
\[
\mathbf c=(0.40,0.10,0.30)+0.5\times(0,0.20,0)=(0.40,\ 0.20,\ 0.30)
\]

**第 6 步**，垂直距离：
\[
d=\lVert(0.02,\ 0,\ 0.01)\rVert=\sqrt{0.0004+0.0001}=\sqrt{0.0005}\approx0.0224\ \text{米}
\]

\(0.0224 < 0.045\) ✓ **这是一个可疑点**。

**如果这样的点凑够 18 个，`SafetyAbort`——夹爪前进的路上被判定为有障碍。**

> ✏️ **检查题 15.1**：同样的 \(\mathbf s,\mathbf t\)，点 \(\mathbf p=(0.40,\ 0.11,\ 0.30)\)（离起点很近）。它会被判定为可疑点吗？
>
> **答**：\(\mathbf p-\mathbf s=(0,0.01,0)\)，点积 \(=0.01\times0.20=0.002\)，\(a=0.002/0.04=0.05\)。\(0.05<0.08\) → **投影落在起点缓冲区内，不算可疑点**（哪怕它离直线很近，也会被跳过）。

## 16. 为什么这层只在最后接近时用

### 16.1 全局阶段用不上它的原因

在全局转移阶段，目标可能还在很远处、中间要绕过各种障碍——"从当前位置到目标画一条直线"这个概念本身就没有意义，因为路径根本不该是直线（那正是[第二册](抓水瓶教程-2-路径规划.md)整册讲的问题）。

腕部相机的视野也窄，全局转移时它可能根本看不到目标方向的画面。

### 16.2 局部接近阶段恰好合适

局部接近本来就要求走**直线**（[第三册](抓水瓶教程-3-机械臂控制.md)第 9 节讲过：局部段刻意选择直线是为了可预测性）。既然路径本来就是直线,圆柱通道检查天然贴合。

而且这时候腕部相机离目标很近，恰好能看清夹爪正前方的情况——这是它**唯一**能派上用场、也**必须**派上用场的阶段：全局体素（来自头部相机）可能根本没捕捉到"刚刚被人放到桌上的一个新物体"，只有实时的腕部通道检查才能发现它。

### 16.3 和另外两层的分工

| 层 | 发现"刚出现的新障碍"的能力 |
| --- | --- |
| ① MoveIt 整臂碰撞 | 基于规划**那一刻**的头部场景快照,规划完成后场景若变化，它不会重新检查 |
| ② 电子围栏 | 基于静态配置的长方体规则，不感知实时障碍（除非桌面自适应，见 §17） |
| ③ 右腕点云通道 | **每次局部段执行前**都重新拍一帧，是唯一能发现"最后一刻突然出现的障碍"的层 |

**这正是"分层各管一段"思想的具体体现：越靠近执行的最后一刻，越需要用最新鲜的感知数据。**

> ✏️ **检查题 16.1**：一个人在机器人规划完成、开始局部接近的过程中，往夹爪正前方放了一个杯子。哪一层最可能发现它？
>
> **答**：第三层，右腕点云通道检查。它在每次局部段执行前都重新拍一帧最新画面，是三层里唯一具备"实时发现刚出现的障碍"能力的一层。

## 17. 桌面为什么每轮重新测

### 17.1 问题：配置会过期

`safety_profiles.json` 里的 `table_top` 禁区是**某一天手动测量**写死的数字（配置注释里写着 "2026-07-15 via head RGB-D + calibrated extrinsics"）。

但现实中：

- 底盘每次自主停靠的位置有**细微差异**（几厘米量级的正常波动）
- 桌子本身可能被挪动
- 手眼标定存在误差

如果每次都完全信任写死的配置，就会出现两种错误：

- **配置的桌面比实际低/远** → 明明安全的空间被误判为危险，机器人不敢靠近
- **配置的桌面比实际高/近** → 真实桌面比配置认为的更危险，防护不足

### 17.2 解法：每轮从头部点云实测

`table_model.py::fit_table_top` 每一轮从头部深度图里,现场拟合出真实的桌面平面,再用这个实测结果去调整（而不是替换）围栏配置。

> ✏️ **检查题 17.1**：为什么不干脆完全信任每次的实测结果，扔掉写死的配置？
>
> **答**：因为实测本身也可能出错（视野遮挡、光照异常、算法偶发失败）。完全信任实测会失去"配置文件里记录的、经过现场验证的合理范围"这个参照系,一旦某次实测出错就没有任何东西能拦住它。§18 会看到,正确做法是"实测在容差内调整配置,超出容差就拒绝"，而不是"实测说了算"。

## 18. 四条保守规则逐条拆解

`table_model.py::adapt_profile_to_table` 的文档字符串明确列出了四条规则，全部**有界、且失败时一律拒绝（fail-closed）**：

### 18.1 规则一：容差内才自适应，超出直接拒绝

```python
height_error = abs(fit.height_m - old_top)
if height_error > params.table_fit_height_tolerance_m:      # 0.12 米
    raise SafetyAbort(f"实测桌面高度 z={fit.height_m:.3f} 与围栏配置顶面 z={old_top:.3f} "
                       f"相差 {height_error * 100:.1f}cm，超出自适应容差 ...")
```

✏️ **手算**：配置里桌面顶面 `old_top = -0.20`。今天实测 `fit.height_m = -0.19`。

\[
\text{误差}=|-0.19-(-0.20)|=|0.01|=0.01\ \text{米}=1\ \text{cm}
\]

\(1\ \text{cm} \le 12\ \text{cm}\)（容差）→ **在容差内，允许自适应**。

再算一个超容差的：实测 `fit.height_m = -0.05`（比配置高了 15 cm）：

\[
\text{误差}=|-0.05-(-0.20)|=0.15\ \text{米}=15\ \text{cm}
\]

\(15 > 12\) → **超出容差，直接 `SafetyAbort`**——桌子或底盘位置变化太大，必须重新走人工测量流程，软件不能自己"猜"这么大的差异。

### 18.2 规则二：顶面双向跟随

在容差内,禁入盒顶面跟着实测走——**可以升高,也可以降低**：

```python
maximum=(..., ..., fit.top_m)
```

**为什么是双向的？** 因为高度误差既可能让真实桌面**更靠近**机械臂（更危险，必须收紧），也可能让真实桌面**更远离**（更保守，可以放松）。只允许单向调整,会在另一个方向上出问题。

### 18.3 规则三：水平范围只扩不缩

```python
minimum=(min(table.minimum[0], fit.x_range[0] - margin),
         min(table.minimum[1], fit.y_front - margin), ...)
maximum=(max(table.maximum[0], fit.x_range[1] + margin), ...)
```

用的是 §2.2 的**并集**运算：新边界取"配置的"和"实测的"两者中**更宽**的那个。

**为什么水平方向和高度（规则二）处理逻辑不一样——一个双向、一个单向？**

**关键区别**：相机能不能**保证**看到桌子的真实边界。

- **高度**：只要相机能看到桌面上的一块区域,就能测出这块区域的高度,这个测量是**直接、可信**的。
- **水平边缘**：相机的视野是有限的（比如图像下方被裁掉了,见 §9.2）,如果算法"没看到"桌子边缘更远处的点,那只能说明"这次没测到那么远"，**不能**倒推成"那么远就没有桌子了"。

**"没看见" ≠ "不存在"。** 这正是规则四要强调的核心逻辑（下一节）。

### 18.4 规则四：允许区随桌面顶面同步移动,但保持相对余量

```python
for zone in profile.allowed_tcp_zones:
    floor = zone.minimum[2]
    attached = (old_top <= floor <= old_top + params.table_fit_zone_attach_band_m)   # 0.06
    if not attached:
        zones.append(zone)          # 和桌面无关的允许区,原样保留
        continue
    new_floor = fit.top_m + (floor - old_top)     # 保持原有的相对高度差
    ...
```

✏️ **手算**：某允许区底面 `floor = -0.18`，配置桌面顶 `old_top = -0.20`。

\[
\text{是否贴桌}:\ -0.20\le-0.18\le-0.20+0.06=-0.14\ ?
\]

\(-0.18\) 在 \([-0.20,\ -0.14]\) 之间 ✓ **判定为"贴着桌面的允许区"**（底面离桌面顶只差 2 cm，明显是"桌面上方紧贴着的任务空间"）。

假设今天实测桌面 `fit.top_m = -0.19`（比配置高了 1 cm）：

\[
\text{新底面}=-0.19+(-0.18-(-0.20))=-0.19+0.02=-0.17
\]

**允许区底面也跟着桌面一起抬高了 1 cm**——因为它是"贴桌面的",桌面变了,它的相对位置也要跟着变,否则会出现"允许区悬空"或"允许区扎进新桌面里"的荒谬情况。

### 18.5 双重保护：调整后不能退化、不能越界

```python
if new_floor >= zone.maximum[2] - 0.05:
    raise SafetyAbort(f"允许区 {zone.id} 底面随桌面自适应后过高，区域退化")
if not profile.tcp_workspace.contains((zone.minimum[0], zone.minimum[1], new_floor), 0.0):
    raise SafetyAbort(f"允许区 {zone.id} 底面随桌面自适应后越出总工作空间")
```

**第一条**：如果调整后底面几乎顶到了区域顶面（差不到 5 cm），说明这个允许区已经被压缩得没有实际意义了（"退化"）,直接拒绝而不是允许一个几乎不存在的允许区继续运行。

**第二条**：呼应 §2.3 的子集检查——调整后的允许区仍然必须完全落在总工作空间内部,否则拒绝。

### 18.6 四条规则汇总

| 规则 | 内容 | 保守方向 |
| --- | --- | --- |
| ① 容差限制 | 误差 > 12 cm 直接拒绝 | 超出可信范围就不猜 |
| ② 顶面双向跟随 | 可升可降 | 不管哪个方向错都要纠正 |
| ③ 水平只扩不缩 | 取并集 | "没看见"不等于"不存在" |
| ④ 允许区同步 + 双重保护 | 跟着桌面走,但设底线 | 不能退化、不能越界 |

> ✏️ **检查题 18.1**：为什么水平范围"只扩不缩",而桌面高度可以"双向调整"？两者不矛盾吗？
>
> **答**：不矛盾,因为两者衡量的是不同性质的东西。桌面高度的测量只要看到一块区域就是可信的直接观测,所以能双向纠正。水平边界的"没测到"是相机视野局限造成的,不能证明"那里没有桌子",所以只能保守地扩大(合并已知信息)而不能因为"没看见"就缩小。

## 19. 三态探针：怎么证明碰撞检测真的在工作

### 19.1 回到 §5 的问题

一个避障系统天天运行,从来没报过错。这到底是"真的一直很安全",还是"检测器压根没在检测"?

### 19.2 本项目的答案：`moveit_collision_selftest.py`

这个脚本**专门验证 MoveIt 的碰撞检测有没有在正常工作**，用的正是 §5.3 讲的三段式验证：

```python
_set_giant_box(node, apply_client, present=False, allow_missing=True)
baseline = _probe_state(node, validity_client)     # 探针一：基线（无障碍）

_set_giant_box(node, apply_client, present=True)
boxed = _probe_state(node, validity_client)         # 探针二：故意放一个巨型障碍

_set_giant_box(node, apply_client, present=False)
cleared = _probe_state(node, validity_client)       # 探针三：撤掉后复原
```

**"巨型障碍"具体是什么**：一个 4×4×4 米的大盒子，把整个机器人完全罩住：

```python
primitive.dimensions = [4.0, 4.0, 4.0]  # 把整台机器人罩住
```

**逻辑很直白**：如果碰撞检测真的在工作,机器人被这么大的盒子整个罩住,**必然**报告"碰撞了"（invalid）。如果它还敢说"没事"（valid）,那碰撞检测这个功能本身就是坏的。

### 19.3 一个真实的坑：探针姿态本身选错了

代码注释记录了一次真实的诊断错误：

> 2026-07-17 重新诊断发现，旧探针使用的关节姿态本身会让腕部撞到底盘，因而无盒子基线永远 invalid，并被旧脚本误诊成"碰撞几何没加载"。

**发生了什么**：旧版本用来测试的那个"标准姿态",本身就有问题——腕部在这个姿态下会碰到底盘。所以**连基线（没有额外障碍时）都报告"invalid"**。

工程师看到这个结果,误以为"MoveIt 的碰撞几何压根没加载"（因为直觉上"没障碍应该是 valid"）。但真正的原因是**测试用的探针姿态本身选得不对**——它跟"碰撞检测有没有在工作"完全是两回事。

**这正是 §5.4 那张表里第二行的真实案例**："基线不安全" → 结论应该是"探针姿态本身有问题",而不是"检测器坏了"。

### 19.4 修复：用一个已验证安全的姿态

```python
# 2026-07-15 真机示教并记录在 table_demo.home_joints_deg 的安全垂下姿态。
PROBE_RIGHT_DEG = [-10.368, 121.646, 55.372, 7.207, 22.587, 5.623, -147.391]
```

换成一个**已经在真机上验证过、确认安全**的姿态（就是 `home_joints_deg`，围栏配置里也记录着同一组数字），基线检查才能正确地显示"valid"。

### 19.5 完整的分类逻辑：`classify_moveit_collision_probe`

这就是[第二册](抓水瓶教程-2-路径规划.md)和之前深入详解教材提到过的函数，现在完整看它的逻辑：

```python
def classify_moveit_collision_probe(*, baseline_valid, boxed_valid, cleared_valid):
    if not baseline_valid:
        return ("baseline_invalid", "无障碍基线姿态已经碰撞，探针姿态或残留场景无效")
    if boxed_valid:
        return ("collision_missed", "巨型障碍盒中的姿态仍被判有效，世界碰撞检测未生效")
    if not cleared_valid:
        return ("cleanup_failed", "撤除巨型障碍盒后没有恢复，规划场景清理或同步失败")
    return ("healthy", "基线、碰撞拒绝和场景恢复均符合预期")
```

逐条对照 §5.4 那张表：

| 代码分支 | 对应 §5.4 表格的哪一行 | 诊断结论 |
| --- | --- | --- |
| `not baseline_valid` | 第 2 行（基线本身不安全） | 探针姿态选错了,不是检测器的问题 |
| `boxed_valid`（明明有巨型障碍还说安全） | 第 3 行（检测器根本没工作） | **最危险**：碰撞检测完全失效 |
| `not cleared_valid`（撤了障碍还说不安全） | 第 4 行（清理失败） | 规划场景状态被污染,没有正确复原 |
| 全部符合预期 | 第 1 行 | 系统健康 |

### 19.6 为什么这个自检极其重要

**因为它检查的不是"这次规划有没有撞",而是"负责判断撞没撞的那个机制本身,到底可不可信"。**

如果没有这个自检,前面讲的所有三层避障、所有精确到毫米的余量计算,都建立在一个未经验证的假设上："MoveIt 的碰撞检测确实在工作"。而 2026-07-17 那次真实的诊断错误告诉我们,**这个假设是可能出错的,而且出错时表现得和"一切正常"一模一样**（都是不报错）。

脚本最后的输出也体现了这份谨慎：

```python
if status == "healthy":
    print("\n结论：MoveIt 碰撞检查工作正常。")
    return 0
print(f"\n结论：MoveIt 碰撞自检未通过 [{status}]：{reason}。")
print("在诊断通过前，禁止把 MoveIt 的碰撞结论当作执行放行条件。")
return 2
```

**自检不通过时,明确禁止信任 MoveIt 的碰撞结论**——这比"报个警告然后照常运行"要严格得多。

> ✏️ **检查题 19.1**：探针测试报告 `baseline_valid=True`、`boxed_valid=True`、`cleared_valid=True`。用 `classify_moveit_collision_probe` 的逻辑判断结果是什么，为什么这是最危险的情况？
>
> **答**：`baseline_valid=True` 跳过第一个分支；`boxed_valid=True` 命中第二个分支，返回 `"collision_missed"`。这是最危险的情况,因为它意味着**哪怕把整个机器人罩进一个 4 米大盒子里,系统还坚持说"安全"**——碰撞检测完全没有生效,任何真实障碍都不会被发现,而系统表现上和"一切正常"完全一样(都不报错)。

## 20. 一个未建模障碍物的完整案例

### 20.1 场景

假设桌子边缘上，机器人开始运动之后，多了一个之前没有的杯子。追踪三层各自在什么时机能不能发现它。

| 检查时机 | 最可能发现它的层 | 结果 |
| --- | --- | --- |
| 头部视野清楚，规划去观察位之前 | ① MoveIt 整臂碰撞（体素来自这一刻的头部快照） | MoveIt 尝试绕行,或这个候选被拒绝、换别的观察位 |
| 体素采样密度不够细（§3.6 的精度换速度）,或规划算法的检查密度有盲区（[第二册](抓水瓶教程-2-路径规划.md)第 20 节）,TCP 刚好贴着杯子边缘飞过 | ② 独立电子围栏（TCP 逐点检查） | 拒绝这个 TCP 点,把违规反馈成临时盒子（§21）,重新规划 |
| 杯子是在规划完成之后、局部接近正在执行时才被放上去的 | ③ 右腕通道点云（每次局部段执行前重新拍） | 在真正靠近前中止 |
| 杯子完全不在任意一个相机的可见范围内(比如被别的东西挡住) | 三层都可能漏掉 | **必须靠现场清场与人员急停** |

### 20.2 核心结论

**没有任何一层能声称"我解决了全部障碍"。三层叠加,是因为它们各自的盲点完全不同——一个基于规划时刻的静态快照、一个基于配置好的抽象规则、一个基于最后一刻的实时画面。任何单独一层都有"看不见"的情况,而三层同时看不见的概率远比一层小。**

**这不是说系统绝对安全**——最后一行提醒我们,视觉终究有极限,人员在场和急停始终是最后一道防线,不能被任何软件层取代。

> ✏️ **检查题 20.1**：为什么三层避障"叠加"能大幅降低漏检概率,而不是简单地"三选一,选一个最好的就够了"？
>
> **答**：因为三层各自基于完全不同的信息来源和时机（规划时的静态快照 / 抽象配置规则 / 实时画面）,它们的盲点互相独立,不重叠。"选一个最好的"意味着接受那一层固有的盲点；叠加多层意味着一个障碍必须同时躲过所有层的检测才能真正被漏掉,概率远低于任何单一层。

## 21. 违规反馈：把拒绝变成下一次规划的线索

### 21.1 一次拒绝不该被浪费

第二层（电子围栏）拒绝一个 TCP 点时,不只是简单地报错让整个规划失败重来。它会把这次违规**变成有用的信息**,反馈给下一次 MoveIt 规划请求：

```python
feedback_boxes.append(
    self.safety.replan_exclusion_box(
        exc, object_id=f"replan_{attempts:02d}", size_m=self.params.replan_exclusion_size_m,
    )
)
```

`replan_exclusion_box`（`safety.py`）：

```python
def replan_exclusion_box(self, violation, *, object_id, size_m):
    center = self.point_to_moveit(violation.point)
    return {"id": str(object_id), "center": center.tolist(), "size": [float(size_m)] * 3}
```

**把"违规发生的那个具体三维点",变成一个新的、边长 `replan_exclusion_size_m`（0.10 米）的临时立方体障碍,加进下一次 MoveIt 请求的障碍列表里。**

### 21.2 直觉：翻译成 MoveIt 能懂的语言

> **"虽然你（MoveIt）的几何碰撞模型不认为这里撞了,但我（独立围栏）的规则说这里不能走。这里给你一个 10 厘米的盒子,下一条路线务必绕开它。"**

这是一次**跨检查器的信息传递**：把"围栏语言"（禁入盒/允许区语义）翻译成"MoveIt 语言"（一个几何障碍盒）——因为 MoveIt 根本不理解"允许区"这个概念,它只理解"这里有个东西挡着"。

### 21.3 为什么 `FenceViolation` 要携带结构化数据

回顾 `safety.py::FenceViolation`：

```python
class FenceViolation(SafetyAbort):
    def __init__(self, message, *, kind, label, point, object_id=None):
        ...
        self.point = tuple(map(float, point))
```

它不只是一个错误字符串,而是携带 `point`（具体违规位置）等结构化字段。**这正是为了能被 `replan_exclusion_box` 直接使用**——如果只有一句错误文字,根本无法从中提取出"该在哪里放一个新的临时障碍盒"。

### 21.4 有限性（呼应第二册的核心思想）

这套"违规反馈"机制不是无限循环。[第二册](抓水瓶教程-2-路径规划.md)第 17 节讲过完整的理由：**规划失败不等于无解,但也不能无限重试**——本项目限定最多 8 个候选、每候选最多 2 条路线。

**为什么这里再提一次？** 因为"违规反馈"机制如果配合无限重试,看起来会很有吸引力（"每次都能学到一点,总有一天能找到路"）。但那正是最危险的想法——见第二册对"确定性失败比侥幸成功更安全"的完整论证。有限次数,是这套反馈机制能够安全使用的前提。

> ✏️ **检查题 21.1**：为什么违规反馈不是"告诉 MoveIt 别去那整片桌子",而是"告诉 MoveIt 别去那一个具体的 10 厘米小盒子"？
>
> **答**：因为围栏拒绝的是**这一次尝试里具体撞线的那个点**,不代表整个桌面禁区都需要重新告诉 MoveIt（MoveIt 本来就已经知道桌子在哪,§14 已经把它当障碍传过去了）。这个反馈针对的是"围栏语义超出 MoveIt 几何认知"的那一小块具体区域(比如 §14 讨论的采样盲区导致的边界误差),范围应该尽量精确,而不是过度保守地排除一大片本可能可用的空间。

## 23. 答案

**B1.** \(x: -0.5\le0.2\le0.5\) ✓；\(y: 0\le0.5\le1.0\) ✓；\(z: -0.3\le0.35\le0.3\)？\(0.35>0.3\) ✗。**z 不满足,点不在长方体里**（虽然 x、y 都合格,但三个条件必须同时成立）。

**B2.** \(\text{key}=(\lfloor0.12/0.05\rfloor,\ \lfloor-0.03/0.05\rfloor,\ \lfloor0.08/0.05\rfloor)=(\lfloor2.4\rfloor,\ \lfloor-0.6\rfloor,\ \lfloor1.6\rfloor)=(2,\ -1,\ 1)\)。中心 \(=((2+0.5)\times0.05,\ (-1+0.5)\times0.05,\ (1+0.5)\times0.05)=(0.125,\ -0.025,\ 0.075)\)。

**B3.** 内缩用在"里面是安全区"的盒子（总工作空间）,让判定更保守（边缘的点不再合格）；外扩用在"里面是危险区"的盒子（禁入盒）,同样让判定更保守（挨着危险区边缘的点也算危险）。方向相反是因为"安全"和"危险"的内外含义相反,但目的都是"离危险远一点"。

**B4.** 分子 \(=(0.1)(0)+(1.5)(1)+0=1.5\)。分母 \(=1^2=1\)。\(a=1.5/1=1.5\)，夹取后 \(a_{clip}=1\)（超过终点）。最近点 \(\mathbf c=(0,0,0)+1\times(0,1,0)=(0,1,0)\)。距离 \(=\lVert(0.1,0.5,0)\rVert=\sqrt{0.01+0.25}=\sqrt{0.26}\approx0.51\) 米。

**B5.** 不能。基线报告不安全,更可能说明**用来测试的姿态本身有问题**（比如姿态本身就贴着底盘,§19.3 的真实案例）,而不是检测器坏了。必须先换一个已验证安全的姿态重新测基线,基线通过之后,再去判断加障碍/撤障碍两步是否符合预期。

检查点 \((-0.70,\ 0.50,\ 0.00)\)：\(x:\ -0.70\ge-0.675\)?**不成立**（\(-0.70<-0.675\)）→ **x 不满足,整体不通过**。这个点比总工作空间的（内缩后）左边界还靠外一点点,被拒绝。

**I2.** 误差 \(=|-0.28-(-0.20)|=0.08\) 米 = 8 cm。\(8\le12\) ✓ 在容差内,允许自适应。新顶面就是实测值 \(fit.top\_m=-0.28\)（附近抬高的经验值,具体看 `fit_table_top` 里第 90 百分位再加 1cm 的实际计算,这里按定义直接取实测顶面）。

**I3.** 起点附近（\(a<0.08\)）往往是 TCP/夹爪本身的结构点,不排除会把自己判成障碍；终点附近（\(a>0.86\)）往往是目标瓶子本身及其边缘残留点,不排除会把接近目标本身误判成"挡路"。两端各留缓冲区,只在中间段严格判定,才能准确识别"真正挡在通行路上"的东西。

**I4.**
- 目标附近未删除 → 瓶子被当成障碍,规划器拒绝任何靠近它的路径,机器人永远抓不到瓶子（且容易被误诊为可达性问题）。
- 图像下方未裁剪 → 机器人自己的手臂/身体被当成世界障碍,起始姿态就"撞了",所有规划请求从一开始就失败。
- 工作范围外未过滤 → 体素数量暴增,可能超过 `scene_max_voxels` 预算导致场景直接被拒绝,或者规划严重变慢。

**I5.** 因为 MoveIt 内部的碰撞检测是按固定密度采样的（[第二册](抓水瓶教程-2-路径规划.md)第 20 节的 lvsf 参数）,两次采样之间存在盲区——一条几何上"看起来没碰"的路径,实际可能已经比垫大后的盒子边界更深入了 1~1.7 cm（2026-07-17 实测数据）。额外的 2 cm 是在为这个采样盲区留出安全余量,补偿的是"规划器认为安全"和"真实路径位置"之间的落差,不是围栏语义本身变严了。

**C1.** **不可靠,这正是 §5、§19 讨论的经典陷阱。** "从来没拒绝过"和"检测器压根没工作"表现完全一样。

验证方法：**不能只看运行日志,要主动做一次三段式验证。** 具体到电子围栏这一层,可以人为构造一个已知必然违规的 TCP 点（比如手算一个明显落在 `table_top` 禁区内的点）,直接调用 `assert_tcp_point` 看它是否正确抛出 `FenceViolation`。对于 MoveIt 层,直接跑 `moveit_collision_selftest.py`,用它的三态探针（基线/巨型障碍/撤除）确认碰撞检测机制本身健康。只有主动验证过检测器"确实会拒绝该拒绝的东西",才能信任"它从没拒绝过"这个事实代表真的安全,而不是代表检测器失灵。

**C2.** **不对,这是危险的调参方向。** 容差存在的意义就是"误差超过这个范围,说明物理布置真的变化太大了,必须走人工测量流程,不能让软件自己猜"。直接放宽容差到 20 cm,等于允许软件在物理环境已经发生较大变化的情况下继续自适应,而这种自适应的前提假设（"这只是正常波动"）已经不成立了。

正确排查顺序：
1. 先确认这次的 18 cm 差异是不是**真实的**——检查底盘这次停靠位置和平时是否有明显偏差、桌子是否真的被挪动过。
2. 检查实测本身是否可靠——查看拟合用的内点数量 `inliers`,是否远超 `table_fit_min_inliers`（60）的门槛,散布是否合理。
3. 如果确认是真实的物理变化（桌子挪了、底盘停靠点变了）,应该按照 §18.1 提示的那样,重新走 runbook 的人工测量流程,更新 `safety_profiles.json` 里的静态配置,而不是放宽容差让软件在物理环境真的变化时继续自动"跟随"。

**C3.** 完整流程：

1. **场景体素化**（第一层输入）：头部深度图反投影成基座系点云（跳步采样 stride=6）→ 删除三类不该算作障碍的区域（目标附近/图像下方自身/工作范围外）→ 6.5 cm 体素化去重 → 超过 550 个则整体拒绝而非截断。
2. **工具保护体**：随每次规划请求一起传给 MoveIt,让 MoveIt 在做整臂碰撞检查时,把夹爪占据的动态几何空间也算进去。
3. **MoveIt 整臂碰撞**（第一层）：基于以上体素、桌面盒、自身/左臂模型、工具保护体,判断候选路径是否几何碰撞。
4. **电子围栏**（第二层）：对密集插值后的每个 TCP 点,依次检查①总工作空间（内缩余量）②禁入盒（外扩余量,给 MoveIt 的盒子额外多垫 2 cm 补偿采样盲区）③允许区（不带余量,防止重叠处出现空隙）。
5. **桌面自适应**：每轮实测桌面,四条规则（容差内才调整/顶面双向跟随/水平只扩不缩/允许区同步且设双重保护底线）保证围栏跟着真实桌面走,同时绝不因为"没看见"而擅自缩小危险区。
6. **局部接近前**：圆柱通道检查（第三层）,用当前 TCP 到锁定目标的直线,配合投影比例 + 垂直距离判定,排除起点/终点缓冲区（0.08–0.86 之外不算）,累计够 18 个可疑点就中止。
7. **全程**：任何一层拒绝都可能触发违规反馈（把拒绝点变成临时障碍盒告诉 MoveIt 下次绕开）,但重试次数有限（8 候选×2 路线）,失败宁可确定性中止,不无限重试。

**C4.** **不能直接照搬,必须重新设计。**

`table_model.py` 的核心假设是"障碍是一个**单一水平平面,在目标下方**"——`fit_table_top` 专门搜索目标下方一段范围内、支持点最多的水平面。层架场景里,障碍变成了**上下左右多个方向的平面**（隔板顶、隔板底、左右侧板、后挡板）,这个假设完全不成立。

`safety_profiles.json` 里的 `shelf_template` 正是为这种场景准备的模板,它的结构提示了答案：

```json
"keepout_boxes": [
  {"id": "replace_with_shelf_bottom", ...},
  {"id": "replace_with_shelf_left_panel", ...},
  {"id": "replace_with_shelf_right_panel", ...},
  {"id": "replace_with_shelf_back", ...}
]
```

**需要的改动**：
1. 从"一个 `table_top`"变成"**多个**禁入盒"（顶/底/左/右/后每个面各一个）——静态电子围栏这部分是天然支持的（`keepout_boxes` 本来就是一个列表）。
2. **每个面**都需要类似 `fit_table_top` 的实测拟合逻辑,但每个面搜索的方向、范围、"支持点最多的平面"判定条件都要针对该面的朝向重新设计（比如左右侧板要搜索垂直平面,而不是水平面）。
3. `adapt_profile_to_table` 的"只扩不缩"逻辑需要按每个面分别推广——每个面各自"没测到就不缩",而不是套用桌面那一套。
4. 模板里 `"verified_for_execution": false`,提示这类新场景**必须先经过现场验证流程**才能真机执行,不能只凭代码写好就上真机——这和 `load_safety_profile` 里 `require_verified` 的强制检查（第一册、第二册都提到过的"配置必须先验证"的思想）是一致的。
