## 1. 关节、连杆、电机：机械臂的身体

### 1.1 三个词

机械臂由几段硬杆和连接处组成：

- **连杆（link）**：硬的杆段，本身不会动。
- **关节（joint）**：两段连杆之间的连接处，**能转动**。
- **电机（motor）**：藏在关节里，驱动关节转动的东西。

```
基座 ═══█═══█═══█═══█═══█═══█═══█── 夹爪
     J1  J2  J3  J4  J5  J6  J7
      ↑
    每个 █ 是一个关节，里面有一个电机
```

本项目右臂是 **RM75**，有 **7 个转动关节**，编号 J1（最靠近基座）到 J7（最靠近夹爪）。

### 1.2 为什么关节编号从基座数

因为**靠近基座的关节，动一点点，末端就动一大截**（杠杆越长，末端画的弧越大）；靠近末端的关节只微调姿态。这个"越靠基座影响越大"的规律，在后面讲奇异点和运动误差时很重要。

### 1.3 末端有三个不同的"点"

```
基座 ── 七个关节 ── 法兰(flange) ── 夹爪工具中心(TCP)
                                └── 右腕 RGB-D 相机
```

- **法兰（flange）**：机械臂最末端的金属连接面，用来接工具。
- **TCP（Tool Center Point，工具中心点）**：夹爪真正干活的那个点。它比法兰往前 `tcp_z_m = 0.151` 米（夹爪本身的长度）。
- **相机**：装在法兰附近，但又是另一个点。

**把这三个点搞混，是控制层最常见的错误。** 后面 §3、§14 会看到代码为此格外小心。

> ✏️ **检查题 1.1**：J1 和 J7 各转 1°，谁让末端移动得更多？
>
> **答**：J1。它离末端最远，杠杆最长，末端划过的弧最大。J7 只是在末端附近微调姿态。

## 2. 关节角与"位形"

### 2.1 关节角

每个关节转到什么角度，用一个数表示，单位**度**。七个关节角合起来写成：

\[
\mathbf q=[q_1,\ q_2,\ q_3,\ q_4,\ q_5,\ q_6,\ q_7].
\]

例如 `[0, -30, 0, 45, 0, 60, 0]`。

代码里读当前关节角就是 `robot.py::joints_deg`：

```python
def joints_deg(self) -> list[float]:
    rc, joints = self.arm.rm_get_joint_degree()
    if rc != 0:
        raise SafetyAbort(f"读取关节角失败: {rc}")
    return list(map(float, joints))
```

`rc` 是返回码（return code），**0 表示成功**，非 0 表示出错——这是本项目所有 SDK 调用的统一约定。读关节角失败也不硬扛，直接 `SafetyAbort`。

### 2.2 位形

> **位形（configuration）**：一组能唯一确定整条胳膊每一节在哪的数字。对 RM75 就是这 7 个关节角。

给我 7 个数，整条胳膊长什么样就定了——这是理解后面一切的基础。

（如果你想深入理解"位形"和"构型空间"，那是[第二册·路径规划](抓水瓶教程-2-路径规划.md)的核心内容，这里只需要记住"7 个数 = 整条胳膊的一个快照"。）

> ✏️ **检查题 2.1**：为什么 7 个关节角就能确定整条胳膊，而不需要额外的信息？
>
> **答**：因为连杆是刚性的、长度固定，关节之间的连接方式也固定。一旦每个关节转了多少确定了，每一节杆的位置和朝向就唯一确定了。

## 3. 正运动学：已知关节角，算末端在哪

### 3.1 定义

**正运动学（Forward Kinematics, FK）**：输入 7 个关节角，输出末端（法兰或 TCP）在空间中的位姿。

\[
\mathbf q\ \xrightarrow{\ \text{FK}\ }\ \mathbf T_{tcp}.
\]

### 3.2 从一根杆理解

最简单的 FK：一根长 \(l\) 的杆，固定端在原点，转了角度 \(\theta\)，末端在：

\[
(x, y) = (l\cos\theta,\ l\sin\theta).
\]

（这里用到 \(\cos\theta\) 是"转过 \(\theta\) 后的横坐标"、\(\sin\theta\) 是纵坐标——如果不熟，见[第二册](抓水瓶教程-2-路径规划.md)的三角函数一节。）

✏️ **手算**：\(l=0.3\) 米，\(\theta=60°\)：

\[
x = 0.3\times\cos60° = 0.3\times0.5 = 0.15,\qquad y = 0.3\times\sin60° = 0.3\times0.866 = 0.26.
\]

末端在 \((0.15,\ 0.26)\)。

### 3.3 七个关节只是叠七层

真实的 RM75 就是把这个过程叠七层：第一个关节的运动决定第二段杆的起点和朝向，第二个再叠上去……最后累积到末端。数学上是七个齐次矩阵连乘：

\[
\mathbf T_{tcp} = \mathbf T_1(q_1)\,\mathbf T_2(q_2)\,\cdots\,\mathbf T_7(q_7)\,\mathbf T_{tool}.
\]

**你不需要手算这个连乘**——SDK 内部算好了。你只需要知道：**FK 有唯一解，直接算，不会失败**（除非关节角本身非法）。

### 3.4 代码里的 FK

`robot.py` 有两个 FK 函数，区别只在于"算到哪个点":

```python
def tcp_from_joints(self, joints_deg):
    self._set_algo_tool_z(self.model_flange_offset_m + self.tcp_z_m)   # 算到 TCP
    tcp_pose = self.algo.rm_algo_forward_kinematics(list(map(float, joints_deg)), 1)
    ...

def controller_flange_from_joints(self, joints_deg):
    self._set_algo_tool_z(self.model_flange_offset_m)                  # 算到法兰
    pose = self.algo.rm_algo_forward_kinematics(list(map(float, joints_deg)), 1)
    ...
```

**注意那行 `_set_algo_tool_z(...)`**：它在每次 FK 前显式告诉算法"这次要算到法兰，还是要算到 TCP"。差的就是 `tcp_z_m = 0.151` 米。

**为什么要这么小心？** 因为算到法兰和算到 TCP 差 15 厘米。如果避障检查用的是法兰位置、但实际夹爪在 TCP（往前 15 cm），那么"模型显示安全，真实夹爪已经撞上去了"。§1.3 提到的三点混淆，就是在这种地方出事。

### 3.5 FK 的用途：把关节路径翻译成 TCP 路径来检查

这是 FK 在本项目最重要的用途。规划器给的是**关节路径**，但电子围栏检查的是 **TCP 位置**。所以要对路径上每个关节点做 FK，得到 TCP 点，再逐点检查：

```python
tcp_points = [self.tcp_from_joints(joints)[:3, 3] for joints in dense]
return safety_profile.assert_tcp_path(tcp_points)
```

`[:3, 3]` 是从 4×4 齐次矩阵里取出平移那一列（前 3 个数），也就是 TCP 的 \((x,y,z)\) 位置。

> ✏️ **检查题 3.1**：为什么 FK 一定有唯一解，不会失败？
>
> **答**：因为关节角完全确定了每一节杆的位置，累积到末端也就唯一确定了。这是"从原因算结果"，结果是确定的。（对比逆运动学是"从结果反推原因"，可能多解或无解——见 §4。）

### 3.6 FK 到底是谁在算：两个不同的对象

前面几节看到 FK 的调用都是 `self.algo.rm_algo_forward_kinematics(...)`。这一节讲清楚 `self.algo` 是什么，以及为什么它和真机连接是**两回事**——这是理解本项目控制层代码结构的一把钥匙。

#### 3.6.1 RobotSession 里其实有两个"机械臂"对象

`robot.py::RobotSession.__init__` 里创建了两个不同的对象：

```python
self.arm = RoboticArm(rm_thread_mode_e.RM_TRIPLE_MODE_E)
self.handle = self.arm.rm_create_robot_arm(ip, port)
...
self.algo = Algo(rm_robot_arm_model_e.RM_MODEL_RM_75_E, rm_force_type_e.RM_MODEL_RM_B_E)
```

| 对象 | 是什么 | 怎么工作 |
| --- | --- | --- |
| `self.arm`（`RoboticArm`） | **真机的网络连接** | 用 `ip, port` 连到真实控制器；读关节角、读夹爪状态、下发 `movej`/`movel`，全部要经过网络来回 |
| `self.algo`（`Algo`） | **一个独立的、纯数学的运动学计算器** | 只知道"RM75 这个型号长什么样"（构造时传入 `RM_MODEL_RM_75_E`），**不连接任何真机**，给它关节角就能算出位姿，反过来也行 |

**这是一个很容易被忽略、但极其重要的架构事实**：`plan_ik`、`tcp_from_joints`、`controller_flange_from_joints` 这些函数调用的都是 `self.algo.rm_algo_...`，**它们不经过网络，只是纯数学计算**。真正需要跟真机对话的，是 `self.arm.rm_get_joint_degree()`（读当前关节角）这类调用。

#### 3.6.2 为什么要分成两个对象

回忆第 14.3 节的"只规划会话"（`take_control=False`）：这种会话不能控制真机、不能改动控制器状态，但**仍然可以做 FK/IK 计算、仍然可以判断某条路径通不通**。

**这正是因为 `self.algo` 是独立的**：只规划会话依然创建了 `self.algo`，依然可以喂给它任意关节角、让它算 FK/IK,全程不需要真的连上、控制那台机械臂。如果 FK/IK 的计算和真机连接绑死在一起，"只算不动"这种安全的预检模式根本无法实现。

#### 3.6.3 algo 引擎需要先"知道"机器人是怎么装的

`self.algo` 只是一个装了"RM75 这个型号"的抽象计算器，但同一型号的机械臂可能被**用不同姿态安装**在不同项目里（比如正着装在桌面上，或者倒挂在龙门架上）。FK/IK 的计算结果和"重力朝哪边""基座朝哪边"密切相关,所以 `self.algo` 在真正开始计算前，必须先被告知这台机械臂的**安装角**：

```python
install = self.arm.rm_get_install_pose()          # 从真机读一次安装角
install_angles = [float(install[key]) for key in ("x", "y", "z")]
self.algo.rm_algo_set_angle(*install_angles)       # 喂给纯数学的 algo 引擎
```

**注意这两行分别用的是哪个对象**：`self.arm.rm_get_install_pose()` 是向**真机**问一次"你是怎么装的"（这一步需要网络，只在会话建立时做**一次**）；`self.algo.rm_algo_set_angle(...)` 是把这个答案喂给**纯数学引擎**，之后 `self.algo` 做的每一次 FK/IK，都会在这个安装角的前提下计算——如果漏了这一步，或者喂错了安装角，`self.algo` 算出来的位姿会系统性地偏，即便关节角本身完全正确。

#### 3.6.4 同样的模式：关节限位也要"喂"给 algo

第 12 节的关卡②检查关节限位，代码是这样读限位、再交给 algo 的：

```python
rc_min, qmin = self.arm.rm_get_joint_min_pos()      # 问真机：限位是多少
rc_max, qmax = self.arm.rm_get_joint_max_pos()
self.algo.rm_algo_set_joint_min_limit(list(qmin))    # 告诉纯数学引擎
self.algo.rm_algo_set_joint_max_limit(list(qmax))
```

**这是和安装角完全一样的模式**：`self.arm` 负责"问真机一个事实"，`self.algo` 负责"拿着这个事实去做数学计算"。`plan_ik` 每次调用都重新读一遍、重新设一遍——因为理论上限位这类配置可能变化，`self.algo` 自己不会主动去同步，必须每次显式喂给它最新值。

#### 3.6.5 一个只提一句、不深入的参数：冗余参数遍历模式

初始化时还有一行：

```python
self.algo.rm_algo_set_redundant_parameter_traversal_mode(True)
```

回忆第 12.3 节讲过的**冗余**：RM75 有 7 个关节、末端只需要 6 个自由度描述，多出的 1 个自由度意味着同一个末端位姿理论上有无穷多组关节角能实现。这一行配置的是 `self.algo` 求解 IK 时，要不要在这个"多出来的自由度"（专业叫法是**冗余参数**或**臂角**）方向上做更完整的搜索，而不是只贴着一个固定分支找解。

**诚实的说明**：这一行的具体搜索策略是 SDK 内部实现，本书没有从这个仓库源码里看到更细的展开，所以这里不编造它内部具体怎么搜索。你只需要知道：**这是初始化时的一次性配置，会影响后续每一次 IK 求解能找到的解的范围**，如果规划总是被"逆解失败"卡住,这是除了目标本身不可达之外，另一个值得确认"这一步是否被正确设置过"的地方。

> ✏️ **检查题 3.2**：如果 `self.algo.rm_algo_set_angle(...)` 这一步被漏掉了会怎样？会立刻报错吗？
>
> **答**：不一定会立刻报错——`self.algo` 仍然能接受关节角、吐出一个位姿，程序不会因为"没设安装角"这件事本身崩溃。但这个位姿是在错误的安装假设下算出来的，会**系统性地**偏离真实值，偏移方向和大小取决于真实安装角和默认假设差多少。这类错误的危险之处正是[第一册](抓水瓶教程-1-抓取点估计.md)第 9.7 节讲过的同一种模式：不报错、只是一直算错。

## 4. 逆运动学：已知想去哪，求关节怎么转

### 4.1 定义

**逆运动学（Inverse Kinematics, IK）**：输入想要的末端位姿，输出能实现它的关节角。

\[
\mathbf T_{tcp}\ \xrightarrow{\ \text{IK}\ }\ \mathbf q.
\]

**方向和 FK 正好相反。** 而且难得多。

### 4.2 为什么 IK 难：多解

回到一根杆的例子太简单，看**两根杆**够到一个点。你会发现——通常有**两种**姿势能够到同一个点：

```
   目标点 ●                    目标点 ●
        /                          \
       /  肘朝上                     \  肘朝下
      ●                              ●
     /                                \
    /                                  \
 基座                                基座

   "肘朝上"解                     "肘朝下"解
```

**同一个末端位置，两种关节角都能实现。** 这叫 IK 有**多解**。

### 4.3 7 自由度：无穷多解

RM75 有 7 个关节，但末端位姿只需要 6 个数（3 位置 + 3 朝向）来描述。7 比 6 多一个，这个多出来的自由度叫**冗余（redundancy）**。

冗余的后果：**同一个末端位姿，有无穷多种关节角能实现**。想象你的手按在桌上不动，肘部还能上下摆——手（末端）没动，但胳膊（关节角）变了。

**所以 IK 必须有规则从无穷多解里挑一个**，这就是复杂度的来源。

### 4.4 IK 可能无解

如果目标点在机械臂**够不到**的地方（太远、超出工作范围），IK 就**无解**。

代码里 IK 失败的处理（`robot.py::plan_ik`）：

```python
rc, solution = self.algo.rm_algo_inverse_kinematics(
    self.ik_params(q, list(pose), 1)
)
if rc != 0:
    raise SafetyAbort(f"路径点 {idx + 1}/{len(poses)} 逆解失败: {rc}")
```

`rc != 0` 就是无解，直接 `SafetyAbort`——**够不到就是够不到，不能硬凑。**

### 4.5 IK 需要"种子"

因为多解，IK 算法需要一个**起点提示**（seed），告诉它"从这个姿态附近找解"。本项目用**当前关节角**当种子：

```python
q = self.joints_deg()           # 当前姿态当种子
...
solution = self.algo.rm_algo_inverse_kinematics(self.ik_params(q, list(pose), 1))
```

**为什么用当前姿态当种子？** 因为我们希望找到的解**离当前姿态近**——离得近意味着动得少，动得少就安全。以当前姿态为种子，算法会优先返回附近的解。

> ✏️ **检查题 4.1**：FK 和 IK，哪个可能无解？哪个可能多解？
>
> **答**：IK 两者都可能——够不到时无解，够得到时可能多解（7 自由度甚至无穷多解）。FK 永远唯一有解。

## 5. 为什么逆运动学是"控制"的核心难点

这一节把 §4 的三个特性（多解、无解、冗余）连到本项目的具体检查上。

### 5.1 多解 → 解跳变 → 危险急动

因为 IK 多解，相邻两个路径点的解**可能落在不同的分支上**（一个"肘朝上"，下一个"肘朝下"）。

如果直接执行，机械臂就要在两点之间**猛地把肘从上翻到下**——这叫**解跳变（solution jump）**。后果是剧烈的急动，可能撞东西、可能触发保护停机。

所以 `plan_ik` 有一道**跳变检查**：

```python
if (not (allow_first_jump and idx == 0)
        and max(abs(a - b) for a, b in zip(solution, q)) > 28):
    raise SafetyAbort(f"路径点 {idx + 1} 逆解关节跳变超过 28°")
```

`max(abs(a - b) ...)` 是"相邻两解里，变化最大的那个关节变了多少度"。超过 28° 就判定为分支跳变，拒绝。

### 5.2 无解 → 目标不可达 → 拒绝

见 §4.4。够不到就 `SafetyAbort`，不硬凑。

### 5.3 冗余 → 可以绕障，但也可能进奇异

冗余是把双刃剑：

- **好处**：同一个末端位姿有多种胳膊姿态，可以选一个避开障碍的。
- **坏处**：某些姿态下机械臂会进入**奇异（singularity）**——大致就是"胳膊快伸直了"的状态，此时控制会病态。

`plan_ik` 里的这道检查就是防奇异的：

```python
if abs(solution[3]) < params.j4_singularity_deg:      # |q4| < 8°
    raise SafetyAbort(f"路径点 {idx + 1} J4={solution[3]:.1f}°，进入奇异区")
```

（奇异点是[第五册](抓水瓶教程-5-奇异点.md)的完整主题，这里只需要知道"控制层会在 IK 阶段就把进入奇异的解拦下来"。）

### 5.4 一句话总结

> **FK 是"控制"里简单的一半（算得准就行）；IK 是难的一半（多解要挑、无解要认、冗余要管）。本项目大量的安全检查，都是围绕 IK 的这三个麻烦展开的。**

> ✏️ **检查题 5.1**：为什么相邻两个路径点的 IK 解可能"跳变"，即使这两个点在空间里离得很近？
>
> **答**：因为 IK 多解。两个空间上相邻的目标，可能一个的最优解在"肘朝上"分支、另一个在"肘朝下"分支。虽然末端位置近，但关节角可以差很多——直接执行就是猛地翻肘。

## 6. 度和弧度、软限位

### 6.1 度和弧度

角度有两种单位：

- **度**：一圈 360°。本项目**关节角**用度（`joints_deg`）。
- **弧度**：一圈 \(2\pi\approx6.28\)。本项目**位姿里的姿态角**（`rx, ry, rz`）用弧度。

换算：\(\text{弧度}=\text{度}\times\frac{\pi}{180}\)，\(1\) 弧度 \(\approx57.3°\)。

⚠️ **搞混的后果是灾难性的**：把一个弧度值当度用，或反过来，会差 57 倍。所以要牢记：**关节角=度，姿态角=弧度。**

### 6.2 软限位

每个关节能转的范围是有限的（机械结构决定）。这个范围叫**限位（joint limit）**。控制器存着每个关节的最小和最大角度，可以读出来：

```python
rc_min, qmin = self.arm.rm_get_joint_min_pos()
rc_max, qmax = self.arm.rm_get_joint_max_pos()
```

### 6.3 限位余量：不要贴着边界走

本项目不允许关节角贴到限位，要留 `joint_limit_margin_deg = 3°` 的余量：

```python
if not (lo + params.joint_limit_margin_deg <= angle <= hi - params.joint_limit_margin_deg):
    raise SafetyAbort(f"路径点 {idx + 1} 关节 J{joint} 距限位过近: {angle:.1f}°")
```

✏️ **手算**：某关节限位是 \([-180°, +180°]\)，余量 3°。解算出 J1 = 178°。合法吗？

\[
-180+3 = -177 \le 178 \le 180-3 = 177\ ?
\]

\(178 > 177\) → **不合法，拒绝**。虽然 178° 还没到 180° 的硬限位，但离得太近（只剩 2°），运动中稍有偏差就会撞限位触发保护停机。

**为什么要留余量？** 因为规划的路径和真实执行总有微小误差；贴着限位走，一点误差就越界了。留 3° 是缓冲。

> ✏️ **检查题 6.1**：关节限位 \([-90°, 90°]\)，余量 3°，解算出 J5 = -88°。合法吗？
>
> **答**：\(-90+3=-87\)。要求 \(-87\le -88\)？ 不成立（−88 比 −87 小）→ **不合法，拒绝**。离下限只剩 2°。

# 第 2 部分：两种运动指令

---

## 7. movej：直接指挥关节

### 7.1 是什么

`movej` 给控制器的是**七个关节角**。意思是："每个关节转到这个角度。"

控制器内部会平滑地把七个关节从当前角度转到目标角度。**它不关心末端在空间里走什么形状的路**——末端的轨迹是七个关节运动"凑"出来的副产品。

### 7.2 直觉

想象你要把手从桌上举到头顶。用 movej 的方式思考是："肩关节转 60°，肘关节转 40°……"——你指挥的是**关节**，手的轨迹是自然结果。

### 7.3 代码

`robot.py::execute_planned_joints` 里：

```python
rc = self.arm.rm_movej(joints, speed, 0, 0, 1)
if rc != 0:
    raise SafetyAbort(f"MoveIt 轨迹点 {index}/{len(dense)} 执行失败: {rc}")
```

`joints` 是七个关节角，`speed` 是速度百分比。

### 7.4 用途

- **执行 MoveIt 的全局路径**：因为 MoveIt 给的本来就是关节路径，直接 movej 最贴合。
- **J4 弯肘逃逸**：从奇异带里逃出来（见[第五册](抓水瓶教程-5-奇异点.md)）。

> ✏️ **检查题 7.1**：movej 能保证末端走直线吗？
>
> **答**：不能。movej 指挥的是关节，末端轨迹是七个关节运动凑出来的，通常是一条弯曲的弧线。要末端走直线得用 movel（下一节）。

---

## 8. movel：指挥末端走直线

### 8.1 是什么

`movel` 给控制器的是**末端 TCP 的目标位姿**。意思是："让末端**沿直线**移动到这个位姿。"

控制器内部会实时算：为了让末端走直线，七个关节每一刻该怎么转（这需要不停做 IK）。

### 8.2 直觉

还是把手从桌上举到头顶。用 movel 的方式思考是："让我的手**径直**升到头顶。"——你指挥的是**手（末端）走的直线**，关节怎么配合是控制器的事。

### 8.3 代码

`robot.py::move_linear`：

```python
def move_linear(self, pose: Sequence[float], speed: int):
    if self.stop_event.is_set():
        raise SafetyAbort("用户停止")
    target = list(map(float, pose))
    rc = self.arm.rm_movel(target, speed, 0, 0, 1)
    if rc != 0:
        context = self._motion_failure_context(target, speed)
        if rc == -6:
            raise SafetyAbort("movel 被外部停止指令中止（API2 -6...）: " + context)
        raise SafetyAbort(f"movel 失败: rc={rc}; {context}")
```

注意它**每次运动前先检查停止事件**（`stop_event`）——用户按了停止就不动了。这个细节在 §18 展开。

### 8.4 用途

局部接近的所有动作，都要末端走可预测的直线：**预抓取接近、最后接近、抬升、下降、退开**。

### 8.5 movel 与奇异的关系（预告）

因为 movel 要求控制器实时做 IK（为了让末端走直线），它**会经过 IK 计算**。而在奇异姿态附近，IK 会病态（需要极大的关节速度）。所以"在奇异带里做 movel"是危险的——这正是[第五册](抓水瓶教程-5-奇异点.md)的核心。记住这个伏笔：**movel 经过 IK，所以怕奇异；movej 不经过 IK，所以不怕。**

> ✏️ **检查题 8.1**：为什么 movel 需要控制器不停做 IK，而 movej 不需要？
>
> **答**：movel 要求末端走直线，控制器必须实时算"为了末端在这条直线上，关节现在该是什么角度"——这就是 IK。movej 直接给了关节角目标，控制器只需插值关节，不用反推。

## 9. 为什么全局用 movej、局部用 movel

### 9.1 两段路的不同性质

| | 全局转移（当前→观察位） | 局部接近（观察位→抓取） |
| --- | --- | --- |
| 距离 | 大 | 小（约 8.5 cm + 几段） |
| 环境 | 复杂，可能要绕行 | 简单，方向明确 |
| 谁规划的 | MoveIt（给关节路径） | 直接用笛卡尔直线插值 |
| 用什么执行 | **movej** | **movel** |
| 要的是 | 绕开障碍的搜索力 | 人能预测的直线 |

### 9.2 全局为什么用 movej

MoveIt 规划出来的本来就是**关节路径**（`points_deg`，一串关节角）。用 movej 逐点执行，SDK 的每段关节运动和已检查的路径**尽可能一致**。

如果全局改用 movel，就得先把关节路径转成 TCP 路径，再让控制器重新做 IK——中间可能选到和规划时不同的关节解，实际走的路和检查过的路就对不上了。**用 movej 是为了"执行的路 = 检查过的路"。**

### 9.3 局部为什么用 movel

局部接近要的是**可预测性**。夹爪往瓶子凑的最后几厘米，必须走一条人一眼能预判的**直线**。movel 天生走直线，最合适。

（局部为什么不让 MoveIt 每段重新规划，是[第二册·路径规划](抓水瓶教程-2-路径规划.md)的话题——简言之：MoveIt 是随机的，每段可能给出形状不同的路径，人无法预判，很危险。）

> ✏️ **检查题 9.1**：为什么全局路径用 movej 能保证"执行的路和检查过的路一致"？
>
> **答**：MoveIt 规划和检查用的都是关节路径。movej 直接执行这串关节角，不重新做 IK，所以不会跑到别的关节解上去，执行轨迹紧贴已检查轨迹。

## 10. 密集插值：把一大步拆成很多小步

### 10.1 问题

MoveIt 给的关节路点可能**间隔很大**——相邻两点某个关节差 6°。如果直接一步 movej 过去，控制器内部怎么走这 6° 我们**无法检查**，中间可能撞桌子。

### 10.2 解法：插密

在两个路点之间插入中间点，让每一步都很小。`core.py::interpolate_joint_path`：

```python
count = max(1, int(np.ceil(np.max(np.abs(target - current)) / max_step_deg)))
for step in range(1, count + 1):
    alpha = step / count
    dense.append(((1 - alpha) * current + alpha * target).tolist())
```

逐行读：

- `np.abs(target - current)`：每个关节要转多少度
- `np.max(...)`：取转得**最多**的那个关节（最保守——按最坏的算段数）
- `/ max_step_deg`：除以每步上限 `planned_joint_step_deg = 1.5°`
- `np.ceil(...)`：**向上取整**（不够一整步也算一步，见下）
- `(1 - alpha) * current + alpha * target`：这是**线性插值**（在起点和终点之间按比例取值）

### 10.3 为什么向上取整

**向上取整（ceil）** 保证每步都 ≤ 上限。

✏️ **手算**：某关节要转 6°，每步上限 1.5°。

\[
\lceil 6/1.5\rceil = \lceil 4\rceil = 4\ \text{段}
\]

四段的角度：

| 段 | \(\alpha\) | 角度 |
| --- | --- | --- |
| 1 | 0.25 | \(6\times0.25=1.5°\) |
| 2 | 0.50 | \(3.0°\) |
| 3 | 0.75 | \(4.5°\) |
| 4 | 1.00 | \(6.0°\) |

每步正好 1.5°。

✏️ **再算一个不整除的**：转 7°，上限 1.5°。

\[
\lceil 7/1.5\rceil = \lceil 4.67\rceil = 5\ \text{段}
\]

每段 \(7/5 = 1.4°\)（≤1.5 ✓）。**如果向下取整成 4 段，每段 1.75° 就超标了**——这就是必须向上取整的原因。

### 10.4 两个地方都用密集插值

**检查时**（`validate_planned_joints`）：插密后对每个小点做 FK + 围栏检查。

**执行时**（`execute_planned_joints`）：

```python
def execute_planned_joints(self, points_deg, speed, max_step_deg):
    ...
    dense = self._dense_joint_path(self.joints_deg(), points_deg, max_step_deg)
    LOG.info("SDK 执行 MoveIt 轨迹: %d 个密集关节点", len(dense))
    for index, joints in enumerate(dense, 1):
        if self.stop_event.is_set():
            raise SafetyAbort("用户停止")
        rc = self.arm.rm_movej(joints, speed, 0, 0, 1)
        ...
        self.current_tcp()          # 每步后读一次 TCP，确认状态正常
```

**注意用的是同一个 `max_step_deg`（1.5°）**——执行密度和检查密度一致，保证"我检查过的每个小点，也正是我执行的每个小点"。

**还注意每步后 `self.current_tcp()`**：这不只是读位置，它内部会检查控制器有没有报错（见 §16）。每走一小步就体检一次。

> ✏️ **检查题 10.1**：某关节要转 10°，上限 1.5°，分几段？每段多少度？
>
> **答**：\(\lceil 10/1.5\rceil=\lceil 6.67\rceil=7\) 段，每段 \(10/7\approx1.43°\)（≤1.5 ✓）。

# 第 3 部分：plan_ik——运动前的四道关卡

`plan_ik` 是局部接近前的核心检查。它对一串目标位姿逐个做 IK，每个解都要过四道关卡。这是控制层最密集的安全逻辑，我们一条条看。

---

## 11. 逐点逆解

### 11.1 输入输出

`plan_ik` 输入一串**目标 TCP 位姿**（局部接近的每一小段），输出对应的**关节角序列**。但它不只是算 IK——它在算的同时**逐点检查**，任何一点不合格就整体 `SafetyAbort`。

```python
def plan_ik(self, poses, params, *, allow_first_jump=False):
    self._set_algo_tool_z(self.model_flange_offset_m + self.tcp_z_m)   # 算到 TCP
    q = self.joints_deg()                                              # 当前姿态当种子
    rc_min, qmin = self.arm.rm_get_joint_min_pos()
    rc_max, qmax = self.arm.rm_get_joint_max_pos()
    ...
    for idx, pose in enumerate(poses):
        rc, solution = self.algo.rm_algo_inverse_kinematics(self.ik_params(q, list(pose), 1))
        # ... 四道关卡 ...
        planned.append(solution)
        q = solution                    # 上一个解当下一个的种子
    return planned
```

**关键细节**：`q = solution`——上一个点的解成为下一个点的种子。这让整串解**连续**（每个都从上一个附近找），减少分支跳变。

### 11.2 起点是否在奇异带，提前记下来

在循环开始前，先记录当前姿态是否已经在奇异带里：

```python
start_in_band = abs(q[3]) < params.j4_singularity_deg
```

这个标记不影响检查本身，但用来**生成更有用的错误提示**（见 §12）——如果起点本来就在奇异带，报错时会提示"需要先做弯肘逃逸"，而不是让人瞎猜。

> ✏️ **检查题 11.1**：为什么把"上一个点的解"当"下一个点的种子"？
>
> **答**：让相邻解都从彼此附近找，保持整串解连续，避免中途从一个 IK 分支跳到另一个（§5.1 的解跳变）。

---

## 12. 四道关卡逐条拆解

对每个 IK 解，依次过四关。任何一关不过，整体 `SafetyAbort`。

### 关卡 ①：IK 有解吗

```python
if rc != 0:
    raise SafetyAbort(f"路径点 {idx + 1}/{len(poses)} 逆解失败: {rc}")
```

无解 = 够不到 = 拒绝（§4.4）。

### 关卡 ②：距限位有余量吗

```python
for joint, (angle, lo, hi) in enumerate(zip(solution, qmin, qmax), 1):
    if not (lo + params.joint_limit_margin_deg <= angle <= hi - params.joint_limit_margin_deg):
        raise SafetyAbort(f"路径点 {idx + 1} 关节 J{joint} 距限位过近: {angle:.1f}°")
```

每个关节都要离限位 ≥ 3°（§6.3）。防止贴着机械边界运行。

### 关卡 ③：进入 J4 奇异带了吗

```python
if abs(solution[3]) < params.j4_singularity_deg:      # |q4| < 8°
    hint = ("；起点姿态本身已在奇异带内，需先做关节空间弯肘逃逸"
            if start_in_band
            else "；目标可能接近手臂最大伸展，需调整目标或移动底盘")
    raise SafetyAbort(f"路径点 {idx + 1} J4={solution[3]:.1f}°，进入奇异区{hint}")
```

`solution[3]` 是 J4（第 4 关节，下标从 0 数）。\(|q_4| < 8°\) 意味着肘部快伸直了，控制会病态（详见[第五册](抓水瓶教程-5-奇异点.md)）。

**看那个 `hint`**：它用 §11.2 记的 `start_in_band` 给出**对症的建议**：

- 起点就在带里 → "需先做弯肘逃逸"
- 起点不在、是路径中途进带 → "目标太远，调整目标或移底盘"

这是很好的工程习惯：**错误信息不只说"错了"，还说"往哪个方向查"。**

### 关卡 ④：解跳变了吗

```python
if (not (allow_first_jump and idx == 0)
        and max(abs(a - b) for a, b in zip(solution, q)) > 28):
    raise SafetyAbort(f"路径点 {idx + 1} 逆解关节跳变超过 28°")
```

相邻解变化最大的关节超过 28° → 判定分支跳变（§5.1），拒绝。（`allow_first_jump` 见 §13。）

### 四关一览

| 关卡 | 检查 | 防的是 | 阈值 |
| --- | --- | --- | --- |
| ① | IK 有解 | 目标不可达 | rc≠0 |
| ② | 距限位余量 | 贴机械边界 | 3° |
| ③ | J4 奇异带 | 病态笛卡尔控制 | 8° |
| ④ | 解跳变 | 分支突跳的急动 | 28° |

> ✏️ **检查题 12.1**：J4 奇异带的报错为什么要根据 `start_in_band` 给不同提示？
>
> **答**：因为两种情况的修法完全不同。起点在带里，要用关节空间弯肘逃逸（movej）；路径中途进带，说明目标太远，要调目标或移底盘。给对提示能让排查少走弯路。

---

## 13. allow_first_jump：为什么第一步例外

### 13.1 参数

```python
def plan_ik(self, poses, params, *, allow_first_jump=False):
```

`allow_first_jump` 默认 False。为 True 时，**关卡 ④（跳变检查）对第一个点放行**：

```python
if (not (allow_first_jump and idx == 0)     # 第一个点 + 允许首跳 → 跳过检查 ④
        and max(...) > 28):
```

### 13.2 为什么需要这个例外

局部接近路径的**第一个点**，是相对**当前姿态**的。而当前姿态可能和局部路径的起始姿态差得比较多（因为刚从全局转移过来，姿态可能需要一次较大的调整才能对准抓取方向）。

如果对第一个点也严格执行 28° 跳变检查，很多合理的接近路径会被误拒——不是因为分支跳变，只是因为"第一步本来就该转得多一点"。

### 13.3 但只放第一步

**关键：只有第一个点（`idx == 0`）例外，后续每一点仍然严格。**

因为：第一步的大转动是预期的、一次性的；而**路径中途**再出现大跳变，那就真的是分支跳变了（一条平滑接近的路，中间不该突然翻肘）。

调用处（`demo.py`）能看到它总是配合局部接近使用：

```python
self.robot.plan_ik(transit_path, self.params, allow_first_jump=True)
```

### 13.4 设计思想

> **例外要尽可能窄。** `allow_first_jump` 不是"关掉跳变检查"，而是"只对那个确实需要例外的点（第一步）放行，其余一律照旧"。放宽一条规则时，把放宽的范围收到最小。

> ✏️ **检查题 13.1**：如果 `allow_first_jump` 对所有点都放行跳变检查，会有什么风险？
>
> **答**：路径中途真正的分支跳变（翻肘急动）就检测不到了。第一步的大转动是预期的，中途的大跳变是危险的——必须只放第一步。

## 14. RobotSession：为什么不直接调 SDK

### 14.1 一层包装

`demo.py` 从不直接调 `rm_movej` 或 `rm_movel`。所有运动都经过 `RobotSession`：

```
BottleDemo → RobotSession → Realman SDK → 控制器与电机
```

### 14.2 为什么加这一层

**统一所有运动都经过同样的检查和错误处理。** 如果每个地方都直接调 SDK，就会出现"这条代码路径忘了检查停止事件""那条忘了包装错误码"的漏洞。把 SDK 包在一层里，规则只写一次，谁也绕不过去。

RobotSession 统一负责：

- 每次运动前检查停止事件
- 把 SDK 的返回码翻译成带上下文的 `SafetyAbort`
- 设置正确的工具坐标系（法兰 vs TCP）
- 断开时的清理

### 14.3 只规划会话 vs 执行会话

有一个重要的开关 `take_control`：

```python
def __init__(self, ..., take_control: bool = True):
```

- `take_control=True`：**执行会话**，会真正控制机械臂（停遥操、设夹爪、可以运动）。
- `take_control=False`：**只规划会话**，只读关节角做 FK/IK，**绝不运动、绝不改控制器状态**。

大量方法开头都有这个守卫：

```python
def execute_planned_joints(self, ...):
    if not self.take_control:
        raise SafetyAbort("只规划会话禁止执行运动")
```

**为什么要区分？** 因为有些流程（比如续抓的可行性预检）只需要"算一算能不能到"，不该真的动机械臂、不该停掉现场的遥操、不该改动控制器状态。用 `take_control=False` 从代码层面**保证**这些只读操作不会误触发运动。

> ✏️ **检查题 14.1**：为什么 `current_flange` 在只规划会话里用 FK 算，而不读控制器的 TCP？
>
> **答**：读控制器 TCP 需要设置工具坐标系、可能改动控制器状态；只规划会话不能有任何副作用。用当前关节角做 FK 能算出法兰位姿，全程只读，不停遥操、不改状态。

## 15. 运动前自检（preflight）

### 15.1 为什么运动前要体检

机械臂是有惯性的重物。在它动之前，必须确认：控制器健康、每个关节都使能且无故障、没有别的安全系统在阻止、夹爪正常。**任何一项不对，宁可不动。**

### 15.2 assert_arm_healthy

`robot.py::assert_arm_healthy` 检查每个关节和控制器：

```python
def assert_arm_healthy(self) -> dict:
    rc, state = self.arm.rm_get_arm_all_state()
    if rc != 0:
        raise SafetyAbort(f"读取机械臂完整关节状态失败: rc={rc}")
    enabled = list(state.get("joint_en_flag", []))       # 每个关节使能了吗
    errors = [int(value) for value in state.get("joint_err_code", [])]   # 每个关节的错误码
    ...
    disabled = [f"J{index}" for index, value in enumerate(enabled, 1) if not value]
    faults = []
    for index, code in enumerate(errors, 1):
        if code:
            name = JOINT_ERROR_NAMES.get(code, "未知关节错误")
            faults.append(f"J{index}=0x{code:04X}({name})")
    if disabled or faults:
        raise SafetyAbort("机械臂关节级自检失败: ...")
```

- `joint_en_flag`：每个关节是否**使能**（通电、准备好动）
- `joint_err_code`：每个关节的**错误码**（0 = 正常）

`JOINT_ERROR_NAMES` 是一张错误码字典，把 `0x0002` 翻译成"过压"、`0xF000` 翻译成"通信丢帧"等，让报错能看懂。

### 15.3 完整的 preflight 清单

真机执行前会依次检查（分散在几个函数里）：

1. **右臂控制器和 7 个关节**都使能、错误码正常
2. **是否只是可恢复的瞬态通信丢帧**（见 §17）
3. **SDK 报告的当前 TCP 可读**
4. **控制器原生电子围栏是否意外仍启用**——若启用则**中止而非擅自关闭**
5. **RM Plus 夹爪**使能、无系统/自由度错误

### 15.4 第 4 条为什么"中止而非关闭"

控制器自己也有一套电子围栏。如果发现它意外还开着，代码**不会替它关掉**：

```python
def controller_fence_status(self) -> dict:
    """Read persistent controller-native fence state without changing it."""
```

注意注释：**只读，不改**。

**为什么？** 因为这个原生围栏可能是**现场另一个安全系统**留下的配置。本 demo 的 Python 围栏没有权限判断"能不能覆盖它"。擅自关掉别人设的安全措施，是极其危险的越权行为。正确做法是停下来，让人来判断。

> ✏️ **检查题 15.1**：发现控制器原生围栏还开着，为什么不直接关掉它继续跑？
>
> **答**：这个围栏可能是现场别的安全系统设的，本 demo 无权判断能否覆盖。擅自关闭别人的安全措施可能酿成事故。应该中止并让现场人员确认。

## 16. 为什么汇总状态会骗人

### 16.1 一个真实的坑

`assert_arm_healthy` 的文档字符串记录了一个惨痛教训：

> `rm_get_current_arm_state()` can report aggregate err=0 while `rm_get_arm_all_state()` still carries a live per-joint error. A real J7 0xF000 frame-loss fault produced API2 -6 for every motion command.

翻译：**"汇总状态"接口可能报告总错误 = 0，但"完整关节状态"接口里某个关节其实还带着实时错误。** 一次真实的 J7 通信丢帧故障，就是汇总状态显示正常，但每条运动指令都失败（返回 -6）。

### 16.2 为什么会这样

有两个不同的状态接口：

- `rm_get_current_arm_state()`：给一个**汇总**的错误标志。
- `rm_get_arm_all_state()`：给**每个关节**的详细状态。

汇总接口可能因为某种内部逻辑，把单关节的错误"平均"掉了，显示总体没事。但那个带错误的关节一旦要动，就会失败。

### 16.3 教训

`assert_arm_healthy` 因此坚持读**逐关节**的 `rm_get_arm_all_state`，而不是图省事看汇总：

```python
rc, state = self.arm.rm_get_arm_all_state()      # 读逐关节，不读汇总
errors = [int(value) for value in state.get("joint_err_code", [])]
for index, code in enumerate(errors, 1):
    if code:                                       # 任何一个关节有错就拒绝
        faults.append(...)
```

> **不要相信"汇总的没事"。要检查每一个单元。** 一个部件的故障可能被整体状态掩盖，但它会在最不该出问题的时候（正在运动时）暴露出来。

这个思想在别处也有回响：`current_tcp` 里也不只看主状态，还翻查嵌套的错误字段：

```python
for key in ("arm_err", "sys_err"):
    value = state.get(key, 0)
    if value not in (0, None, [0]):
        raise SafetyAbort(f"控制器报告 {key}={value}")
nested = state.get("err")
if isinstance(nested, dict):
    values = nested.get("err", [])
    if any(str(value) != "0" for value in values):
        raise SafetyAbort(f"控制器报告 err={nested}")
```

> ✏️ **检查题 16.1**：为什么 `assert_arm_healthy` 读逐关节状态而不读汇总状态？
>
> **答**：汇总状态可能显示总错误=0，却掩盖了某个关节的实时故障（真实发生过 J7 通信丢帧被汇总掩盖）。那个故障关节一旦运动就会让指令失败。必须逐关节检查才能在运动前发现。

## 17. 瞬态故障的一次性恢复

### 17.1 一个可恢复的特例

不是所有错误都必须中止。有一个**狭窄的、可恢复的**特例：

> 按住机械臂末端的绿色拖动按钮（示教用），松开后可能给某个关节留下一个**通信丢帧标志**（0xF000）。此时控制器其他方面完全健康、所有关节仍使能。只有这一个标志，是可以清掉的。

### 17.2 恢复逻辑（`recover_transient_joint_frame_loss`）

```python
affected = [index for index, code in enumerate(errors, 1) if code == 0xF000]
nonzero = [code for code in errors if code]
if (not affected                              # 没有丢帧标志
        or len(enabled) != 7
        or any(value != 1 for value in enabled)   # 有关节没使能
        or any(code != 0xF000 for code in nonzero)):  # 有别的错误
    return []                                  # 不符合特例，不处理
```

**这个条件极其严格**，只有满足全部才恢复：

- 确实有 0xF000 标志
- 7 个关节全使能
- **除了 0xF000 没有任何别的错误**

任何一条不满足，都不碰——**这不是"清错误",是"只清这一种、且只在环境干净时清"**。

### 17.3 清完必须复核两次

```python
for joint in affected:
    clear_rc = self.arm.rm_set_joint_clear_err(joint)
    if clear_rc != 0:
        raise SafetyAbort(f"清除 J{joint} 瞬态通信丢帧失败: rc={clear_rc}")

for verification in range(1, 3):        # 复核 2 次
    time.sleep(0.5)
    verify_rc, verify_state = self.arm.rm_get_arm_all_state()
    verify_errors = [...]
    if any(verify_errors):              # 清完又冒出来 → 拒绝
        raise SafetyAbort("关节通信丢帧清除后再次出现，拒绝运动: ...")
```

清完之后，隔 0.5 秒读一次、再隔 0.5 秒读一次，**连续两次都干净**才允许运动。如果清完又冒出来，说明不是瞬态、是真故障，拒绝。

### 17.4 设计思想

> **允许自动恢复的范围要极窄，且恢复后要验证。** 只对一种已知的、无害的瞬态标志、在环境完全干净时、清一次、并连续复核两次确认——这才叫"安全的自动恢复"，而不是"出错就重试"。

对比一个反面做法："检测到任何错误就清错误重试"——那会把真正的故障（过流、过温、位置超限）也一并清掉继续跑，直到硬件损坏或伤人。

> ✏️ **检查题 17.1**：为什么清除瞬态丢帧后要连续复核两次才允许运动？
>
> **答**：确认这个标志是真的瞬态（清一次就好了），而不是持续故障（清完立刻又出现）。连续两次干净才能排除"清掉又冒出来"的真故障情况。

## 18. 停住并保持，而不是自动撤退

### 18.1 停止事件

程序为 Ctrl+C 和 SIGTERM（终止信号）注册了**停止事件**。所有运动函数在每次发指令前都检查它：

```python
def move_linear(self, pose, speed):
    if self.stop_event.is_set():
        raise SafetyAbort("用户停止")
    ...

def execute_planned_joints(self, ...):
    for index, joints in enumerate(dense, 1):
        if self.stop_event.is_set():
            raise SafetyAbort("用户停止")
        rc = self.arm.rm_movej(joints, speed, 0, 0, 1)
```

**在每一小步之前检查**，意味着停止最多延迟一小步（1.5°），响应很快。

### 18.2 停下来之后做什么

无论是安全异常还是用户停止，最外层的 `finally` 都调用 `hold`：

```python
def hold(self):
    if not self.take_control:
        return
    try:
        self.arm.rm_set_arm_slow_stop()          # 慢停
    except Exception:
        pass
```

`rm_set_arm_slow_stop` 是**慢停**——平滑减速停住，然后**保持在原地不动**。

### 18.3 为什么是"保持"而不是"撤退"

这是一个重要的设计决策。出错时，为什么不让机械臂自动退回安全位置？

```
未知错误
  → 此时不能可靠相信周围空间（错误的原因可能就是环境变了）
  → 后退也是一段运动，会引入新的、未经验证的运动
  → 保持不动，由现场人员观察和处置
```

**核心逻辑**：出错意味着"我的世界模型可能已经不可信了"。在这种状态下**再做任何自动运动都是赌博**——包括后退。后退的那条路可能正好撞上导致出错的那个新障碍。

所以：**停住，保持，等人来看。** 人的眼睛此刻比机器的模型可靠。

### 18.4 停止时抓一份诊断快照

`move_linear` 失败时，在断开连接前先抓一份现场快照（`_motion_failure_context`）：

```python
context = {
    "target": ...,
    "arm_state": query("rm_get_current_arm_state"),
    "arm_all_state": query("rm_get_arm_all_state"),
    "controller_state": query("rm_get_controller_state"),
    "collision_stage": query("rm_get_collision_stage"),
    "controller_fence_enable": query("rm_get_electronic_fence_enable"),
    ...
}
```

**为什么要抓？** 因为一旦断开 SDK，这些现场信息就没了。出故障时这份快照是唯一的破案线索。

它还特别区分了 `rc == -6`：

```python
if rc == -6:
    raise SafetyAbort("movel 被外部停止指令中止（API2 -6，不是点云障碍或"
                      "Python 电子围栏拒绝）: " + context)
```

**为什么单独说明 -6？** 因为 -6 是"被外部停止指令中止"，很容易被误认为是"撞到障碍了"或"被围栏拒了"。明确标注能避免排查时找错方向——这又是"错误信息要指路"的思想。

> ✏️ **检查题 18.1**：机械臂在接近瓶子时出了未知错误。为什么不让它自动退回起点？
>
> **答**：出错说明世界模型可能已不可信（环境可能变了）。后退也是一段运动，会引入新的未验证运动，退回的路上可能正好有导致出错的那个新障碍。应该停住保持，让现场人员用眼睛判断。

## 19. 夹爪不是简单的 open/close

### 19.1 装的是什么夹爪

本机装的是 **RM Plus（ZX）两指夹爪**。⚠️ **旧的 `rm_set_gripper_*` API 控制不了它**，必须用专门的 `rm_get_rm_plus_state_info` 读状态、`rm_set_hand_*` 发指令。

用错 API 是个隐蔽的坑：调用不报错，但夹爪根本不动。

### 19.2 夹爪状态里有什么

```python
def gripper_state(self) -> dict:
    rc, state = self.arm.rm_get_rm_plus_state_info()
    if rc != 0:
        raise SafetyAbort(f"读取 RM Plus 夹爪状态失败: {rc}")
    if int(state.get("sys_state", 0)) != 0:
        raise SafetyAbort(f"RM Plus 系统状态异常: {state}")
    dof_err = state.get("dof_err", [0])
    if dof_err and int(dof_err[0]) != 0:
        raise SafetyAbort(f"RM Plus 夹爪故障: {state}")
    return state
```

关键字段：

| 字段 | 含义 |
| --- | --- |
| `pos` | 当前开口位置（数字越大越张开，0=完全闭合，900=完全张开） |
| `dof_state` | 运动状态（2=停在张开位，3=夹住了有力，5/6=保护/故障） |
| `speed` | 当前运动速度 |
| `current` | 电流（夹住东西时电流大） |
| `sys_state` / `dof_err` | 系统/自由度错误 |

`sys_state` 或 `dof_err` 非零，`gripper_state` 立刻 `SafetyAbort`——夹爪故障不含糊。

### 19.3 位置的含义

```python
gripper_open_position: int = 900        # 完全张开
gripper_close_position: int = 0         # 完全闭合（指令目标）
```

**关键洞察**：发闭合指令时目标是 0（完全并拢），但如果夹爪**夹住了瓶子**，它并不会真的到 0——瓶子挡住了，它会停在某个 `pos > 0` 的位置。**这个"停在哪"就是判断有没有抓到东西的依据**（§21）。

> ✏️ **检查题 19.1**：发闭合指令（目标 pos=0）后，夹爪停在 pos=180。说明什么？
>
> **答**：夹爪没能完全并拢到 0，被某个约 180 宽度的物体挡住了——很可能夹到了瓶子。如果停在接近 0（比如 5），说明没夹到东西，完全并拢了。

## 20. 状态机与去抖动

### 20.1 为什么发个指令还这么复杂

你可能觉得"让夹爪闭合"就是发个指令等它动完。但真实硬件有**瞬态噪声**——运动过程中会短暂上报一些看起来像故障、实际只是过渡态的读数。如果把这些瞬态当真，会误判。

`_command_gripper_position` 是一个**状态机 + 去抖动**逻辑，专门处理这个。

### 20.2 一个真实的瞬态故障

代码注释记录了这个坑（`robot.py:704`）：

> RM Plus may publish an internally inconsistent transition sample while reversing direction: the 2026-07-17 robot run reported state=6 with sys_state=0, dof_err=0 and speed=74, then aborted halfway through reopening.

翻译：**夹爪换向（比如从闭合转为张开）时，可能上报一帧自相矛盾的过渡数据**——`dof_state=6`（看起来像保护停机），但同时 `sys_state=0`、`dof_err=0`（系统没事）、`speed=74`（还在动！）。2026-07-17 那次运行就因为把这一帧当真，在重新张开的中途中止了。

**一个还在以 speed=74 运动的夹爪，显然没有真的"保护停机"。** 那一帧是噪声。

### 20.3 去抖动：连续多帧才算数

**去抖动（debounce）** 的思想：**别信单独一帧，要连续几帧一致才下结论。**

```python
if state in (5, 6):                              # 看起来像保护/故障
    settled_samples = 0
    if speed_now == 0:                           # 而且真的停住了
        stopped_fault_samples += 1
        if stopped_fault_samples >= 3:           # 连续 3 帧停住的故障
            raise SafetyAbort("RM Plus 夹爪连续 3 帧处于保护或故障且已停住")
    else:                                        # 还在动 → 是过渡噪声
        # 只警告，不中止，继续等
        moving_fault_seen = True
        stopped_fault_samples = 0
    time.sleep(0.05)
    continue
```

**关键区分**：

- `state=6` **且 speed=0**（真停住了）→ 累计，**连续 3 帧**才判真故障
- `state=6` **但 speed≠0**（还在动）→ 只是换向过渡噪声，警告并继续等

**一个真正的保护停机必须是停住的。还在动的"故障"是自相矛盾的，不能当真。**

### 20.4 判断"动作完成"也要去抖动

```python
if movement_seen and state in (2, 3) and speed_now == 0:
    settled_samples += 1
    if settled_samples >= 3:              # 连续 3 帧稳定终态
        return latest
else:
    settled_samples = 0                   # 一旦不稳定，重新计数
```

判断"到位了"也要求**连续 3 帧**都是稳定终态（state 是 2 或 3、速度为 0），中间只要有一帧不稳就重新数。

### 20.5 还有超时兜底

```python
deadline = time.monotonic() + timeout_s      # 5 秒
while time.monotonic() < deadline:
    ...
raise SafetyAbort("RM Plus 夹爪动作超时: ...")
```

万一夹爪既不完成也不明确报故障（比如卡住了），5 秒后超时中止。**永远要有超时兜底，否则可能无限等待。**

### 20.6 设计思想

> **和有噪声的硬件打交道，单帧读数不可信。用"连续 N 帧一致"来过滤瞬态，用超时防止无限等待，用"自相矛盾的读数（还在动的'停机'）不当真"来避免误判。**

>
> **答**：不该。真正的保护停机一定是停住的（speed=0），而这里还在以 speed=74 运动——这是换向时的过渡噪声，自相矛盾。应该警告并继续等待稳定终态，只有"连续 3 帧停住的故障"才中止。

## 21. 空夹基线：怎么判断"真的抓到了"

### 21.1 问题

夹爪闭合后，怎么知道**夹到瓶子了**，还是**夹了个空**？

朴素想法：闭合位置离 0 远就是抓到了。但"多远算抓到"这个门槛不好定——而且它会**漂移**。

### 21.2 一个惨痛教训

`core.py` 注释记录了 2026-07-15 的故障：

> 余量取 6：2026-07-15 实测抓稳的窄金属瓶只比空夹基线高 8，旧余量 35 把真实成功误判成空夹。

翻译：一个**很窄**的金属瓶，抓稳后闭合位置只比"空夹时的位置"高 8。当时的判定余量是 35（要求高出 35 才算抓到），结果把这次**真实的成功**误判成了"抓空"。

**根源**：写死的"空夹位置"常量会随环境和夹爪状态**漂移**。今天的空夹位置可能和上周不同。

### 21.3 解法：每轮实测空夹基线

`calibrate_empty_close` 在**每轮开始、夹爪前方无物体时**（比如在观察位），实测今天的空夹闭合位置：

```python
def calibrate_empty_close(self, params=None):
    opened = self.open_gripper(params)
    opened_pos = int(opened["pos"][0])
    state = self._command_gripper_position(params.gripper_close_position, ...)
    baseline = int(state["pos"][0])
    travel = opened_pos - baseline
    if travel < params.gripper_calibration_min_travel:      # 行程 < 100
        self.open_gripper(params)
        raise SafetyAbort("空夹基线标定异常，闭合行程不足（夹爪前方可能有物体或硬件故障）")
    self.empty_close_pos = baseline           # 记住今天的空夹位置
    self.open_gripper(params)
    return baseline
```

- 先张开，记录张开位 `opened_pos`
- 空夹闭合，记录闭合位 `baseline`
- 检查**行程** `travel = opened_pos - baseline` 是否够大（≥ 100）——如果行程太小，说明**夹爪前方有东西挡着**（本该是空的！）或硬件故障，标定本身就失败
- 把 `baseline` 存下来，作为今天的判定基准

### 21.4 抓取判定

`close_gripper` 用**本轮实测的** baseline 判断：

```python
baseline = getattr(self, "empty_close_pos", params.gripper_empty_closed_position)
minimum_object_pos = baseline + params.gripper_object_margin      # baseline + 6

if dof_state != 3:                          # 没达到夹持力
    raise SafetyAbort("夹爪未达到内部夹持力，禁止抬升")
if pos <= minimum_object_pos:               # 闭合位置≈空夹
    raise SafetyAbort("夹爪闭合位置等同空夹，判定未抓到水瓶，禁止抬升")
```

两个条件都要满足才算抓到：

1. `dof_state == 3`（真的用上夹持力了）
2. `pos > baseline + 6`（闭合位置明显比空夹高，说明有东西挡着）

✏️ **手算**：今天实测空夹 baseline = 390，余量 6。闭合后 pos = 398。抓到了吗？

\[
\text{门槛} = 390 + 6 = 396,\qquad 398 > 396\ ?\ ✓\ \textbf{判定抓到}.
\]

再算：如果闭合后 pos = 394：

\[
394 > 396\ ?\ ✗\ \textbf{判定抓空，禁止抬升}.
\]

### 21.5 为什么余量小到 6

因为要能识别**很窄的瓶子**（§21.2 的金属瓶只高出 8）。余量太大，窄瓶子会被误判成抓空。

但余量小也有风险：噪声可能让"真空夹"偶尔高出几个数。所以代码里保留了一个**动态标定失败时的静态回退值**：

```python
gripper_empty_closed_position: int = 394       # 2026-07-16 实测的静态回退
gripper_object_margin: int = 6
```

只有当本轮动态标定成功时用实测 baseline；万一没标定成功，才用这个静态值兜底。

### 21.6 三个夹爪动作的语义区别

代码里有三个闭合函数，语义不同：

| 函数 | 用途 | 会不会判"抓没抓到" |
| --- | --- | --- |
| `calibrate_empty_close` | 标定空夹基线 | 不——它就是要空夹，检查的是行程够不够 |
| `close_gripper` | 抓取瓶子 | **会**——空夹会被判成失败 |
| `close_empty_gripper` | 放下瓶子后收拢空夹爪 | 不——放完瓶子收拢，空夹是正常的 |

`close_empty_gripper` 的注释解释了为什么要单独一个：

> `close_gripper()` 是抓取动作，空夹闭合会被它有意判成抓取失败；放瓶并退开后的收纳动作语义不同，只需等待 RM Plus 返回稳定终态。

**同一个物理动作（闭合），在不同语境下语义完全不同**——抓取时空夹是失败，收纳时空夹是正常。用三个命名清晰的函数区分，比用一个函数加一堆参数开关要安全得多。

> ✏️ **检查题 21.1**：为什么每轮都要重新标定空夹基线，而不用一个固定常量？
>
> **答**：空夹闭合位置会随环境和夹爪状态漂移。用固定常量会在漂移后误判——2026-07-15 就因此把真实抓取成功误判成空夹。每轮实测能让判定基准跟着当天的真实状态走。

**B2.** J2=118°：\(120-3=117\)，\(118>117\) → **不合法**（离上限只剩 2°）。J3=-115°：\(-120+3=-117\)，\(-117\le-115\le117\) → **合法**（离下限还有 5°）。

**B3.** \(\lceil 9/1.5\rceil=\lceil 6\rceil=6\) 段，每段 \(9/6=1.5°\)。

**B4.** movej 发七个关节角，用于执行 MoveIt 全局路径和 J4 弯肘逃逸。movel 发 TCP 位姿（走直线），用于预抓取接近、最后接近、抬升、下降、退开。

**B5.** 夹爪没完全并拢到 0，被一个约 250 宽度的物体挡住了——很可能夹到了瓶子（或某个更宽的东西）。

**I1.**

| 关卡 | 检查 | 防 | 阈值 |
| --- | --- | --- | --- |
| ① | IK 是否有解 | 目标不可达 | rc≠0 |
| ② | 每个关节距限位余量 | 贴机械边界运行 | 3° |
| ③ | J4 是否进奇异带 | 病态笛卡尔控制 | \|q4\|<8° |
| ④ | 相邻解跳变 | 分支突跳急动 | >28° |

**I2.** 门槛 = 385+6 = 391。
(a) pos=397>391 且 dof_state=3 → **抓到** ✓
(b) pos=390≤391 → **判抓空**（虽然 dof_state=3，但闭合位置等同空夹，禁止抬升）
(c) dof_state=2（不是 3，没达到夹持力）→ **判抓空**（连夹持力都没有，pos=420 高只是没夹到东西完全张着，或状态本身就不对）

**I3.** 汇总状态接口（`rm_get_current_arm_state`）可能报告总错误=0，却掩盖某个关节的实时故障。真实案例：J7 通信丢帧（0xF000）时汇总显示正常，但每条运动指令都返回 -6。所以必须读逐关节的 `rm_get_arm_all_state`，检查每个关节的 `joint_err_code`，才能在运动前发现被汇总掩盖的故障。

**I4.** 在**第 5 帧**中止（连续第 3 帧 `speed=0` 的故障）。前两帧（speed=80、40）虽然 state=6，但还在运动——是换向过渡噪声，自相矛盾（真保护停机应停住），只警告不中止。第 3、4、5 帧连续 speed=0，累计到 3 帧才判真故障。

**C1.** **不对，控制器很可能有问题。** 这正是 §16 描述的经典陷阱：汇总状态会骗人。

排查：改用 `rm_get_arm_all_state()` 读**逐关节**状态，检查每个 `joint_err_code`。很可能发现某个关节（如 J7）带着 0xF000 通信丢帧标志——汇总接口把它掩盖了，但那个关节一旦要动就让指令失败（-6）。

进一步：如果确认是 0xF000 且其他一切正常，可能是按住绿色拖动按钮留下的瞬态标志，`recover_transient_joint_frame_loss` 能在严格条件下清一次并复核。如果是别的错误码（过流/过温/位置超限），那是真故障，必须现场处理，不能清了继续跑。

**C2.** 可能要调小 `gripper_object_margin`（当前 6）——如果这个瓶子比空夹基线高出的量小于余量，就会被判抓空。

**调之前必须确认**：
1. 本轮空夹基线 `empty_close_pos` 标定成功了吗？（如果标定失败用了静态回退值 394，而今天的真实空夹漂移到了别处，判定基准本身就错了。）
2. 记录这个瓶子实际的闭合 `pos` 和 baseline 的差值——像 2026-07-15 那样把数据写下来，再据此调余量。

**调错方向的后果**：如果误把余量调**大**，会有更多真实成功被判成抓空（和现在的问题相反但同源）；如果调得**过小**，噪声会让真正的空夹偶尔被判成抓到，机械臂举着空夹爪去"放瓶子"，更危险。所以要基于实测数据，而不是拍脑袋。

**C3.** 完整流程：

1. **plan_ik 四关**：对局部接近路径每个位姿逐点做 IK，检查①有解②距限位≥3°③J4 不进 8° 奇异带④相邻解跳变≤28°（第一点因 `allow_first_jump` 可例外）。任何一点不过则 `SafetyAbort`。
2. **围栏 + 通道**：逐点电子围栏检查 TCP；右腕点云通道检查夹爪正前方有无障碍。
3. **密集插值执行**：接近路径用 movel 逐段执行，每段前检查停止事件；控制器实时做 IK 让末端走直线（所以怕奇异，前面已确保不进带）。
4. **每步体检**：（全局段是 movej 逐密集点，每点后 `current_tcp()` 检查控制器错误。）
5. **夹爪标定**：接近前已在观察位用 `calibrate_empty_close` 实测本轮空夹基线，并检查张开→闭合行程 ≥100。
6. **闭合**：`close_gripper` 带力（force=30）闭合，`_command_gripper_position` 状态机连续读状态，用去抖动过滤换向瞬态（还在动的"故障"不当真），要求连续 3 帧稳定终态，5 秒超时兜底。
7. **抓取判定**：要求 `dof_state==3`（有夹持力）**且** `pos > baseline+6`（闭合位置明显高于空夹）。都满足才允许抬升，否则 `SafetyAbort`。

**C4.** 

**"空夹基线"逻辑不适用**——吸盘没有"闭合位置"这个量。吸盘的抓取判据应该是**真空度/压力传感器**：吸住东西时管路里形成负压，吸空时压力接近大气压。判据变成"负压是否达到阈值且稳定"。

**去抖动思想仍然适用**：读压力也会有瞬态噪声，同样需要"连续 N 帧稳定"才下结论、超时兜底。

**不受影响的部分**：
- **movej / movel**：这些是手臂运动，和末端执行器类型无关。
- **plan_ik 四关**：检查的是手臂关节，不涉及夹爪，完全不变。
- **停止哲学**：停住保持、不自动撤退——和末端类型无关，照旧。
- **preflight 中的手臂/控制器检查**：不变；只有夹爪那部分检查要换成吸盘的健康检查。

**这说明一个好的分层设计的价值**：末端执行器的判定逻辑被隔离在 `close_gripper` / `calibrate_empty_close` 这几个函数里，换末端只需改这几处，运动控制、安全检查、停止哲学全部复用。

1. 阶段 A 的完整手算
2. 阶段 B 的行号对照和三段解释
3. 阶段 C 的日志分析
4. **一段给安全评审员的话**（不超过 250 字），论证"从路径到抓取，没有一个动作是没检查就发生的"

### 评分标准

| 维度 | 及格 | 优秀 |
| --- | --- | --- |
| 手算 | 三题算对 | 每个判定都写出用了哪一关、哪个阈值 |
| 代码对照 | 找到行号 | 能解释去抖动为什么这样设计 |
| 日志分析 | 读出数字 | 能手动复核抓取判定，和程序对上 |
| 论证 | 说清有检查 | 能列出完整的检查链，指出每层堵什么漏洞 |

### 可选扩展

2. 找一个夹爪出现过瞬态警告但最终成功的 run，画出那几帧的 `state`/`speed`/`pos` 变化，直观看去抖动怎么救了这一次。
