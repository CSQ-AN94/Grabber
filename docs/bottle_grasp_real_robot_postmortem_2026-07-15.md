# 水瓶抓取 Demo 真机测试复盘

## 1. 结论

昨天写出的代码不是完全没有价值，但不能称为“已经写好的夹水瓶程序”。

它完成了部分基础框架：

- 单进程状态机和日志目录；
- 右臂 SDK 连接、真实 TCP 设置、关节读取；
- MoveIt 只规划、机器人 SDK 执行；
- 软件电子围栏和部分轨迹离线检查；
- 头部 RGB-D 粗定位；
- 示教关节路径的记录、压缩、加密检查和低速回放；
- 异常时停止并保持，没有自动乱退。

但用户真正要求的核心闭环没有完成验证：

- 没有从默认初始位自主规划出一条通用避障路径；
- 没有可靠完成透明水瓶的腕部三维定位；
- 没有稳定到达预抓取位；
- 没有完成最后接近；
- 没有夹紧水瓶；
- 没有抬升 \(5\ \text{cm}\)；
- 没有证明桌面、椅面或未来货架场景下的通用避障能力。

从 21:08 到 23:21，机器人端共保存了 26 次运行记录：

- 4 次只完成离线规划或示教路径检查；
- 1 次只完成观察位视觉验证；
- 21 次以安全中止或程序错误结束；
- 0 次成功抓取；
- 0 次生成 `success.json`；
- 日志中没有出现“夹紧水瓶”“抬升 5 cm”或“完成并保持”。

因此，正确评价是：

> 昨天的代码是一个包含安全框架、视觉与规划部件的实验原型，不是一个完成的水瓶抓取 Demo。今天把它直接推进到真机闭环抓取是不合格的工程判断。

## 2. 今天实际证明了什么

### 2.1 已经证明的部分

以下结果有真机日志支持：

- 示教路径可以被压缩为 139 个记录点，并加密检查为 219 个状态。
- 示教路径及其接入段曾通过 MoveIt 状态检查、软件 TCP 围栏检查。
- 右臂以 3% 速度执行过示教路径，到达腕部观察位，控制器未报错。
- 头部模型对当前水瓶的检测较稳定，多次 7 帧定位散布约为 \(2.2\) 至 \(3.2\ \text{mm}\)。
- 在观察位加入误检过滤后，腕部 7 帧定位曾达到 \(1.6\) 至 \(2.1\ \text{mm}\) 的表观散布。
- MoveIt 曾生成并执行多段局部轨迹，软件围栏检查通过。
- 所有失败都在夹紧和抬升前停止，最终控制器错误码为 0。

### 2.2 没有证明的部分

以下能力没有被今天的测试证明：

- 示教路径不是自主避障路径，只证明同一条人工路径能够被回放。
- MoveIt 的“规划成功”不等于已经建立了完整、正确的桌面障碍模型。
- 腕部点云局部建图多次为 0 个体素，因此没有证明腕部深度相机能对透明瓶周围进行可靠避障。
- 头部相机看不到完整桌面，动态点云只有约 70 至 90 个稀疏体素，不能代表完整环境。
- 当前电子围栏主要限制允许工作空间，不等同于识别和绕开桌面、椅背、货架立柱等实体。
- 腕部定位的“小散布”只表示当前启发式输出稳定，不等于三维坐标一定准确。
- 最后 \(8.5\ \text{cm}\) 接近、夹爪中心对准、夹紧力和抬升路径均未验证。

## 3. 今天遇到的问题

## 3.1 运行环境和集成问题

### MoveIt 启动和规划不稳定

日志中出现：

- `等待 MoveIt2 规划服务超时`
- 三次 `MoveIt2 规划失败: error=99999`

这说明启动顺序、服务健康检查、规划场景或目标状态在上机前没有形成稳定的集成测试。程序只能报告通用错误码，缺少足够的失败诊断。

### 坐标和数据类型错误

`20260715_221815` 出现未处理异常：

```text
ValueError: Expected angles ... got (1, 4)
```

代码把变换矩阵传给了只接受六维位姿的函数。此类接口错误应当被单元测试或计划模式覆盖，不应在真机阶段首次出现。

### 真实 TCP 设置不具备幂等性

`20260715_224735` 因 `设置真实 TCP 失败: 1` 中止。原因是 `bottleTCP` 已存在时，代码仍按首次创建处理。

后续虽然改成“存在则读取、更新并切换”，但这说明昨天版本连重复启动这一基本场景都没有验证。

### SDK 算法状态和安装角存在全局污染风险

RealMan 的算法对象涉及安装角和工具坐标状态。左右臂读取曾影响右臂算法状态，后续才将左臂关节读取隔离到子进程。

这类全局状态问题直接影响 FK、IK 和电子围栏坐标，属于上机前必须固定的基础设施。

### 相机热插拔和清理路径不完整

`20260715_231505` 中，头部相机序列号未出现在设备列表，程序正确拒绝自动换用另一台相机，但随后清理逻辑又尝试 `join` 一个从未启动的线程，产生二次异常。

这暴露出：

- 没有启动前相机健康检查；
- 没有设备重试或明确恢复流程；
- 失败清理路径未测试。

## 3.2 电子围栏和避障问题

### 初始电子围栏来自猜测，不是现场测量

程序先后出现：

- 围栏 profile 未确认，禁止执行；
- 规划轨迹落在允许区之外；
- 起始 TCP 被判断为越出总工作空间。

这些结果表明初始坐标范围和禁入区不是基于可靠的现场测量，甚至与机器人真实可行示教路径冲突。

后续删除了猜测的桌面实体禁入盒，并扩大允许区，虽然让示教路径能够执行，但也降低了环境实体约束。

### 电子围栏不等于通用避障

当前围栏主要回答“TCP 是否仍在允许工作空间”，不能回答：

- 桌面在哪里；
- 椅背在哪里；
- 货架隔板和立柱在哪里；
- 夹爪、腕部相机和前臂是否会撞到环境；
- 环境是否在运行中发生变化。

因此不能把“软件围栏通过”表述成“具有完整避障能力”。

### 动态障碍场景不完整

今天的动态场景存在两个明显缺口：

- 头部相机视野不完整，只生成少量稀疏体素；
- 腕部透明瓶场景多次产生 0 个有效体素。

程序在“腕部体素为 0”时仍继续使用头部旧场景规划。这是一个关键设计缺陷：局部传感器没有有效障碍数据时，程序应降低能力或禁止接近，而不是把“没有点”解释为“没有障碍”。

### 示教路径掩盖了自主规划问题

用户通过遥操作给出了一条可行路径。程序随后将其记录、验证并回放。

这对安全接近观察位有帮助，但它只证明：

> 当前机器人、当前桌面、当前初始姿态下，这条人工路径可以重复执行。

它没有证明：

- 从任意默认位都能自主生成路径；
- 桌面或货架变化后仍能避障；
- 目标位置变化后仍能选择观察位；
- 头部视觉和规划器能够独立完成全局接近。

示教路径应被定义为调试或恢复工具，不能作为“自主抓取 Demo 已完成”的依据。

## 3.3 透明水瓶视觉问题

### 原自定义模型不适合腕部近距离视角

自定义模型 `8_17.pt` 在头部视角检测稳定，但到达腕部近距离观察位后出现 `0/7` 检测。

后续临时引入通用 `yolo11n.pt`，它能够检测腕部水瓶，但置信度初期只有约 0.05 至 0.18，并产生多个错误框：

- 图像左下角约 \(9 \times 44\) 像素的小框；
- 中下部其他细长区域；
- 正确水瓶框约为 `(343, 256)-(425, 480)`。

这说明模型并未针对当前腕部相机、透明瓶、近距离裁切和实际背景验证。

### 透明瓶深度基本不可直接使用

腕部水瓶框内的深度主要来自瓶后背景，原有 \(0.12\) 至 \(0.65\ \text{m}\) 有效范围内经常没有可信瓶体点。

后续采用“头部纵深先验 + 腕部二维框修正”，但这是现场临时设计，没有离线数据验证。

更严重的是，程序一度在“深度函数偶尔返回数值”时改用该数值，导致同一检测框下目标从约：

```text
[0.016, 0.606, -0.030]
```

跳到：

```text
[0.019, 0.575, -0.050]
```

三帧散布达到 \(34.8\ \text{mm}\)，却因为阈值设置为 \(35\ \text{mm}\) 而被判为“稳定”。这是错误的安全门设计。

### 固定检测框几何阈值不适合接近过程

为了过滤左下角误检，现场加入了检测框最小面积、高度和长宽比规则。

随着机械臂接近，真实水瓶被图像下边缘裁切，正确框变为约：

```text
(353, 375)-(475, 479)
```

固定长宽比规则又把真实水瓶连续拒绝，最终出现 `0/7`。

这说明使用静态框形状规则处理“从完整瓶到近距离裁切瓶”的全过程是不可靠的。

### 腕部抓取点定义不清楚

程序用检测框中心附近的经验像素作为瓶身抓取点，但没有可靠估计：

- 瓶身竖直轴；
- 瓶身中部的真实高度；
- 瓶径；
- 夹爪两指相对瓶身的横向偏差；
- 瓶子被画面裁切时的完整边界。

因此，即使输出坐标多帧稳定，也不能证明夹爪会对准瓶身中部。

## 3.4 局部运动规划问题

### 抓取姿态没有形成稳定定义

早期 `candidate_path` 从“当前 TCP 姿态”生成抓取姿态。每移动一段后，当前姿态发生变化，下一轮抓取姿态也随之漂移。

`20260715_231136` 在执行四段局部轨迹后，所有候选角度均因：

```text
路径点 2 逆解关节跳变超过 28°
```

而失败。

这不是简单调大阈值可以解决的问题，而是抓取姿态和 IK 分支管理没有被正确设计。

### “分段执行”最初分的是关节轨迹点，不是笛卡尔距离

程序最初从完整 MoveIt 轨迹中只执行前 6 个加密关节点，再重新识别。

这不能保证 TCP 每段向水瓶前进 \(4\) 至 \(6\ \text{cm}\)。实际多轮运行中，关节发生较大调整，但 TCP 只移动很小距离，主要在改变姿态。

这与需求中的“每段最多移动约 \(4\) 至 \(6\ \text{cm}\)”不等价。

后续才改为先生成一个笛卡尔子目标，再让 MoveIt 完整到达该子目标，但该修改尚未完成端到端验证。

### 最后接近和夹爪闭合从未被验证

程序从未执行到：

- 最后直线接近；
- 闭合夹爪；
- 检测抓取是否成功；
- 抬升路径；
- 抬升后保持。

因此，夹爪 TCP、夹紧位置、闭合位置 `80`、夹紧速度和水瓶是否会滑落都没有实证。

## 3.5 测试和工程流程问题

### 单元测试数量不足且覆盖错误目标

本地 8 个测试可以通过，但这些测试没有覆盖：

- 真实相机帧序列；
- 透明瓶伪深度；
- 检测框被图像边缘裁切；
- YOLO 多个错误框的时间序列；
- 相机掉线后的清理；
- 已存在 TCP 的重复启动；

- 预抓取到最终抓取的连续 IK；
- 完整状态机是否能到达成功状态。

“8 个测试通过”不能支持真机完整抓取。

### 缺少离线回放数据集

- 不同距离下的框裁切测试；

- 规划请求的确定性回放。

结果是每发现一个问题，就直接改代码并再次上真机。

### 代码库和机器人端版本没有受控

当前相关目录在本地 Git 中仍是未跟踪状态：

- `bottle_grasp/`

这会造成：

- 无法准确回答某次运行对应哪一版代码；
- 无法可靠回滚；

### 失败后的人工恢复不完整

程序接管右臂时会停止遥操作进程，但退出后不会自动恢复遥操。

这样做避免了失败后机器人意外运动，但缺少明确的恢复命令和状态提示。今天多次失败后，现场状态管理不够清晰。

## 5. 为什么今天的表现会显得“乱”

根本原因不是单个模型或单个阈值，而是测试顺序错误：

1. 先写了一个覆盖面很大的完整流程；
2. 没有用录制数据离线跑通视觉；
3. 没有在固定机器人姿态下单独验证腕部定位；
4. 没有单独验证预抓取姿态和最终 IK；
5. 没有建立完整障碍模型；
6. 直接连接真机；
7. 每次失败后现场修改核心逻辑；
8. 修改后立即继续真机；
9. 版本没有冻结，测试结果彼此不可直接比较。

这相当于同时调试相机、模型、透明物体深度、标定、TCP、IK、MoveIt、电子围栏、分段控制和夹爪。任何一个环节变化都会影响其他环节。

这是今天效率低、问题不断出现、用户难以判断进展的主要原因。

## 7. 下一次真机前必须完成的整改

### 阶段 A：冻结和整理项目

- 将水瓶 Demo 放到独立、清晰的目录；
- 建立 Git 分支和基线 commit；
- 记录模型文件校验值；
- 为机器人端生成版本号；
- 禁止继续直接用临时 `scp` 覆盖未知版本；
- 保存并索引今天所有 RGB-D 和日志数据。

### 阶段 B：离线视觉回放

至少建立以下录制场景：

- 观察位完整水瓶；
- 逐渐接近、瓶体被下边缘裁切；
- 左下角和背景误检；
- 透明瓶无有效深度；
- 标签、瓶盖和瓶身不同反光状态；
- 桌面、椅背或货架背景变化。

离线验收要求：

- 正确目标连续检测率至少 95%；
- 错误框不能进入抓取目标；
- 从观察位到预抓取位，目标基座坐标跳变不超过 \(10\ \text{mm}\)；
- 目标被裁切时必须明确降级或停止，不能靠修改长宽比阈值继续猜。

### 阶段 C：固定姿态视觉验证

机器人保持不动，只验证：

- 头部坐标；
- 腕部坐标；
- 两者变换一致性；
- 多帧稳定性；
- 瓶身抓取高度定义；
- TCP 在图像中的投影。

这一阶段不控制夹爪，不执行运动。

### 阶段 D：离线运动规划验证

对录制的目标坐标和固定机器人状态验证：

- 预抓取姿态唯一且固定；
- MoveIt 规划结果到达正确 TCP；
- 全轨迹无自碰撞和环境碰撞；
- 每个笛卡尔子目标不超过 \(4\) 至 \(6\ \text{cm}\)；
- 每段终点误差可检查；
- 最后接近连续 IK 无分支跳变；
- J4 奇异区和关节限位在规划前被排除。

### 阶段 E：使用不透明、软质测试瓶

先用深度可靠且碰撞风险低的测试瓶完成：

1. 腕部观察；
2. 预抓取；
3. 最后接近；
4. 轻夹；
5. 抬升 \(2\ \text{cm}\)；
6. 再扩展到 \(5\ \text{cm}\)。

只有该阶段连续成功后，才重新测试透明水瓶。

### 阶段 F：透明水瓶正式验证

透明瓶需要专门的感知策略，不能继续依赖框中心深度：

- 使用瓶盖、标签或轮廓关键点；
- 估计瓶身轴线和抓取高度；
- 明确头部纵深先验的有效期和不确定度；
- 腕部只做横向视觉伺服时，应使用图像误差控制，而不是伪装成完整三维深度；
- 无有效局部障碍数据时禁止最后接近。

## 8. 下一版的最小可验收定义

下一版在被称为“可真机测试的水瓶抓取 Demo”之前，至少应满足：

- 固定 commit 和机器人端版本一致；
- 一条命令启动，不现场修改代码；
- 相机和模型只在单次运行中初始化一次；
- 相机缺失时干净退出，无二次异常；
- 默认初始位、观察位和抓取位均有明确状态；
- 头部和腕部目标坐标通过离线回放；

- 完成至少 5 次连续透明瓶抓取；
- 任一失败均停止保持，且可明确恢复遥操；
- 日志能够对应到唯一代码版本。

## 10. 责任判断

今天的主要问题不能归因于用户现场、透明水瓶难度或机器人硬件。

透明物体视觉和真机避障确实困难，但在已经知道这些风险的情况下，仍然把未完成离线验证的代码描述为接近可直接抓取，并在真机现场连续修改核心逻辑，是不合格的执行方式。

安全中止避免了碰撞，这是必要的底线，但不能把“没有撞到”当作 Demo 成功。

后续正确做法是暂停真机抓取，先完成版本整理、离线回放、固定姿态视觉验证和分阶段验收，再安排下一次真机测试。
