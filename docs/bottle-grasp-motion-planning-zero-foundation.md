# 水瓶抓取的运动学、规划与安全：零基础深度教材

这是一份配合本仓库水瓶 demo 阅读的深入教材。它只讲五个问题：

1. 程序怎样估计“应该夹瓶子的哪个三维点”；
2. 程序怎样从当前位置规划到该点附近；
3. 机械臂怎样把抽象路径变成真实的七个关节运动；
4. 程序怎样发现和规避桌子、障碍物与危险空间；
5. 什么是奇异点，为什么本项目特别检查 J4，以及失败时怎样处理。

假设读者没有机器人学基础，但会看一点 Python。读完的目标不是独自上真机改参数，而是能顺着代码和日志解释一次运动为何被允许、被重规划或被拒绝。

> 阅读顺序：若你还不熟悉像素、深度、相机内参和坐标变换，请先读 [项目导读的第 3 节与第 5 节](bottle-grasp-learning-note.md)。那里从每个符号的含义和具体数字例子开始；本章在此基础上继续讨论规划与运动。

> **安全前提。** 这里的所有数字，如 \(8.5\,\mathrm{cm}\)、\(3\%\) 速度、\(2.5\,\mathrm{cm}\) 余量，都是当前右臂桌面 demo 的实测/保守设置，不是普适答案。理解它们不等于可以跳过 plan、observe、人员急停与现场复核。

## 0. 总图：五个问题不是五段独立代码

抓取水瓶可抽象成以下因果链：

    RGB-D 图像
      → 稳定的瓶身三维点
      → 一个可达、可观察的腕部观察位
      → 一条避开障碍物的全局关节路径
      → 一条短而可验证的末端直线接近路径
      → 夹爪闭合与抬升

每一个箭头都可能失败。最重要的是：后一个步骤绝不“修复”前一个步骤的坏输入。

| 问题 | 主文件 | 真正输出 | 下游怎样使用 |
| --- | --- | --- | --- |
| 抓取点估计 | perception.py、demo.py 的 localize | Localization.point_base | 生成观察位和局部抓取点。 |
| 全局路径规划 | safe_planner.py、planner.py | MoveIt 的关节路径 points_deg | 把手臂从当前姿态送到观察位或 home。 |
| 局部接近 | demo.py 的 candidate_path、_approach_pregrasp | 小段 TCP 位姿序列 | 经逆解后由 SDK 逐段 movel。 |
| 机械臂控制 | robot.py | SDK 的 movej、movel、夹爪指令 | 真正引起机械臂和夹爪运动。 |
| 避障与围栏 | safety.py、scene.py、collision.py | 通过或 SafetyAbort | 是所有执行路径的门禁。 |
| 奇异点门禁 | robot.py、demo.py | 通过的逆解，或绕轴/弯肘方案 | 防止接近奇异姿态时继续笛卡尔运动。 |

先记住一句话：**视觉提供任务目标，规划提出候选动作，安全层决定候选动作是否有资格执行，SDK 才执行。**

## 1. 零基础词典：读后续章节必须认识的对象

### 1.1 位置、姿态、位姿

位置只说明一个点在哪里，例如“瓶身中部在右臂基座前方”。它有三个数：

\[
\mathbf{p} =
\begin{bmatrix}
x\\y\\z
\end{bmatrix}.
\]

姿态说明一个物体朝向哪里。例如夹爪两根手指是水平还是竖直、夹爪从哪个方向靠近瓶子。

位姿（pose）等于位置加姿态。在本项目中，SDK 常把它表示为六个数：

    [x, y, z, rx, ry, rz]

前三个单位是米；后三个是欧拉角。数学推导和坐标变换时，代码使用 \(4 \times 4\) 齐次矩阵：

\[
\mathbf{T} =
\begin{bmatrix}
\mathbf{R} & \mathbf{p}\\
\mathbf{0}^T & 1
\end{bmatrix},
\]

其中 \(\mathbf{R}\) 是 \(3 \times 3\) 旋转矩阵，\(\mathbf{p}\) 是位置。你不必手算矩阵，但要知道它能同时回答“在哪里”和“朝哪里”。

### 1.2 关节空间与笛卡尔空间

右臂有 7 个转动关节。关节空间中的一个姿态是：

\[
\mathbf{q}=[q_1,q_2,q_3,q_4,q_5,q_6,q_7]^T.
\]

例如 \(\mathbf{q}\) 的每一项可以是一个角度。笛卡尔空间则描述末端/TCP 的位姿。

两种描述像两种语言：

| 语言 | 描述什么 | 项目中何时使用 |
| --- | --- | --- |
| 关节空间 | 七个电机各转到多少度。 | MoveIt 全局轨迹、SDK 的 movej、关节限位和 J4 检查。 |
| 笛卡尔空间 | 夹爪 TCP 要到哪里、以什么方向到。 | 观察位、预抓取位、最后直线接近、抬升。 |

正运动学（forward kinematics, FK）是 \(\mathbf{q} \to \mathbf{T}_{tcp}\)：已知关节角，算末端在哪里。逆运动学（inverse kinematics, IK）是 \(\mathbf{T}_{tcp} \to \mathbf{q}\)：已知想去的末端位姿，求关节怎样转。

项目中的 RobotSession.tcp_from_joints 是 FK；RobotSession.plan_ik 和 solve_flange_ik 使用 SDK 算法做 IK。

### 1.3 法兰、TCP、相机不是同一个点

机械臂末端的机械连接面叫法兰（flange）。夹爪真正进行任务的参考点叫 TCP。右腕相机又固定在法兰附近，但不等于 TCP。

    基座 ── 七个关节 ── 法兰 ── 夹爪/TCP
                                  └── 右腕 RGB-D 相机

从法兰到 TCP、从法兰到右腕相机都是固定标定关系；从基座到法兰会随关节变化。若把它们混为一谈，最常见后果是“规划显示安全，真实夹爪却比模型更低或更前”。

本项目维护三个相关偏移：

| 名称 | 作用 |
| --- | --- |
| T_flange_wrist_camera | 把右腕相机测到的点转换到法兰，再转换到基座。 |
| T_flange_tcp | 法兰到工具中心点；当前 TCP 沿工具轴有 \(0.151\,\mathrm{m}\) 偏移。 |
| moveit_link7_to_controller_flange_m | 对齐 MoveIt 模型末端 link 与控制器法兰。 |

## 2. 抓取点估计：程序如何知道该夹哪一个点

### 2.1 “检测框中心”为什么不是抓取点

YOLO 的检测结果是一张图中的矩形框：

    左上角 (x1, y1) ──────────┐
                              │  瓶子
    右下角 (x2, y2) ──────────┘

框中心只是一张二维图上的像素。它存在三个问题：

1. 不知道离相机多远；
2. 框常包含背景，中心像素未必落在瓶子上；
3. 即使位置正确，抓在瓶盖、瓶肩、瓶底的成功率也不同。

因此，这个项目把“检测到瓶子”分成了三个层次：

    检测框
      → 可靠深度与抓取像素
      → 相机坐标系三维点
      → 基座坐标系多帧共识点

只有最后一个产物才叫抓取目标。

### 2.2 由像素和深度恢复三维点

相机内参为 \(f_x,f_y,c_x,c_y\)，某像素为 \((u,v)\)，深度为 \(z\)。针孔模型给出：

\[
x_c=\frac{(u-c_x)z}{f_x},\qquad
y_c=\frac{(v-c_y)z}{f_y},\qquad
z_c=z.
\]

举一个只用于理解的例子：假设 \(f_x=600\)，\(c_x=424\)，目标水平像素 \(u=454\)，深度 \(z=0.30\,\mathrm{m}\)。则：

\[
x_c=\frac{(454-424)\times0.30}{600}=0.015\,\mathrm{m}.
\]

这说明该点在相机光轴右侧 \(1.5\,\mathrm{cm}\)。真实代码从 CameraThread 读取内参，而不是写死这些数字。

然后用当前相机外参把点变换到右臂基座：

\[
\begin{bmatrix}\mathbf{p}_{base}\\1\end{bmatrix}
=
{}^{base}\mathbf{T}_{camera}
\begin{bmatrix}x_c\\y_c\\z_c\\1\end{bmatrix}.
\]

右腕相机随手臂动，所以当前外参是：

\[
{}^{base}\mathbf{T}_{wrist}
=
{}^{base}\mathbf{T}_{flange}(\mathbf{q})
{}^{flange}\mathbf{T}_{wrist}.
\]

这正是 demo.py 在右腕定位时提供的 transform_provider：读取当前法兰位姿，再乘固定腕相机外参。

### 2.3 为什么深度要从三个区域采样

打开 perception.py 的 _zones。它从检测框中抽取三个子区域：靠近瓶盖、标签、瓶身。随后 depth_point_for_detection 从这三个区域分别随机取深度像素。

这样做是为了抵抗以下现实情况：

| 情况 | 单点或整框中位数的风险 | 三分区采样的作用 |
| --- | --- | --- |
| 透明瓶 | 能看到前壁、后壁和背景，深度可能有多个峰。 | 多位置取样，提高找到瓶体支持簇的机会。 |
| 标签反光 | 标签区域深度可能失效。 | 瓶盖或瓶身区域仍可提供数据。 |
| YOLO 框偏大 | 框里有桌面/墙。 | 后续选择最近、被足够样本支持的深度簇。 |
| 单个飞点 | 一个深度值会完全带偏结果。 | 中位数与 MAD 对少量离群点更鲁棒。 |

注意：三个区域并不表示“取三个深度再平均”。它们只是提供候选像素池，真正的选择在 robust_near_cluster。

### 2.4 robust_near_cluster：怎样从混杂深度中挑出瓶子

将所有合法深度放入约 \(1\,\mathrm{cm}\) 宽的直方图桶后，代码只保留“有足够样本支持”的连续桶。然后从近到远找第一个支持数量足够的连续深度簇。

为什么选最近的簇？右腕相机看向瓶子时，瓶前壁通常比桌面、墙、瓶后壁更靠近相机；这里的任务是夹住最靠近相机的瓶身表面，而不是测到后方背景。

对选中的深度簇，代码计算：

\[
\operatorname{median}(z),\qquad
\operatorname{MAD}(z)=\operatorname{median}(|z-\operatorname{median}(z)|).
\]

MAD 是中位绝对偏差。它比标准差不容易被少量大误差拉高。当前参数规定 MAD 不能大于 \(18\,\mathrm{mm}\)。

**工作例子。** 假设抽样深度为：

    0.294, 0.296, 0.295, 0.297, 0.296, 0.344, 1.82

前五个值在 \(0.295\,\mathrm{m}\) 附近，后两个可能是后壁/背景。中位数是 \(0.296\,\mathrm{m}\)，前五个形成最近且支持充足的簇。程序会抛掉远离这个簇的值，而不会把 \(1.82\,\mathrm{m}\) 平均进去。

**边界例子。** 如果有效点不到 18 个、没有稳定簇，或簇内 MAD 太大，程序不会“拿上一帧凑合”，而是拒绝本帧并继续等待新的有效图像。

### 2.5 为什么抓取像素不直接取深度像素的中位数

横向 \(u\) 取可信深度点的中位数；纵向 \(v\) 却使用检测框从上到下的 0.66 比例：

\[
v=y_1+0.66(y_2-y_1).
\]

原因是：深度有效像素的纵向分布会随反光、标签和边缘裁切改变。若每一帧把“哪些深度点恰好有效”的中位数当抓取高度，夹点可能一会儿落在瓶肩、一会儿落在瓶身下部。固定比例是一个更一致的任务定义：本 demo 希望夹在瓶身偏下位置。

这不是说 0.66 对所有瓶子都正确；它只说明当前系统把“夹在哪里”作为显式参数，而不是让噪声隐式决定。

### 2.6 多帧共识：七帧为什么比一帧更可信

BottleDemo.localize 默认收集 7 帧有效三维点。设这些点是 \(\mathbf{p}_1,\dots,\mathbf{p}_7\)。程序计算它们两两间距离：

\[
d_{ij}=\lVert \mathbf{p}_i-\mathbf{p}_j\rVert_2.
\]

它找到“附近邻居最多”的点作为种子，并要求至少 \(70\%\) 的帧落在 max_position_spread_m 半径内。默认半径是 \(25\,\mathrm{mm}\)，七帧时至少要有五帧共识。最终目标是内点的坐标分量中位数。

为何不用平均值？看两个簇：

    五帧：瓶子前壁，约 0.30 m
    两帧：背景或瓶后壁，约 0.35 m

平均会把抓取点推到两者之间；中位数共识会选支持更多的前壁簇。若没有任何簇达到门槛，正确动作是 SafetyAbort，而不是生成一个“折中位置”。

### 2.7 透明瓶的特别退路

若检测框存在，但该帧深度质量不合格，且调用方提供了已有的 base 系先验点，localize 可用“先验纵深 + 本帧二维框”生成临时测量。它只是在深度失效时维持关联，并不是任意时刻都信任旧位置。

最重要的区分是：

| 场景 | 能否用先验 | 原因 |
| --- | --- | --- |
| 首次续抓定位 | 否。 | 瓶子/桌子可能已被人移动，必须独立测量。 |
| 右腕精定位时偶发透明深度失败 | 可以。 | 头部粗定位给出合理深度先验，本帧仍有二维检测。 |
| 多帧都无法形成共识 | 否。 | 说明当前视觉没有足够证据，不能把先验伪装成测量。 |

## 3. 路径规划：为什么全局转移和最后接近要分开

### 3.1 路径规划到底在求什么

设当前关节角为 \(\mathbf{q}_{start}\)，目标关节角为 \(\mathbf{q}_{goal}\)。规划器寻找一条连续路径：

\[
\mathbf{q}(s),\quad s\in[0,1],
\]

满足：

\[
\mathbf{q}(0)=\mathbf{q}_{start},\qquad
\mathbf{q}(1)=\mathbf{q}_{goal}.
\]

同时，路径上每一个姿态都必须：

1. 不超出关节限位；
2. 不与机器人自身、左臂、桌面、场景障碍物和工具保护体碰撞；
3. 对应的 TCP 位于电子围栏允许区，不进入禁入盒；
4. 不进入项目定义的 J4 奇异带。

这不是在三维直线空间中绕一个点那么简单。因为机械臂有 7 个关节，规划器是在七维关节空间中寻找可行通道。

### 3.2 为什么不能从头部检测点直接抓

头部相机适合看大范围场景，却不适合最后夹取：距离远、视角固定、分辨率有限，而且夹爪接近时不能持续看到接触区域。因此全自主流程先规划到“右腕观察位”。

观察位的定义不是某个固定关节角，而是：右腕相机能以合理距离、角度和无遮挡视野看向已经估计的瓶子。

demo.py 的 _observation_flange_candidates 对每个目标生成：

    4 个与瓶子的观察距离
    × 4 个高度偏移
    × 3 个侧向偏移
    = 48 个候选相机位姿

对于每个候选，相机光轴朝向瓶子；再利用腕相机相对法兰的固定外参，反推出对应的法兰位姿。

候选不是保证能到达的目标。_observation_plan_targets 还要逐一经过：

    候选法兰 → TCP
      → 电子围栏检查
      → 逆运动学
      → 关节限位与 J4 检查
      → 按离当前关节角的距离评分

只有全都通过的候选才交给 MoveIt。

### 3.3 MoveIt 在项目中负责什么，不负责什么

MoveIt 是全局关节路径规划器。bottle_grasp/planner.py 把规划请求写成 JSON：当前左右臂关节角、目标右臂关节角、目标法兰位姿、场景体素、桌面盒、工作空间和工具保护体。

MoveIt 负责：

- 从当前姿态到观察位/home 的大范围绕行；
- 利用机器人模型处理自碰撞和左右臂关系；
- 检查它已知的场景点云/盒子；
- 给出一串关节角路径 points_deg。

MoveIt 不负责：

- 决定哪一个 YOLO 框才是目标；
- 保证真实桌子和 JSON/点云完全一致；
- 解释电子围栏的“允许区”语义；
- 保证实际 SDK 执行时外部环境没有变化；
- 代替实时腕部点云检查最后接近通道。

所以 MoveIt 成功只是“模型内候选路线存在”，不是“可立即执行”的最终判定。

### 3.4 SafeMotionPlanner：一条路线通过的完整审批流程

打开 safe_planner.py 的 SafeMotionPlanner.plan。它把 MoveIt 作为候选生成器，再用独立检查批准或否决候选。

    1. 按评分选前 8 个观察位候选。
    2. 每个候选最多让 MoveIt 尝试 2 条路线。
    3. 规划失败：换路线或换观察位。
    4. 规划返回关节路径：先做密集关节插值。
    5. 对每个密集关节点做 FK，得到 TCP 点。
    6. 独立电子围栏逐点检查 TCP。
    7. 将密集关节路径再交给 MoveIt 做后验碰撞复核。
    8. 全部通过：返回 VerifiedPlan；否则继续有限次尝试。

这里有两个看似重复、实际不同的检查：

| 检查 | 输入 | 关心的风险 |
| --- | --- | --- |
| 电子围栏复核 | FK 算出的密集 TCP 点。 | TCP 是否离开总工作区、允许走廊，或进入桌面禁区。 |
| MoveIt 后验复核 | 同一条密集关节路径。 | 全臂/工具模型是否与点云、盒子、自身、左臂发生碰撞。 |

一个只盯 TCP，不知道整条手臂；另一个知道整个模型，但未必带有项目定义的允许区语义。二者不能互相替代。

### 3.5 为什么需要“密集插值”

假设 MoveIt 给了两个相邻关节路点 \(\mathbf{q}_a,\mathbf{q}_b\)。若只检查这两个端点，端点都安全，连线中间仍可能擦过桌面。

interpolate_joint_path 令每一轴的相邻变化不超过 \(1.5^\circ\)。若某段最大关节差为 \(6^\circ\)，它会拆成至少 4 小段。每个小段再做 FK 和围栏检查。

这是一种离散近似：它不能在数学上证明连续世界绝对安全，但比“只看粗路点”严得多；再配合 MoveIt 的后验精确碰撞复核，能显著缩小采样漏检风险。

### 3.6 违规反馈为什么能帮助重规划

若电子围栏发现某个 TCP 点进入 table_top，SafeMotionPlanner 不立即把所有规划机会耗尽。它把该违例点附近构造成一个临时 \(0.10\,\mathrm{m}\) 左右的碰撞盒，反馈给下一次 MoveIt 请求。

直觉上，这告诉规划器：“虽然你的几何碰撞模型没有认为这里撞了，但独立规则说这里不能再走；下一条路线绕开这一小块区域。”

这不是无限搜索：最多 8 个端点、每端点最多 2 条路线。有限次数很重要，因为“不断重试直到偶然找到可走路径”会掩盖现场模型错误。

### 3.7 局部接近为什么不用每段都重新让 MoveIt 规划

从观察位到预抓取位、再到抓取点，是短距离、方向明确的动作。项目不再让 MoveIt 对每 \(4.5\,\mathrm{cm}\) 小段反复全局重规划；那会造成“走一点、重算、再走一点”的蠕动动作，且每次都可能选择不易解释的路径。

局部策略是：

1. 以固定抓取姿态建立预抓取点和抓取点；
2. 用直线插值生成短小位姿序列；
3. 逐点检查电子围栏；
4. 对整段做连续逆解、限位、跳变和奇异检查；
5. 用右腕深度图检查夹爪前进走廊；
6. 每一执行段验证相机存活与锁定目标关联。

因此它不是“更简单所以更不安全”，而是把路径形状限制为人容易预测的一条直线，并用更贴近任务的感知检查保护它。

## 4. 机械臂控制：路径怎样变成真实运动

### 4.1 RobotSession 是什么

robot.py 的 RobotSession 是对 Realman SDK 的安全包装。demo.py 不直接调用 rm_movej 或 rm_movel，而是调用 RobotSession，以便每次执行都遵循统一的状态检查、错误包装、停止行为和工具坐标设置。

可以把调用层次看成：

    BottleDemo
      → RobotSession
        → Realman SDK
          → 控制器与电机

这条封装边界使得“规划逻辑”不需要知道 SDK 的返回码细节，也避免不同代码路径绕过安全检查。

### 4.2 movej 与 movel 的区别

| 指令 | 给控制器的目标 | 本项目的典型用途 | 直觉 |
| --- | --- | --- | --- |
| movej | 七个关节角。 | 执行 MoveIt 全局路径；J4 弯肘逃逸。 | 让每个关节去指定角度。 |
| movel | TCP 位姿。 | 预抓取接近、最后接近、抬升、下降、退开。 | 让末端沿笛卡尔直线靠近目标。 |

MoveIt 给出的全局路径本来就是关节路径，所以 execute_planned_joints 会先插密，再逐个调用 movej。这样 SDK 的每段关节运动与已检查路径尽量接近。

局部段先在笛卡尔空间确定“希望末端怎样直线移动”，由 plan_ik 逐段检查所有位姿是否有可行关节解，之后才调用 movel。

### 4.3 一次运动前检查什么

真机 execute 模式在 _preflight 中先检查：

1. 右臂控制器和全部关节是否已使能、错误码是否正常；
2. 是否仅出现允许恢复的瞬态通信丢帧，且复读后已恢复；
3. SDK 报告的当前 TCP 是否可读；
4. 控制器原生电子围栏是否意外仍启用；
5. RM Plus 夹爪是否使能且无系统/自由度错误。

控制器原生围栏若仍启用，程序会中止而不是擅自关闭。原因是它可能是现场另一个安全系统留下的配置；本 demo 的 Python 围栏不能代表有权覆盖它。

### 4.4 执行中如何停止

scripts/bottle_grasp_demo.py 为 Ctrl+C 和 SIGTERM 注册停止事件。RobotSession.move_linear 和 execute_planned_joints 每次发送动作前都检查该事件。

无论安全异常还是用户停止，外层 finally 最终调用 RobotSession.hold，它尝试对控制器下发慢停。设计选择是“停止并保持”，而非自动撤退：

    未知错误
      → 此时不能可靠相信周围空间
      → 后退也会引入新的未验证运动
      → 保持、由现场人员观察和处置

### 4.5 夹爪控制不只是 open/close

本机安装的是 RM Plus 夹爪，robot.py 专门读取 RM Plus 状态，而不使用旧夹爪 API。

每轮抓取的夹爪流程为：

    观察位自由空间
      → 打开位置、闭合位置与行程检查
      → 空夹闭合，记录动态基线
      → 再打开
      → 接近水瓶
      → 带力闭合
      → 连续读取位置/速度/状态
      → 与本轮空夹基线比较，判定是否抓到实物

若夹爪被物体挡住，它无法闭合到空夹位置，闭合位置会与空夹基线有足够差异。若差异小于 gripper_object_margin（当前为 6），系统认为抓空或物体过窄而中止后续假设。

## 5. 避障：本项目有三类障碍检查

“避障”不是一个函数，而是三个不同尺度的问题。

### 5.1 第一层：MoveIt 的整臂碰撞

MoveIt 看到的是：

- 右臂和左臂的模型；
- 机器人自碰撞规则；
- 头部 RGB-D 转换出的场景体素；
- safety profile 里的桌面等盒子；
- 为工具额外加的保护体积。

scene.py 的 build_scene_voxels 做了几件关键事：

1. 将深度图按稀疏网格反投影为 base 系点云；
2. 移除水瓶检测框附近的点，以免把目标瓶本身当成“不可接近障碍”；
3. 移除图像下方容易看到机器人自身的区域，以免把自己投回世界障碍；
4. 只保留瓶子附近一定工作范围内的点；
5. 以 \(6.5\,\mathrm{cm}\) 体素去重，并最多保留 550 个相关体素。

体素不是精细网格，而是“这个小立方体里存在障碍”的近似。它牺牲部分几何精度，换取规划能在有限时间内完成。

### 5.2 第二层：电子围栏

SafetyProfile.assert_tcp_point 对每个 TCP 点按以下顺序判断：

    点必须在总工作空间内
      → 不能进入任何扩张后的禁入盒
      → 必须至少落在一个允许区

它们的语义不同：

| 元素 | 例子 | 作用 |
| --- | --- | --- |
| 总工作空间 | 右臂可被允许使用的最大长方体。 | 防止远离已验证操作区域。 |
| 禁入盒 | table_top。 | 明确禁止 TCP 穿进的区域。 |
| 允许区 | 桌面上方任务体积、已示教的通行包络。 | 即使不撞桌子，也不让 TCP 飞到未经验证的地方。 |

禁入盒检查使用 clearance_m 扩张，即使 TCP 没有穿入原始桌面几何，离它过近也会被拒绝。allowed zones 则不分别缩小，以免相邻允许走廊之间被人为切出空隙。

**很重要的限制。** 电子围栏只检查 TCP 点；它不知道手臂每一节在哪里。这正是它必须与 MoveIt 整臂碰撞检查并用的原因。

### 5.3 第三层：右腕点云的“最后接近通道”

全局 MoveIt 点云来自头部相机，最后接近时最关心的是夹爪前方当前是否突然有障碍。collision.py 的 check_approach_corridor 从右腕深度图构造点云，删掉水瓶检测框附近的像素，避免把目标本身算作障碍。

设 TCP 当前点为 \(\mathbf{s}\)，锁定水瓶目标为 \(\mathbf{t}\)，任意点云点为 \(\mathbf{p}\)。程序计算点在线段方向上的投影比例：

\[
a=\operatorname{clip}\left(
\frac{(\mathbf{p}-\mathbf{s})^T(\mathbf{t}-\mathbf{s})}
\lVert\mathbf{t}-\mathbf{s}\rVert^2},0,1
\right).
\]

线段上与 \(\mathbf{p}\) 最近的点是：

\[
\mathbf{c}=\mathbf{s}+a(\mathbf{t}-\mathbf{s}).
\]

若 \(\lVert\mathbf{p}-\mathbf{c}\rVert\) 小于 corridor_radius_m（当前 \(4.5\,\mathrm{cm}\)），而且投影不在起点/终点附近，就把它当成走廊中的可疑点。可疑点达到 obstacle_min_points（当前 18）时，程序中止。

这是一个圆柱形“通行管道”检查。它解决的问题不是全臂碰撞，而是“夹爪直线冲向瓶子时，瓶子前方有没有额外物体”。

### 5.4 桌面为什么还要每轮拟合

table_model.py 会从头部点云中，在水瓶下方一定距离范围寻找支持最多的水平平面。它不是无条件改围栏：

1. 找不到足够点支持的桌面平面，直接中止；
2. 实测桌面高度与 profile 差超过 \(12\,\mathrm{cm}\)，直接中止；
3. 在容忍范围内，禁入盒顶面才跟随实测桌面；
4. 水平范围只允许扩张，不允许因为相机没看见而缩小。

最后一条很保守。相机看不到桌子边缘不表示桌子不存在；缩小禁入盒会把“没测量”误当成“安全空间”。

### 5.5 三层怎样协同：一个障碍物案例

假设桌面边上多了一个未建模杯子。

| 检查时机 | 最可能发现它的层 | 结果 |
| --- | --- | --- |
| 头部视野清楚，去观察位前 | MoveIt 体素碰撞。 | MoveIt 尝试绕行或换观察位。 |
| 路线模型采样太粗，TCP 靠桌边 | 独立电子围栏。 | 拒绝 TCP 点，并把违例反馈成临时盒重规划。 |
| 杯子刚被放到夹爪前方 | 腕部通道点云。 | 在最后接近前中止。 |
| 杯子完全不在任意相机可见范围 | 三层都可能漏掉。 | 必须靠现场清场与人员急停。 |

没有一层能声称“我解决了全部障碍”。把它们叠加，是因为各自的盲点不同。

## 6. 奇异点：为什么关节 J4 接近零会被拒绝

### 6.1 先用直觉理解奇异点

机械臂末端的小变化可以近似写成：

\[
\dot{\mathbf{x}}=\mathbf{J}(\mathbf{q})\dot{\mathbf{q}},
\]

其中 \(\dot{\mathbf{x}}\) 是 TCP 的速度，\(\dot{\mathbf{q}}\) 是关节速度，\(\mathbf{J}\) 是雅可比矩阵。

奇异点（singularity）发生在某些姿态下，\(\mathbf{J}\) 丢失了方向能力：要得到一个很普通的末端小速度，可能需要极大的关节速度；某些末端方向甚至无法由小关节变化实现。

可以把它想成把手臂拉得几乎完全直：此时想让手腕沿某些方向平滑移动，肘部必须突然决定向哪边弯。数学解可能存在，实际控制却容易剧烈跳变。

### 6.2 本项目的工程性奇异判定

项目不试图对完整 7 自由度雅可比做通用条件数分析，而是采用已验证的工程门禁：若 IK 解的第 4 关节满足

\[
|q_4| < 8^\circ,
\]

就称它进入 J4 奇异带并拒绝。

这不是“宇宙中所有 J4=0 都必然不可动”的数学定理，而是此 Realman 机构、当前任务和当前控制方法下的安全工作区约束。它简单、可解释，并直接进入 RobotSession.plan_ik 的每个路径点检查。

同时，任何关节离 SDK 报告的软限位不足 \(3^\circ\) 也会被拒绝；相邻逆解之间若出现超过 \(28^\circ\) 的跳变，也会被拒绝。这三类检查分别防止：

| 门禁 | 防的是什么 |
| --- | --- |
| J4 奇异带 | 接近伸直肘部时的病态笛卡尔控制。 |
| 关节限位余量 | 贴着机械/软件边界运行。 |
| 连续解跳变 | IK 从一个分支突然跳到另一支。 |

### 6.3 两种“奇异问题”必须分开

这是理解源码最关键的一点。

| 情况 | 发生在哪里 | 代码的正确处理 |
| --- | --- | --- |
| 目标/路径点会落入 J4 带。 | 计划一个新局部位姿时。 | 尝试绕工具接近轴转小角度，重新做 IK。 |
| 机器人当前起点已经在 J4 带。 | 要开始抬升、下降、退开等局部笛卡尔动作前。 | 先用关节空间仅弯 J4 逃逸，再从新 TCP 重建路径。 |

为什么不能把两种都用“旋转夹爪”解决？绕工具自身 z 轴的 roll 会改变末端朝向和 IK 分支，但不会改变腕心到肩部的几何距离。若当前肘部本来已经几乎伸直，保持 TCP 位姿的 roll 无法把 \(q_4\) 从接近零变成安全角度。

### 6.4 方法一：绕接近轴的小角度重试

_plan_ik_avoiding_singularity 对局部路径尝试：

    0°, +8°, -8°, +15°, -15°, +25°, -25°

对每个路径位姿，代码右乘绕工具 z 轴的旋转，再做完整 plan_ik。只有这条实际旋转后的路径通过逆解、限位、J4 和跳变检查，才会被返回并执行。

candidate_path 在建立抓取/预抓取姿态时也尝试 \(0^\circ,\pm15^\circ,\pm30^\circ\)。这些角度不是为了让瓶子位置改变，而是让夹爪在不改变接近位置的情况下换一个可行的姿态/逆解分支。

**何时有效？** 原姿态接近关节限位、某个姿态分支不连续，或略改手腕方向就能让 IK 解离开危险带时。

**何时无效？** 目标位置太远、手臂近乎完全伸直，导致无论夹爪怎样绕自身轴转，肘部几何仍在奇异带。

### 6.5 方法二：当前就在奇异带时的 J4 弯肘逃逸

RobotSession.escape_j4_singularity 只在当前 \(|q_4|<8^\circ\) 时运行。它尝试将 J4 关节角移动到 \(+14^\circ\) 或 \(-14^\circ\)：

1. 先检查目标 J4 仍留有关节限位余量；
2. 将从当前角到目标角的关节路径按 \(1.5^\circ\) 插密；
3. 对每一个插值关节姿态做 FK，得到 TCP；
4. 对每个 TCP 做电子围栏检查；
5. 只在全部通过时用 movej 执行这段关节逃逸；
6. 从逃逸后的真实 TCP 重新构建抬升/下降/退开路径。

为什么逃逸后必须重建路径？因为改变 J4 会让 TCP 实际位置发生变化。若仍执行逃逸前算好的“向上抬 5 cm”位姿序列，就等于从错误起点执行路径。

这也解释了 _plan_local_leg 为什么接收 build_path 回调，而不是直接接收已算好的路径：它先处理可能的 J4 逃逸，再让回调根据新的当前姿态生成正确路径。

### 6.6 奇异失败的实际诊断顺序

看到“路径点 N J4=X°，进入奇异区”时，不要先把阈值从 \(8^\circ\) 改小。按以下顺序判断：

1. 当前观察位是否太远、太低或太接近手臂最大伸展；
2. 目标瓶子是否移动，或手眼标定是否让目标误落到远处；
3. 绕接近轴的候选是否已全部尝试；
4. 若是放回/抬升/退开，起点是否已在带内，是否需要让程序执行弯肘逃逸；
5. 是否应调整底盘位置或重新选择观察位，而不是强迫手臂穿过带。

把阈值调小只是在允许更接近病态区域运行；它不是修复“几何不可达”的办法。

## 7. 把五部分连成一次可审计的 grasp

下面用“从 observe 成功升级到 grasp”的典型运行，按证据链逐步追踪。

### 阶段 A：确认任务目标

头部 RGB-D 产生检测框。perception.py 从三个区域采样深度、找最近稳定簇、将点变换到右臂基座。localize 收集 7 帧并得到 head_target。

此时日志的关键证据是：

    头部粗定位稳定
    共识帧 7/7
    散布 N mm

若没有稳定共识，不能讨论规划，因为后续每一步都依赖这个目标位置。

### 阶段 B：让右腕相机到可观察位置

系统围绕 head_target 生成 48 个候选观察位。每个候选先过围栏和 IK，再按关节变化评分排序。SafeMotionPlanner 让 MoveIt 计划，随后用密集 TCP 围栏和 MoveIt 后验碰撞复核审批。

此时“安全轨迹确定”的日志说明的是：某个观察位端点与路径在当前建模场景中通过了多层检查；它还不表示已经抓到瓶子。

### 阶段 C：右腕重新测量并锁定

执行密集 movej 到观察位。右腕相机再做 7 帧定位，得到 wrist_target。现在后续局部抓取使用 wrist_target.point_base，而非 head_target，因为右腕观测更贴近夹爪。

目标一旦锁定，运动中的视觉不再重新定义抓取点。它只检查“我看见的是否仍是这个锁定点对应的瓶子”。

### 阶段 D：可预测地靠近

程序以当前 TCP 姿态为基准，建立预抓取点。它检查：

    TCP 到目标距离是否单调收敛
    预抓取终点是否约为 8.5 cm 悬停
    逐点电子围栏
    连续 IK、限位、关节跳变、J4 奇异带
    右腕点云通道
    每段图像存活与锁定目标关联

这就是为什么日志中出现“直线接近预抓取位”前，已经经过了多道检查。

### 阶段 E：夹住并验证

预抓取复检只确认目标仍合理存在；近距离观测可能受遮挡，所以不重写锁定坐标。最后接近低速执行；夹爪闭合后与本轮空夹基线比较；成功才计划抬升 \(5\,\mathrm{cm}\)。

若任一阶段失败，程序保存图像、深度、规划 JSON、run.log 和 run_summary.json，然后保持而不是自动乱动。

## 8. 你应该能回答的检查题

1. 为什么“YOLO 检测到瓶子”不足以开始 movel？
2. 为什么全局 MoveIt 规划和最后笛卡尔直线接近使用不同策略？
3. 为什么电子围栏与 MoveIt 碰撞检查两者都需要？
4. 当腕部检测丢失时，为什么有时使用头部确认，有时只记录警告？
5. 为什么起点卡在 J4 奇异带时要先用 movej 弯肘，而不是仅旋转夹爪？

### 答案要点

1. 还缺可靠深度、基座系变换、多帧稳定性、可达性、碰撞和围栏检查。
2. 大范围转移需要绕开复杂环境，适合 MoveIt 的关节空间搜索；最后几厘米需要人可预测的直线，适合严格局部检查和实时右腕通道守卫。
3. MoveIt 检查整臂模型碰撞，但不表达项目的允许区语义；电子围栏检查 TCP 任务空间边界，但不知道整条手臂形状。
4. 预抓取转移中检测丢失不是预期遮挡，需要独立确认；最后几厘米夹爪遮挡检测框是可预期的，但相机流中断仍必须中止。
5. 纯 roll 不改变近乎伸直的肘部几何；J4 弯肘逃逸直接把关节带离带区，并逐点验证逃逸路径。

## 9. 建议的实践项目：只读复盘一条规划

不要先上真机改参数。找一个已有的 outputs/bottle_grasp 运行目录，完成以下只读练习：

1. 打开某个右腕定位 JSON，画出从 Detection.box 到 point_base 的数据路径。
2. 打开对应的 MoveIt request JSON，找出 start_joints_deg、goal_joints_deg、obstacles、boxes、tool_guard。
3. 打开 plan JSON 和 validation JSON，记录规划粗点数与后验复核状态数。
4. 对照 run.log，标出“安全规划尝试”“安全轨迹确定”“右腕点云通道检查”“低速最后接近”各自发生在何处。
5. 写出一句判断：这条日志是否证明可以再次 execute？你的答案必须同时列出日志能证明什么、不能证明什么。

合格标准是：能把一条路径解释为“视觉测量 + 候选规划 + 双重轨迹复核 + 局部实时守卫”的产物，而不是把它叫作“MoveIt 自动生成的动作”。

## 10. 继续读代码的最短路线

若你想把上述概念逐行落回代码，按这个顺序读：

    perception.py
      → core.py 的 Localization 与插值函数
      → demo.py 的 localize
      → safety.py
      → safe_planner.py
      → demo.py 的 candidate_path 与 _approach_pregrasp
      → robot.py 的 plan_ik、escape_j4_singularity、move_linear、execute_planned_joints
      → collision.py

每读一个函数，都问同一个问题：它接收的坐标是哪个坐标系？它输出的是测量、候选、批准动作，还是实际执行？它失败后会继续、换候选，还是安全中止？

能稳定回答这三个问题，就能真正读懂本项目最关键的五个部分。
