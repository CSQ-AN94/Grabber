## 3. 从零开始的视觉与坐标系基础

这一节只解决一个问题：相机画面中的“水瓶”，如何变成机械臂能使用的一个三维位置。先不要急着看公式；先把每一个名词和符号说清楚。

### 3.1 先看一张图：什么是像素、什么是检测框

把相机画面想成一张由很多极小方格组成的纸。每个小方格叫一个像素（pixel）。程序用两个整数给它编号：

    左上角是 (0, 0)
    向右移动，第一项变大
    向下移动，第二项变大
    
    (0, 0) ───────────────→ 向右，编号变大
       │
       │      ┌────────┐
       │      │  水瓶  │
       │      └────────┘
       ↓
    向下，编号变大

YOLO 不会直接告诉程序“夹这里”。它只画出一个检测框（bounding box），并说“这个框里的物体像水瓶”：

    (x1, y1)  = 检测框左上角像素
    (x2, y2)  = 检测框右下角像素
    confidence = YOLO 认为它是水瓶的把握，范围通常为 0 到 1

例如，若 YOLO 返回：

    box = (400, 120, 520, 380)
    confidence = 0.95

意思是：在图像横向第 400 到 520 个像素、纵向第 120 到 380 个像素围成的矩形里，模型认为有一个水瓶，信心约为 95%。它**不**表示瓶子在真实空间中距机械臂多远，也不表示夹爪应该夹住框的中心。

### 3.2 RGB-D 相机比普通相机多了什么

普通 RGB 相机对每个像素只给出颜色，例如红、绿、蓝三种强度。RGB-D 相机额外给出该像素的深度（depth）：从相机镜头到该处物体的距离。

可以把它理解为两张对齐的图：

| 图像 | 每个像素记录什么 | 本项目用来做什么 |
| --- | --- | --- |
| 彩色图（RGB） | “这里看起来是什么颜色/形状”。 | YOLO 找水瓶框。 |
| 深度图（D） | “这里离相机多远”，单位是米。 | 把水瓶从二维画面还原为三维位置。 |

例如，同样在彩色图中占 100 像素高的瓶子，可能是近处的小瓶，也可能是远处的大瓶。只有深度图才能区分二者。

### 3.3 公式前的符号字典：每个字母到底是什么

下面的符号只在本小节使用。先把表看懂，再看公式。

| 符号 | 中文意思 | 单位/类型 | 直观理解 |
| --- | --- | --- | --- |
| \(u\) | 目标像素的横向编号。 | 像素。 | 这个点离画面左边有多少格。 |
| \(v\) | 目标像素的纵向编号。 | 像素。 | 这个点离画面上边有多少格。 |
| \(z\) | 深度图在 \((u,v)\) 处给出的距离。 | 米。 | 这个点离镜头多远。 |
| \(f_x\) | 相机横向焦距参数。 | 像素。 | 将“横向偏了多少格”换成真实横向距离时的比例尺。 |
| \(f_y\) | 相机纵向焦距参数。 | 像素。 | 将“纵向偏了多少格”换成真实纵向距离时的比例尺。 |
| \(c_x\) | 光学中心的横向像素编号。 | 像素。 | 相机真正正前方在画面中的横坐标，通常接近画面宽度的一半。 |
| \(c_y\) | 光学中心的纵向像素编号。 | 像素。 | 相机真正正前方在画面中的纵坐标，通常接近画面高度的一半。 |
| \(x_c\) | 该点在相机坐标系中的左右位置。 | 米。 | 正值在相机右边，负值在相机左边。 |
| \(y_c\) | 该点在相机坐标系中的上下位置。 | 米。 | RealSense 光学坐标里，正值通常向下。 |
| \(z_c\) | 该点在相机坐标系中的前后位置。 | 米。 | 正值在镜头前方；此处等于深度 \(z\)。 |
| \(\mathbf{p}_{camera}\) | “点在相机坐标系中的位置”。 | 三个数构成的向量。 | 把 \(x_c,y_c,z_c\) 打包后的名字。 |
| \(x_b,y_b,z_b\) | 该点在右臂基座坐标系中的三个坐标。 | 米。 | 下标 \(b\) 是 base 的缩写；后续规划最终使用它们。 |

下标 camera 不是乘法，也不是变量的一部分；它是在提醒你：这三个数是“以相机为原点、按相机方向量出来的”。

### 3.4 像素怎样变成相机前方的三维点

有了像素位置 \((u,v)\) 和深度 \(z\)，相机模型计算：

\[
\mathbf{p}_{camera} =
\begin{bmatrix}
x_c\\
y_c\\
z_c
\end{bmatrix}
=
\begin{bmatrix}
\frac{(u-c_x)z}{f_x} \\
\frac{(v-c_y)z}{f_y} \\
z
\end{bmatrix}.
\]

这一个式子不是要你背下来。把它拆成三句即可：

1. \(u-c_x\)：目标像素相对“画面正前方”向左或向右偏了多少像素；
2. 乘 \(z/f_x\)：这个偏差在当前距离下换算成多少米；
3. 纵向也做同样的换算；前后距离直接就是深度 \(z\)。

#### 一个完整的数字例子

假设某一帧相机内参为：

    fx = 600 像素，fy = 600 像素
    cx = 424 像素，cy = 240 像素

YOLO 和深度算法选定的水瓶抓取像素为：

    u = 454 像素，v = 300 像素，z = 0.30 米

代入横向公式：

\[
x_c=\frac{(454-424)\times0.30}{600}
=\frac{30\times0.30}{600}
=0.015\,\mathrm{m}.
\]

所以这个点位于相机正前方偏右 \(1.5\,\mathrm{cm}\) 处。纵向同理：

\[
y_c=\frac{(300-240)\times0.30}{600}
=0.030\,\mathrm{m}.
\]

最后 \(z_c=0.30\,\mathrm{m}\)。因此：

\[
\mathbf{p}_{camera}
=
\begin{bmatrix}
0.015\\
0.030\\
0.300
\end{bmatrix}\mathrm{m}.
\]

请注意，这仍然只是“相对于相机”的位置。机械臂还不知道这个位置在它自己的左边、右边、前面还是后面。

**快速检查。** 若瓶子仍在画面正中央，但从 \(0.30\,\mathrm{m}\) 移到 \(0.60\,\mathrm{m}\)，相同 30 像素的横向偏差对应的真实横向距离会变大还是变小？

答案：变大一倍。距离越远，同样的画面角度偏差对应越宽的真实空间偏差。

### 3.5 坐标系：同一个水瓶可以有不同的坐标

“坐标系”可以先理解为一把带方向的尺子。每把尺子都要说明两件事：

1. 原点在哪里；
2. 哪个方向叫正方向。

本 demo 至少涉及三把尺子：

    相机坐标系：原点在镜头；z 轴朝镜头前方。
    法兰坐标系：原点在机械臂末端金属法兰。
    右臂基座坐标系：原点在右臂底座；规划和围栏的主要参考。

同一个瓶子在相机坐标中可能是：

    [0.015, 0.030, 0.300] 米

这不等于它在右臂基座中的坐标。因为相机装在机器人上方/末端，它的“向前”可能对应机械臂基座中的“向下”或“向左”。所以必须做坐标变换。

### 3.6 读懂变换公式：左上角和右下角的文字是什么意思

公式为：

\[
\begin{bmatrix}
\mathbf{p}_{base}\\
1
\end{bmatrix}
=
{}^{base}\mathbf{T}_{camera}
\begin{bmatrix}
\mathbf{p}_{camera}\\
1
\end{bmatrix}.
\]

逐个解释：

| 符号 | 完整读法 | 意思 |
| --- | --- | --- |
| \(\mathbf{p}_{camera}\) | “p，下标 camera”。 | 该点用相机这把尺子量出来的三维位置。 |
| \(\mathbf{p}_{base}\) | “p，下标 base”。 | 同一个点用右臂基座这把尺子量出来的三维位置。 |
| \(x_b,y_b,z_b\) | “p base 里的三个分量”。 | 分别是基座坐标系中的三个方向位置。 |
| \({}^{base}\mathbf{T}_{camera}\) | “从 camera 变到 base 的 T”。 | 一张已标定的换算表：先把相机方向转成基座方向，再把原点平移到基座原点。 |
| 左上角的 base | 结果要在哪个坐标系表达。 | 结果用 base 的尺子表示。 |
| 右下角的 camera | 输入原本在哪个坐标系表达。 | 输入是用 camera 的尺子量的。 |
| 末尾的 \(1\) | 齐次坐标的固定补位。 | 让“旋转 + 平移”可以写成一次矩阵乘法；它不是额外的空间坐标。 |

你可以先把这条式子读成一句自然语言：

> 把“相机看到的点”放进从相机到右臂基座的换算器，得到“右臂应该理解的点”。

矩阵 \({}^{base}\mathbf{T}_{camera}\) 是手眼标定（hand-eye calibration）的结果。它不是 YOLO 学出来的，也不应随意手改。若相机松动、头部转了、底盘或基座相对桌子的位置改变，换算结果就可能错。

### 3.7 头部相机与腕部相机的区别

头部相机固定在机器人头部。只要头部舵机回到标定时的角度，它到右臂基座的换算表可视为固定：

    T_base_right_to_camera_head

右腕相机固定在右臂末端。机械臂一动，右腕相机也动。因此它到基座的换算要由两段相乘：

\[
{}^{base}\mathbf{T}_{wrist}
=
{}^{base}\mathbf{T}_{flange}(\mathbf{q})
{}^{flange}\mathbf{T}_{wrist}.
\]

符号表：

| 符号 | 意思 |
| --- | --- |
| wrist | 右腕相机坐标系。 |
| flange | 机械臂末端法兰坐标系。 |
| \(\mathbf{q}\) | 当前 7 个关节角组成的一组数；机械臂姿态一变，\(\mathbf{q}\) 就变。 |
| \({}^{base}\mathbf{T}_{flange}(\mathbf{q})\) | 由当前关节角计算出来的“基座到法兰”的变换。 |
| \({}^{flange}\mathbf{T}_{wrist}\) | 腕相机安装在法兰上的固定变换，由标定得到。 |

这条式子可读为：

> 先从右腕相机换到法兰，再从当前法兰换到右臂基座。

demo.py 在每一帧腕部定位时都会读取当前法兰位姿，因此不会把“上一秒相机的位置”错误用于“这一秒的图像”。

### 3.8 法兰、TCP 和三种失败

法兰是第七轴末端的金属安装面；TCP 是程序规定的工具参考点，通常靠近夹爪真正执行任务的位置。本 demo 的 TCP 沿工具轴偏移 \(0.151\,\mathrm{m}\)。相机、法兰和 TCP 是三个不同点，不能混用。

core.py 中三个异常也应区分：

| 异常 | 白话意思 | 程序为什么这样处理 |
| --- | --- | --- |
| CameraFrameUnavailable | 相机没有新画面或画面中断。 | 失去判断依据，必须停。 |
| BottleDetectionLost | 相机还在工作，但没找到“已锁定的那只瓶”。 | 某些远距离阶段可请头部相机独立确认一次。 |
| SafetyAbort | 任一安全前提不成立。 | 停止并保持；不自动后退。 |

到这里你应能说清：YOLO 框给出候选区域；RGB-D 给出距离；相机内参把像素换成相机三维点；手眼变换再把它换成机械臂基座三维点。

## 4. 核心数据：一次定位结果长什么样

阅读项目时，不要先钻进 SDK。先认识 demo.py 传递的三个数据对象。

| 对象 | 来源 | 关键字段 | 作用 |
| --- | --- | --- | --- |
| Detection | YOLO。 | box、confidence、class_name。 | 一个二维候选。 |
| Localization | BottleDemo.localize。 | point_camera、point_base、depth_m、spread、frame_count。 | 已经过多帧共识的三维目标。 |
| DemoParams | core.py。 | samples、pregrasp_standoff_m、segment_m、lift_m 等。 | 算法与动作的安全参数集合。 |

真正供后续规划使用的是 Localization.point_base，而不是 Detection.box。这个设计很关键：**二维框只服务于测量，基座系三维点才是任务对象。**

一次右腕定位成功后，程序会在本次运行目录保存：

    outputs/bottle_grasp/年月日_时分秒/
      右腕精定位_color.jpg
      右腕精定位_depth_m.npy
      右腕精定位_localization.json
      run.log
      run_summary.json

其中 localization JSON 是最适合你复盘的文件。它把“这次究竟抓哪个点、该点深度怎样、稳定帧有几张”保存下来；图像与深度数组则让你回看当时的视觉证据。

## 5. 从一帧画面到“可信抓取点”：逐步读懂 BottleDemo.localize

这一节比前面更贴近代码。目标是读完后你能解释：函数拿到了什么、每一帧发生了什么、为什么一帧会被丢弃、7 帧怎样决定最终抓取点。

入口函数是 demo.py 中的 BottleDemo.localize。它并不“识别一次就结束”，而是反复收集有效帧，直到拿到一组稳定的三维测量。

### 5.1 先看输入与输出：localize 想把什么变成什么

把 localize 看成一个机器：

    输入：彩色图 + 深度图 + 相机内参 + 相机相对基座的位置
      → 重复筛选多张有效画面
      → 输出：一个可以用于规划的 Localization 对象

它的四个输入参数含义如下：

| 参数名 | 白话解释 | 例子 |
| --- | --- | --- |
| label | 这次定位的日志名称。 | “头部粗定位”或“右腕精定位”。 |
| transform_provider | 一个会返回“当前相机到右臂基座”的变换的函数。 | 腕相机每帧随手臂移动，所以必须现算。 |
| depth_params | 本次定位采用的门槛参数。 | 需要几帧、允许多大深度噪声、最远/最近距离。 |
| depth_prior_base | 可选的旧三维点先验。 | 透明瓶某一帧深度坏掉时，用它暂时提供距离参考。 |

它的输出 Localization 可以先理解为一张“测量报告”：

| 字段 | 这是什么 | 单位 | 后续用途 |
| --- | --- | --- | --- |
| point_camera | 最终点用相机坐标表示的 \([x_c,y_c,z_c]\)。 | 米。 | 用于记录与检查。 |
| point_base | 同一个最终点用右臂基座坐标表示的 \([x_b,y_b,z_b]\)。 | 米。 | **规划和抓取真正使用的目标。** |
| pixel | 最终抓取像素 \([u,v]\)。 | 像素。 | 在图像中标出测量位置。 |
| depth_m | 最终使用的深度。 | 米。 | 判断物体离镜头是否合理。 |
| depth_mad_m | 深度样本的离散程度。 | 米。 | 数值越小，单帧深度越一致。 |
| position_spread_m | 多帧基座三维点的最大散布。 | 米。 | 数值越小，多帧定位越稳定。 |
| box | 最终选中的检测框 \([x_1,y_1,x_2,y_2]\)。 | 像素。 | 留存视觉证据。 |
| confidence | 选中检测框的 YOLO 置信度。 | 0 到 1。 | 只是检测信心，不等于三维精度。 |
| frame_count | 最终同意这个位置的有效帧数。 | 帧。 | 看共识是否充分。 |

最重要的一句：后续机械臂规划使用的是 point_base，不是 box，也不是 confidence。

### 5.2 第 0 步：函数只收“新的有效画面”

相机线程不断更新最新彩色图和深度图。localize 不会无限快地重复使用同一帧，而是先检查 timestamp（时间戳）是否比上一张更新：

    新时间戳？
      否 → 等待一点时间，不记入样本
      是 → 读取这张彩色图与深度图，开始处理

原因很简单：假设同一张错误画面被重复读 7 次，看似得到“7 帧一致”，实际只是一帧错误被复制了 7 次。时间戳确保 7 个样本来自不同时间。

若超过等待期限仍凑不齐规定数量的有效帧，函数会报“检测/深度稳定帧不足”，而不会用少量帧偷偷继续。

### 5.3 第 1 步：YOLO 检测框到底是什么，为什么不只取最高分

BottleDetector 接收彩色图，输出一个或零个 Detection。一个 Detection 有三部分：

    box        = (x1, y1, x2, y2)
    confidence = 这个框像瓶子的分数
    class_name = 模型给出的类别名

项目先使用专门模型；专门模型没有找到符合 bottle、water、矿泉水等别名的框时，才用通用 YOLO 兜底。这样做不是为了“多跑一个模型”，而是为标签朝向、遮挡导致专用模型失效留一条保守退路。

右腕相机距离瓶子近，画面可能同时出现远处小瓶、包装图案或局部背景。于是 localize 在右腕模式传入一个形状过滤条件。这个条件要求候选框：

| 检查 | 它在问什么 | 为什么需要 |
| --- | --- | --- |
| 框宽度够大 | 这是不是近处、能抓到的物体？ | 过滤远处非常小的检测。 |
| 框高度够大 | 这个物体有没有完整进入视野？ | 防止只拍到瓶子很小一部分。 |
| 框面积够大 | 框不是一个偶然噪声吗？ | 过滤很小的误检。 |
| 高度/宽度够大 | 外形是否更像竖立瓶子？ | 过滤横向细长或方形背景物。 |

所以“最高置信度”并不是唯一标准。一个 0.98 分的远处小框可能不是当前要夹的瓶子；一个 0.75 分但完整、近处、竖直的框更符合本任务。

### 5.4 第 2 步：检测框里为什么还要再选三个采样区

假设 YOLO 得到：

    x1 = 400，y1 = 120
    x2 = 520，y2 = 380

这个框宽度为 \(520-400=120\) 像素，高度为 \(380-120=260\) 像素。它框住的是整个瓶子，不是一个精确三维点。

perception.py 中的 _zones 会从此框内部取三个小矩形：

    瓶盖附近：框的中上部
    标签附近：框的中部
    瓶身区域：较长的中间区域

对上面的例子，三个区大致是：

| 区域 | 大致像素范围 | 为什么取它 |
| --- | --- | --- |
| 瓶盖区 | 横向 442–478，纵向 127–177。 | 可能提供靠近瓶顶部的深度。 |
| 标签区 | 横向 430–490，纵向 218–296。 | 有时纹理丰富、深度较稳定。 |
| 瓶身区 | 横向 440–479，纵向 172–343。 | 覆盖较大瓶身，增加有效点数量。 |

这里“抽三个区”不等于说三个区各取一个点后平均。它的意思是：从三个位置收集许多深度候选，避免某一小块恰好反光、透明或缺深度时整帧失败。

### 5.5 第 3 步：先理解深度图里的 NaN、前壁、后壁和背景

depth 是一张和颜色图对齐的二维数表。depth[v,u] 表示：第 \(v\) 行、第 \(u\) 列像素测得的距离，单位为米。

但对透明或反光瓶，框内可能同时出现三类数：

    0.295 m 左右：瓶子靠近相机的前壁
    0.340 m 左右：穿透/反射后测到的瓶子后壁
    1.800 m 左右：透过瓶子或框边缘看见的背景

还可能出现 NaN。NaN 的意思不是数字 0，也不是距离无限远；它表示这一个像素没有可靠深度值。代码会直接丢弃 NaN。

在每个采样区中，代码只保留同时满足以下条件的深度像素：

    是有限数字
    ≥ min_depth_m
    ≤ max_depth_m

右腕默认的 min_depth_m 是 \(0.12\,\mathrm{m}\)，max_depth_m 是 \(0.65\,\mathrm{m}\)。因此特别远的背景值不会进入右腕抓取深度的候选集合。

### 5.6 第 4 步：robust_near_cluster 怎样选深度

这一步最容易被一句“深度聚类”吓到。它可以完全用分组投票理解。

假设从三个采样区收集到很多深度值。函数 robust_near_cluster 里的变量含义如下：

| 变量名 | 它保存什么 | 白话理解 |
| --- | --- | --- |
| values | 所有合法深度值。 | 一大把候选距离。 |
| bins | 每 \(1\,\mathrm{cm}\) 划分一次的深度边界。 | 一排小抽屉，按距离收纳数据。 |
| hist | 每个抽屉里有多少深度值。 | 哪个距离段票数多。 |
| supported | 票数达到最低门槛的抽屉编号。 | 不是偶然噪声的距离段。 |
| run | 连续相邻的 supported 抽屉。 | 一个可能属于同一物体表面的深度簇。 |
| cluster | 某一个 run 中真正的深度值。 | “这群看起来测到同一表面”的样本。 |
| median | cluster 的中间值。 | 这帧采用的距离 \(z\)。 |
| mad | 每个样本离 median 的绝对偏差的中间值。 | 这群深度自身有多散。 |
| filtered | 丢掉太离谱样本后留下的 cluster。 | 更干净的最终样本集合。 |

#### 用具体数字走一遍

考虑以下 16 个深度值，单位为米：

    0.293, 0.294, 0.295, 0.295, 0.296, 0.296,
    0.297, 0.298, 0.299, 0.300, 0.301, 0.302,
    0.341, 0.343, 1.810, 1.820

把距离按约 \(1\,\mathrm{cm}\) 分抽屉后：

    0.29–0.30 m 附近：12 票，且彼此连续
    0.34 m 附近：2 票
    1.81 m 附近：2 票

最靠近相机、又有足够票数支持的簇是 \(0.29\) 到 \(0.30\,\mathrm{m}\) 的那一群。代码选它，而不取所有 16 个值的平均数。因为平均数会把瓶子、后壁和背景混成一个现实中不存在的距离。

接着计算中位数。排序后中间位置大约在 \(0.296\,\mathrm{m}\)，于是最终深度约为：

\[
z=0.296\,\mathrm{m}.
\]

MAD 的计算步骤是：

1. 对每个样本算“它离 \(0.296\,\mathrm{m}\) 有多远”；
2. 把这些绝对偏差排序；
3. 取中间偏差作为 MAD。

若大多数样本只差 \(1\) 或 \(2\,\mathrm{mm}\)，MAD 很小，说明这一帧深度一致；若样本散到 \(0.29\)、\(0.33\)、\(0.40\) 等很多位置，MAD 会大，代码会拒绝这帧。当前门槛是：

\[
\mathrm{MAD} \le 18\,\mathrm{mm}.
\]

请把它读成：“这帧中被选中的瓶子表面，深度不能乱跳得超过允许程度。”

### 5.7 第 5 步：最终抓取像素 \(u,v\) 是怎样选的

深度簇给出“瓶身大概离相机多远”。下一步要选画面中的一个横向像素 \(u\) 和纵向像素 \(v\)，以便把它投影为三维点。

代码的策略是：

    u = 所有“深度接近 z”的像素横坐标的中位数
    v = y1 + 0.66 × (y2 - y1)

其中：

| 符号 | 在这里代表什么 |
| --- | --- |
| \(y_1\) | 检测框最上方的像素行。 |
| \(y_2\) | 检测框最下方的像素行。 |
| \(0.66\) | 从框顶部往下走 66% 的固定比例。 |
| \(u\) | 可信深度像素在水平方向的中间位置。 |
| \(v\) | 预先定义的、偏向瓶身下部的夹取高度。 |

仍用上面的检测框：\(y_1=120\)，\(y_2=380\)。

\[
v=120+0.66(380-120)
=120+171.6
\approx292.
\]

也就是说，程序把夹取高度放在图像第 292 行附近，而不是让每一帧的反光/缺深度像素决定抓取高度。这里的 0.66 是当前水瓶 demo 的任务选择；它不是相机原理，也不是所有物体都应使用的数字。

得到 \(u,v,z\) 后，才使用第 3 节的相机内参公式得到 point_camera，再通过当前相机外参得到 point_base。

### 5.8 第 6 步：一张有效帧必须同时通过哪些门

一张画面被加入 localize 的样本列表前，必须按顺序通过：

    1. 这是一张新画面
    2. 彩色图和深度图都存在
    3. YOLO 找到符合要求的瓶子框
    4. 三个采样区至少有有效深度
    5. 深度能形成足够支持的近处簇
    6. 深度 MAD 不超过门槛
    7. 像素点能被转换为相机三维点
    8. 相机三维点能被转换为右臂基座三维点

通过后，代码才把本帧的以下内容 append 到列表：

    camera_points：本帧的 point_camera
    base_points：本帧的 point_base
    depths：本帧的 z
    mads：本帧的深度 MAD
    detections：本帧的 YOLO 检测框
    pixels：本帧的 (u, v)

append 的意思是“追加到列表末尾”。这个列表就是后面多帧共识的原始证据。

### 5.9 第 7 步：7 帧共识到底怎样计算

先用一个简化例子。假设 7 个 base 坐标点的单位都写成毫米，仅为方便阅读：

| 帧 | \([x_b,y_b,z_b]\) | 它接近哪一处 |
| --- | --- | --- |
| 1 | [300, 100, -120] | 瓶子。 |
| 2 | [302, 101, -119] | 瓶子。 |
| 3 | [299, 99, -121] | 瓶子。 |
| 4 | [301, 100, -120] | 瓶子。 |
| 5 | [300, 102, -120] | 瓶子。 |
| 6 | [360, 105, -120] | 可能测到了背景/另一表面。 |
| 7 | [358, 104, -121] | 可能测到了背景/另一表面。 |

代码对任意两帧计算三维直线距离。两点 \(\mathbf{a}\) 和 \(\mathbf{b}\) 的距离为：

\[
d=\sqrt{(a_x-b_x)^2+(a_y-b_y)^2+(a_z-b_z)^2}.
\]

这里的 \(a_x,a_y,a_z\) 是点 \(\mathbf{a}\) 的三个坐标，\(b_x,b_y,b_z\) 是点 \(\mathbf{b}\) 的三个坐标。你可以把它看作三维版的“横向差、纵向差、高度差一起算”。

默认允许半径是 max_position_spread_m \(=0.025\,\mathrm{m}=25\,\mathrm{mm}\)。上表前 5 帧彼此只相差几毫米，构成一个 5 帧簇；第 6、7 帧与前 5 帧相距约 60 毫米，落在簇外。

代码的具体规则是：

    required = ceil(0.70 × 有效帧数)，但至少为 3

当有效帧数是 7：

\[
\operatorname{ceil}(0.70\times7)
=\operatorname{ceil}(4.9)
=5.
\]

因此 7 帧里至少要有 5 帧在 25 毫米半径内，才叫稳定共识。前 5 帧通过，后 2 帧被当作离群点。

最终点不是 7 帧平均值，而是这 5 个内点在每一个坐标维度上的中位数：

    x_b 取 299、300、300、301、302 的中位数 = 300
    y_b 取 99、100、100、101、102 的中位数 = 100
    z_b 取 -121、-120、-120、-120、-119 的中位数 = -120

最终位置是：

\[
\mathbf{p}_{base}=
\begin{bmatrix}
300\\100\\-120
\end{bmatrix}\mathrm{mm}.
\]

这正是“共识定位”而不是“简单平均”的含义。

#### 一个必须修正的边界情况

若 7 帧中有 4 帧落在瓶前壁、3 帧落在背景墙，程序**不会**选择 4 帧，也不会平均。因为默认规则要求至少 5 帧同簇；4 小于 5，所以 localize 报“多帧定位没有稳定共识”并中止本次定位。

这是故意保守的。4 对 3 说明视觉系统在两个解释之间摇摆，不能把“略多的一方”伪装成可信结论。

### 5.10 日志中的三个数字应该怎样看

定位成功日志常类似：

    右腕精定位稳定：共识帧 7/7，散布 3.2 mm

逐项解释：

| 日志片段 | 意思 | 能说明什么 | 不能说明什么 |
| --- | --- | --- | --- |
| 共识帧 7/7 | 7 张有效三维测量都落入同一稳定簇。 | 当前视觉测量非常一致。 | 不保证手眼标定绝对正确。 |
| 散布 3.2 mm | 这 7 个点中，离最终中位数最远的点仍只有 3.2 毫米。 | 本轮深度和相机/机器人同步稳定。 | 不代表夹爪一定能夹住。 |
| YOLO 置信度 0.95 | 选中框在某一帧很像水瓶。 | 分类模型很自信。 | 不代表距离正确，也不代表 7 帧稳定。 |

因此“共识帧”和“散布”通常比单个 YOLO 分数更值得关注；但它们仍只证明测量稳定，后续还必须通过规划、围栏和避障。

若你想在源码里跟一帧数据，按以下顺序阅读：

## 6. 从头部到右腕：完整状态机逐步追踪

现在打开 demo.py 的 BottleDemo.run。把下面的伪代码与源码并排阅读，基本能跟完整个项目。

    initialize()
    preflight()
    
    如果是 finish-from-current：
        不再定位；只放回、返回初始姿态
    否则如果是 resume-at-wrist：
        读取上一轮记录
        右腕重新独立定位
        检查与旧记录的跳变
        可选择仅视觉确认，或进入抓取
    否则：
        头部粗定位水瓶
        从深度图构建场景，并拟合桌面
        规划到某个右腕观察位
        plan-only 则结束
        执行到观察位
        切到右腕相机，精定位
        stop-after-observation 则结束
        进入抓取、抬升、可选放回

### 6.1 initialize：连接什么，尚未移动什么

initialize 做五件事：确认头部标定基准角度；加载 safety profile；启动 dashboard；打开头部或右腕相机；在 plan 或 execute 模式下连接右臂、左臂关节读取器和 MoveIt。

“连接右臂”和“接管右臂”不同。RobotSession 的 take_control 只会在 execute 且不是只读视觉检查时为真。这样 check/plan 仍可读取必要的状态，但不会把自己变成运动控制源。

### 6.2 头部粗定位：解决“往哪里看”

全自主模式先用头部相机调用 localize。其输出要先通过电子围栏的 assert_tcp_point；目标若已经不在允许的任务体积内，后续根本不规划。

然后 _build_head_scene 从头部深度图生成稀疏体素障碍点，同时调用 table_model.fit_table_top 拟合真实桌面高度。若本轮桌面高度与已验证 profile 的差异在容忍范围内，adapt_profile_to_table 才会相应调整 table_top 禁入盒；超出范围会中止，而不是“猜一个新桌面”。

这一步回答两个不同的问题：

| 产物 | 回答的问题 |
| --- | --- |
| head_target.point_base | 瓶子大致位于哪里？ |
| scene_voxels 和 table_top | 从当前位置到观察位，什么空间不能穿过？ |

### 6.3 观察位不是写死姿态，而是一组候选

_observation_flange_candidates 围绕水瓶生成候选腕部相机位姿：4 个观察距离、4 个高度偏移、3 个侧向偏移，合计 \(4 \times 4 \times 3 = 48\) 个候选。每个候选的相机光轴都朝向水瓶，再借由腕部相机外参反推法兰姿态。

_observation_plan_targets 对每个候选依次做：

1. 把候选法兰变换成 TCP，检查是否在电子围栏允许区且不碰桌面。
2. 用机械臂逆运动学求七个关节角。
3. 按离当前关节角的距离评分，保留可达候选。

所以系统不是“硬编码一个观察位然后祈祷能到”。它会让一批可能看清瓶子的端点竞争，再交给全局规划器。

### 6.4 SafeMotionPlanner：为什么有 MoveIt 后还要它

MoveIt 只负责提出一条关节路径。safe_planner.py 的 SafeMotionPlanner 将它包装为“可执行候选”的流程：

1. 至多选评分前 8 个观察位候选。
2. 每个候选至多尝试 2 条路线，因此尝试总数有上限，不会无限重试。
3. 将头部点云、静态桌面禁入盒和工具保护体加入 MoveIt。
4. 得到轨迹后，先以 \(1.5^\circ\) 的最大关节步长插值。
5. 用机器人正运动学得到密集 TCP 点，独立调用电子围栏检查。
6. 再让 MoveIt 对这条密集关节路径做后验碰撞检查。
7. 若电子围栏发现某一点越界，把该点附近变成临时碰撞盒，换路线或换端点。

这是一种“规划器提出，独立规则复核”的设计。规划阶段与复核阶段不会完全共享同一种采样误差，能降低路径恰好从桌面边缘擦过的风险。

### 6.5 右腕精定位与目标锁定

机械臂到观察位后，程序切换到右腕相机，再跑一次 7 帧定位。头部定位只是粗先验；真正供抓取使用的是 wrist_target.point_base。

之后目标被锁定。target_guard.py 中的 ProjectedTargetAssociation 会把这一个固定三维点投影到当前腕部图像；只有覆盖该投影点附近的检测框才算“同一瓶”。它避免机器人在移动途中把画面里的另一个瓶子、背景瓶或新噪声框误认作目标。

若腕部画面活着但关联失败，LockedTargetGuard 最多切到固定头部相机做一次独立确认。头部确认的结果只回答“瓶子仍在锁定点附近吗”；它绝不静默替换 wrist_target。若偏移超过 \(5\,\mathrm{cm}\)，当前路径作废。

## 7. 最后十几厘米：局部路径、奇异点与夹爪判定

### 7.1 抓取点与预抓取点

candidate_path 以锁定目标为抓取点，再沿工具接近轴反向退 \(8.5\,\mathrm{cm}\) 得到预抓取点。路径被切成最长 \(4.5\,\mathrm{cm}\) 的笛卡尔段。

这使动作分为两段：

1. 当前姿态到预抓取位：每段前检查点云通道、电子围栏、逆解、目标关联；腕部关联丢失可停下来交给头部确认。
2. 预抓取位到抓取点：低速执行。夹爪开始遮挡瓶子时允许检测框临时消失，但不允许相机流中断。

这不是“走得慢就安全”。低速只是降低后果；真正的安全来自每段均经过可达性、碰撞、围栏和感知状态检查。

### 7.2 为什么候选姿态会绕轴旋转

同一个瓶身位置不只对应一种夹爪朝向。candidate_path 会尝试 \(0^\circ,\pm15^\circ,\pm30^\circ\) 的绕接近轴旋转；_plan_ik_avoiding_singularity 还会处理第 4 关节接近 \(0^\circ\) 的奇异带。

奇异点可以简单理解为：某些姿态下，末端一点点方向变化会要求关节异常大的变化，控制变得不稳定。代码并不假装“求出逆解就没问题”，而是保留关节限位余量并拒绝穿过奇异带的局部路径。

### 7.3 夹爪为何每轮都做空夹标定

_grasp_and_lift 先在观察位的自由空间中闭合夹爪，记录本轮空夹闭合位置。随后打开、接近、夹紧水瓶，并比较反馈位置：

    夹到物体的闭合位置 > 本轮空夹闭合位置 + object_margin

当前 object_margin 是 6，而不是一个与日期无关的神秘常量。这样可避免夹爪磨损、温度、通讯细节改变时，仍把旧的“空夹位置”当成真理。若本轮空夹行程本身太短，程序也会中止，因为这可能说明夹爪前已有障碍物或硬件异常。

夹稳后，程序生成并验证向上 \(5\,\mathrm{cm}\) 的路径。cycle 模式会反向下降、松开、沿接近轴退 \(8.5\,\mathrm{cm}\)，最后空载收拢夹爪；return-home 则再次走同一套 SafeMotionPlanner 回到 profile 中的 home_joints_deg。

## 8. 安全 profile：什么能改，什么不能随便改

safety_profiles.json 的 table_demo 是“当前桌面已经验证过”的现场模型。它包含：

| 配置 | 含义 | 改动后意味着什么 |
| --- | --- | --- |
| frame / moveit_frame / T_moveit_from_profile | 电子围栏坐标系与 MoveIt 坐标系的关系。 | 必须重新验证坐标变换，不能凭感觉平移数字。 |
| tcp_workspace | TCP 的总工作边界。 | 改大不等于真实可达或安全。 |
| allowed_tcp_zones | 事先允许通行的安全体积。 | 需要结合机械臂、桌面和周边物体现场验证。 |
| keepout_boxes.table_top | 桌面及其下方的禁入三维盒。 | 桌子移动或高度变化后必须重测。 |
| clearance_m | 盒子外扩的安全余量。 | 改小会直接降低碰撞余量。 |
| home_joints_deg | cycle 结束后返回的七轴关节角。 | 底盘/桌子位置变化后先只跑 plan。 |

正确的改动流程不是先改 JSON 再 execute，而是：测量实际几何 → 写入候选 profile → 跑单元测试与 plan → 现场 observe → 人工确认无误后才把 profile 标为可执行。货架场景必须从 shelf_template 建模，不能复用 table_demo。

## 9. 两个完整的思考例子

### 例子 A：正常的一次 observe 为什么值得信任

假设头部定位得到 \(\mathbf{p}_{base}\)，生成的某个观察位候选通过围栏和逆解。SafeMotionPlanner 找到路线，密集 TCP 复核也没有进入 table_top。observe 真实执行到观察位后，右腕日志显示：

    有效帧 1/7 ... 有效帧 7/7
    右腕精定位稳定：共识帧 7/7，散布 3.1 mm
    观察位测试完成：本轮不抓取

此时可以得出的结论是：在这一次摆位下，机器人成功到达一个右腕可稳定看到瓶子的姿态，且本轮三维定位的一致性很好。不能得出的结论是“以后任何摆位都可以直接 cycle”——场景与标定仍是前提。

### 例子 B：腕部检测丢失为什么有时中止、有时只是警告

若在前往预抓取位时，画面还在但投影关联不到锁定点，程序不能假设是遮挡：手指此时通常尚未覆盖瓶子。它会暂停并让头部相机确认；确认失败或位置偏移过大，就中止。

若在最后接近的最后若干厘米，手指已经进入相机视线，检测框丢失很可能是遮挡。此时程序保留原锁定点并记录警告，继续完成已验证的短距离路径。但无论哪个阶段，只要 RGB-D 流断开，就会中止，因为它失去了判断当前阶段的依据。

## 10. 推荐的代码阅读顺序

不要从 robot.py 的 SDK 调用开始。按下面顺序，每读完一项都能回答一个完整问题。

1. **scripts/bottle_grasp_demo.py**：有哪些命令行模式？异常为什么转成退出码 2？
2. **bottle_grasp/core.py**：DemoParams、Localization、位姿插值分别是什么。
3. **bottle_grasp/demo.py 的 run 与 initialize**：全局状态机从哪里分支。
4. **bottle_grasp/perception.py 和 demo.py 的 localize**：检测框如何成为稳定的 base 点。
5. **bottle_grasp/safety.py 与 safety_profiles.json**：什么叫“允许空间”，坐标如何转给 MoveIt。
6. **bottle_grasp/safe_planner.py**：为什么规划后仍密集复核与重规划。
7. **demo.py 的 candidate_path、_approach_pregrasp、_grasp_and_lift**：最后接近如何执行。
8. **bottle_grasp/robot.py**：最后再看 SDK 调用、关节健康检查、夹爪反馈与保持。

每看完一个函数，建议在 run.log 中找同名 stage。这个项目刻意用 stage 方法记录“初始化”“右腕精定位”“安全规划尝试”“低速最后接近”等阶段；日志不是附属品，而是状态机对外可审计的轨迹。

## 11. 常见误解与调试方向

| 现象或误解 | 先查哪里 | 正确理解 |
| --- | --- | --- |
| YOLO 分数高，但程序仍拒绝定位。 | perception.py 日志、深度 MAD。 | 分类可信不代表深度可信。 |
| plan 有路径，observe 却失败。 | 真机相机、头部基准、围栏、关节状态。 | 规划模型与真实世界可能不同。 |
| 目标在近处“跳动”。 | localization JSON、锁定目标守卫。 | 近距裁边/遮挡会导致重新测量不可靠，因此不应随帧改目标。 |
| 路径碰桌面。 | safety_profiles.json、桌面拟合日志、坐标系。 | 首先怀疑 profile 或外参，而不是随意降低 clearance。 |
| 夹爪显示抓空。 | 空夹标定值、夹紧后的 pos/current、实物宽度。 | 必须比较本轮动态基线，不能只套历史位置。 |
| 程序中止却不自动缩回。 | run.log 中最后一个 SafetyAbort。 | 这是故意的 fail-closed 设计；未知原因下缩回也是危险运动。 |

## 12. 练习与小项目

### 练习

1. **基础。** 用自己的话解释 Detection 与 Localization 的区别；哪个可以直接用于规划？
2. **理解。** 为什么腕部相机的外参需要与当前法兰位姿相乘，而头部相机通常不需要？
3. **诊断。** 给定“共识帧 2/7”，列出至少三类可能原因，并分别说明该去看图像、深度还是标定。
4. **迁移。** 要把 demo 从桌面改到货架，为什么不能只把 table_top 的高度改一下？
5. **设计。** 如果要增加“放进盒子”的动作，请指出至少三个需要扩展的安全/规划位置。

### 答案要点

1. Detection 是二维分类候选；Localization 是经过深度、坐标变换和多帧共识的基座系三维点，后者才能规划。
2. 腕部相机相对世界随关节运动；头部相机在锁定基准姿态时可使用固定外参。
3. 可能是瓶子出画或 YOLO 不稳（看颜色图）；透明/反光使深度失败（看深度和 MAD）；相机/机器人姿态或手眼标定改变（看点的基座系跳变和头部基准）。
4. 还需测量货架侧板/层板、建立允许走廊和碰撞几何，验证新的观察位与可达性，并按 plan、observe、grasp 的等级验证。
5. 至少包括盒子碰撞盒和允许区、放置姿态及其逆解、放低/松夹/退开局部路径、以及放置后返回初始姿态的全局路径。

### 小项目：完成一次可审计的 observe 复盘

选一次 outputs/bottle_grasp 下的 observe 输出目录，写一页复盘。交付物必须包含：

1. 画出从头部定位到右腕精定位的数据流，并标注两个坐标系。
2. 摘录本次 run.log 的关键 stage，并说明每一步解决了什么风险。
3. 打开 localization JSON，报告 point_base、frame_count、depth_m、position_spread_m，并解释它们是否支持升级到 grasp。
4. 检查所用 safety profile，写出这次执行依赖的三个现场假设。

评分标准：不是“程序没报错”，而是能用配置、图像、三维定位记录和日志证明你理解了这次运行的安全边界。

## 13. 最后用一条链记住项目

这个 demo 的核心不是 YOLO，也不是 MoveIt，而是下面这条不能缺环的因果链：

    稳定视觉测量
      → 基座系锁定目标
      → 可达的观察位
      → 碰撞规划与独立围栏复核
      → 分段接近中的目标守卫
      → 动态夹爪判定
      → 抬升/放回/返回时仍走同样的安全链

你能逐项解释这条链，并能在代码、配置和日志中找到每一项时，就已经真正掌握了这个水瓶 demo 的结构。下一步再读 docs/bottle_grasp_demo_runbook.md，用真实失败日志对照第 11 节，会比直接修改参数更有效。
