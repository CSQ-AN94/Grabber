## 一、全部现场启动命令

在 Mac 的仓库根目录执行。脚本会同步当前代码、检查头部/右腕相机占用，然后远程
启动机器人任务。

| 步骤 | 命令 | 做什么 | 正常终点 |
|---|---|---|---|
| **0. 板房体检（上任务前必跑，零机械臂运动）** | `scripts/run_bottle_grasp_site_check.sh` | 时钟 → 头部舵机基准 → MoveIt 碰撞三态探针 → 相机/SDK/MoveIt 栈 → 右臂健康 → 夹爪反馈 → 头部深度流 → 真实 YOLO 定位 → 桌面拟合+场景预算 → **完整规划彩排**（真实场景+真实 IK+全部契约，产出可执行轨迹）→ 右腕相机流 | 逐项表格 + `GO`（退出 0）/`NO-GO`（退出 2）；证据在 `outputs/bottle_grasp/<run>/site_check.json` |
| 1a. 右臂已经在腕部观察位 | `scripts/run_bottle_grasp.sh from-observation` | 新鲜头部锁定 → 本轮桌面/场景 → 新鲜腕部关联与观察位门禁 → 抓取 → 抬升 → 放回并松开 → 退开 → 固定头部确认释放 → 空载收拢 | 夹爪空载收拢，右臂停在退开位，进程退出 0 |
| 1b. 从头部观察开始 | `scripts/run_bottle_grasp.sh from-start` | 新鲜头部锁定 → 本轮桌面/场景 → MoveIt 到右腕观察位 → 与上一行相同的共享抓放流程 → MoveIt 返回配置的 home | 瓶子已放回，右臂回 home，进程退出 0 |

**三层验证各自保证什么（别混）**：本地 `pytest test/bottle_grasp/`（mock）只
保证"逻辑没被改坏"，对上机成功率没有预测力；**板房体检**在真机上用真实数据把
整条链路（相机、舵机、SDK、YOLO、桌面、MoveIt、IK/FK 契约）验到"产出一条真的
可执行轨迹"为止，GO 意味着 from-start 会执行的就是彩排同款轨迹；但抓取/放回的
**执行段**（movel 到位精度、夹爪力控、视觉截断）只有真跑任务才验得到。旧
`plan` 模式只覆盖体检的前半段且无逐项结论，已被体检取代。

两个任务都会在接管 SDK 前停止 `atom`/`zhixing_ctrl.py` 遥操；任务退出后**不会自动
恢复遥操**。先确认机械臂已经静止、周围安全，再从 Mac 单独运行：

```bash
ssh rm@192.168.3.68 \
  'bash /home/rm/rmc_aida_l_atom/scripts/upstart_all.sh'
```

这条恢复命令不是第三个抓放入口，只负责在完整任务结束后恢复官方遥操。

可覆盖的部署变量如下；它们只改变连接、运行时路径、dashboard 端口或 profile，
不改变工作流拓扑：

| 变量 | 默认值 | 备注 |
|---|---|---|
| `ROBOT_HOST` | `rm@192.168.3.68` | SSH 用户与主机；不接受空格或 shell 元字符 |
| `REMOTE_DIR` | `/home/rm/Grabber` | 机器人上的仓库绝对路径 |
| `REMOTE_PY` | `/home/rm/miniconda3/envs/tube_vision/bin/python` | 机器人上的 Python 绝对路径 |
| `SAFETY_PROFILE` | `table_demo` | 已验证的电子围栏 profile 名 |
| `PORT` | `8879` | 机器人本地 dashboard 端口，范围 `1-65535` |


`BOTTLE_GRASP_ALLOW_LEGACY=1` 只给开发者做隔离诊断，不是现场任务命令。

## 二、运行前条件

两种模式都必须满足：

1. 瓶子放稳，桌面和机械臂周围没有未建模的杂物；显示器、线缆和人的身体不会被
   RGB-D/MoveIt 自动“理解”。
2. `table_demo` 的静态边界仍适用于现场；任务会用本轮头部深度拟合桌面高度，但不会
   猜测完全不同的桌子、货架或障碍物几何。
3. 夹爪前方没有物体，以便在观察位做一次本轮空夹闭合基线标定。
4. 控制器和七个关节无故障；控制器原生旧围栏不得处于启用状态。
5. 一名操作者全程守硬件急停。终端的 Ctrl+C 只请求缓停和保持，不能替代硬件急停。
6. 从头部场景采集到全局运动结束期间，工作区和左臂必须保持冻结；人员、线缆、瓶子
   或另一机械臂都不能进入/移动。程序会核对左臂，但 RGB-D 快照不是持续动态避障器。

`from-observation` 还要求右臂已经处于腕部相机能观察瓶子的位置。程序不会信任人工
描述，而会在右臂开始抓取接近前检查：目标是本轮新鲜检测、与头部锁定投影关联、
腕部纵深在 `0.110–0.550 m` 内，并且从当前姿态进入预抓取位的 IK、关节限位和
电子围栏都通过；当前 TCP 必须仍在安全域内，完整的
观察位 → 预抓取 → 抓取 → 抬升 → 放低 → 退开关节链还会经过 MoveIt 全链、自碰、
左臂和场景复核。初始化阶段仍可能校正固定头部并收拢空夹爪，因此这里不是“任何
硬件动作之前”的无运动检查。

## 三、半瓶可见的处理

2026-07-18 真实日志中的腕部框为 `(344, 165, 467, 479)`，图像大小为
`640×480`，即瓶子被画面底边确定性截断。旧代码把可见表面的 `0.315 m` 深度写回
原先的 `0.360 m` 目标中心，并在预抓取位强制重新做三帧完整 3D 定位，最终出现
`0/3` 中止。

现在的规则是：

- 固定头部的本轮锁定拥有瓶心深度和物理抓取高度；
- 腕部原始框只要与锁定目标投影关联，就允许瓶身被画面边缘截断；
- 腕部只做有界横向居中，不用透明瓶近表面深度或截断框的可见高度覆盖锁定值；
- 到预抓取位只确认“同一瓶子仍在”，不重新定义抓取点；腕部局部视野丢失时，固定
  头部可独立确认一次，RGB-D 断流仍立即中止；
- 放回退开后必须由固定头部再次确认瓶子仍在锁定位置；腕部 2D 框不能证明释放，
  因为粘在手指上的瓶子可能在退开时仍停留于相同腕部像素。确认前任务的物体状态
  保持 `unknown`。

## 四、规划与执行门禁

`from-start` 的全局转移现在有以下硬门禁：

1. 本轮头部占据场景不再删除整块检测框，也不再清空目标周围半径 `14 cm` 的球；
   观察位转移是非接触运动，瓶旁障碍和目标本身必须保留为占据证据。
2. 观察位使用明确的关节目标，执行的是通过 RealMan IK 和后续抓放预演的同一冗余
   分支；MoveIt 端点还必须通过 SDK FK 回算到候选法兰位姿。不能再用位姿目标落到
   另一条靠近奇异点的关节分支。
3. MoveIt 会预检候选 SDK IK 终态，并在失败信息里返回具体自碰撞 contact；不再只打印
   `error=99999`。
4. MoveIt 的 live PlanningScene 必须能读回请求的碰撞盒和 `bottle_tool_guard`；同一
   起点/端点关节下的 MoveIt `r_link7` FK 还必须与 SDK FK 对齐。
5. MoveIt 返回端点必须由 RealMan SDK 正解得到同一个控制器法兰位姿；位置差超过
   `12 mm` 或姿态差超过 `4°` 时整条轨迹禁止执行。
6. 轨迹绑定规划时的真实起始关节。执行前偏离超过 `0.8°` 即判定轨迹过期；每个阻塞
   SDK 关节点执行后读取真实关节反馈，最大偏差超过 `1.2°` 就停止继续下发。
7. MoveIt 全臂密集状态复核和独立 SDK TCP 电子围栏复核总是分别运行并共同留证，
   任一失败都拒绝；不能因为 SDK 围栏先失败就跳过 MoveIt 复核。
8. `JointTrajectory` 必须恰好包含 `r_joint1…r_joint7`，并按消息里的
   `joint_names` 重排后才允许交给 SDK；缺失、重复、额外关节和 NaN/Inf 全部拒绝。
9. 搜索会覆盖最多 `48` 个按后续抓放余量排序的观察位，并轮转
   RRTConnect、LBKPIECE、RRT*、PRM*；总预算 `120 s`。某条重复或失败路线不会
   代表“无路可走”，也不会让程序提前放弃剩余候选。若搜索时间让原场景变旧，程序
   会重新采集 RGB-D，并用新场景复核**已经选中的完整轨迹**，通过后才执行。
10. 计划同时绑定左右臂快照；执行前、执行中和执行后都会复核左臂，偏离超过 `0.8°`
   会触发缓停；任务级监控还覆盖接近、抓取、抬升、放低和退开。RGB-D 场景年龄超过
   `45 s` 会拒绝执行，而且在可能阻塞的左臂读取之后会再次检查，避免时效竞态。
11. 到达观察位前，规划得到的**实际终点**会重新预演整个抓放尾段，并用更宽的 J4
   奇异区余量淘汰“能到观察位、但下一步抓不了”的分支。完整任务中不允许临时发送
   只看 TCP 围栏的 J4 弯肘逃逸 `movej`；若实时状态已在奇异带内会直接安全中止。
12. 两个入口的局部抓放链都启动 MoveIt：只从场景中删除锁定瓶子的有界物理圆柱，
   桌面和邻近物仍保留；SDK 围栏与 MoveIt 全链、自碰、左臂和 RGB-D 场景必须共同
   通过。无腕部框时也不会把整条接近通道当作自由空间。
13. 最后接近、抬升、放低和退开使用的每个阻塞 `movel` 不再只相信返回码：还会读取
    关节健康状态与真实 TCP，位置偏差超过 `8 mm` 或姿态偏差超过 `4°` 就停止后续动作。
14. 夹爪反馈不再等于“已经抓住瓶子”：抬升后必须由固定头部的新鲜 3D 测量证明瓶子
   离开原桌面点并到达约 `+5 cm`；释放后也必须重新实测回到锁定点，深度缺失时禁止
   用旧深度补成成功。否则任务保持 `unknown` 并中止，不能写 `HELD` 或 `DONE`。
15. 体素超过安全预算时不再按“离瓶最近”静默删除远处障碍，而是整轮拒绝运动；SDK
    围栏生成的反馈盒只用于下一次规划，不会污染对原轨迹的独立 MoveIt 诊断。

当前仍是“MoveIt 规划与复核 + RealMan SDK 密集低速执行”的迁移实现，没有伪装成
ROS 2 `FollowJointTrajectory` 的统一执行链。成熟的后续方向是使用 RealMan 官方
`ros2_control` 驱动、`joint_trajectory_controller` 和 MoveIt 执行监控；在那之前，
上述模型一致性和反馈门禁不可删除。

## 五、成功、失败与证据

每轮输出目录为机器人上的：

```text
/home/rm/Grabber/outputs/bottle_grasp/<微秒时间戳_UUID>/
```

关键文件：

| 文件 | 含义 |
|---|---|
| `run.log` | 本轮完整日志 |
| `task_journal.jsonl` | 带 `run_id`、任务阶段和 `object_state` 的事务顺序 |
| `task_result.json` | 唯一终态；只有 `status=done`、`phase=done`、`object_state=empty` 才算软件流程完成 |
| `grasp_lift.json` | 夹持反馈和抬升证据；它本身不再被叫作 success |
| `head_scene.json` | 本轮桌面拟合、碰撞盒和 RGB-D 体素摘要 |
| `*_request.json` / `*_plan.json` | MoveIt 规划输入与输出 |

任何异常都会返回非零退出码并保持，不会加载旧日志自动续跑，也不会在物体状态未知时
假装空手回 home。任务成功后正常退出，不再无限等待 Ctrl+C。

## 六、第一次实机验收

第一次修改后验收按风险递增执行，但每次都调用完整流程，不能用旧阶段命令拼接：

1. 右臂放在已知观察位，先运行 `from-observation`；用带标签的不透明瓶，清空周围，
   速度保持 profile 当前的 `3%`。
2. 验证半瓶场景：让检测框只在画面底边截断，确认日志出现“保持头部锁定深度/抓取
   高度”，并完成抓放，而不是出现 `0/3` 复检。
3. 检查 `task_result.json` 和现场视频：瓶子确实被抬升、放稳、夹爪释放、手臂退开。
4. 再运行 `from-start`，重点核对 MoveIt 路径与现场障碍的距离、模型端点门禁、返回
   home 的实际反馈。
5. 至少连续三轮都得到真实 `DONE` 证据后，才能把对应的固定布置/profile 标记为已验收；
   更换桌子、瓶型、相机、标定或障碍布局后重新验收。
